---primer Почему `count++` из двух потоков теряет значения
`count++` выглядит как одно действие, но процессор делает три: прочитать, прибавить, записать.
Два потока могут прочитать одно и то же значение:

```text
Поток A: прочитал 5
Поток B: прочитал 5
Поток A: записал 6
Поток B: записал 6     ← один просмотр потерян
```

Это **гонка данных** (race condition). Способы защититься:

```csharp
// 1. lock: в блок заходит только один поток за раз
private readonly object _gate = new();
lock (_gate) { count++; }

// 2. Interlocked: атомарная операция процессора для одного числа, без блокировки
Interlocked.Increment(ref count);

// 3. Потокобезопасная коллекция
var dict = new ConcurrentDictionary<string, int>();
dict.AddOrUpdate("key", 1, (key, old) => old + 1);
```

Обычный `Dictionary` не рассчитан на одновременную запись: внутри он перестраивает массивы, и два потока могут сломать его состояние.

## Что ломалось

Два потока читали одно значение и оба записывали «+1» — один просмотр терялся. А обычный `Dictionary` при одновременной записи
ещё и портит своё внутреннее состояние: .NET замечает это и бросает исключение (в старом .NET Framework бывали даже вечные циклы).
Локально баг не воспроизводится, потому что один человек не создаёт сотни одновременных запросов. Такие баги ловят нагрузочными тестами,
как здесь с `Parallel.For`.

## lock, Interlocked или ConcurrentDictionary

- **`lock`** — самое понятное и универсальное: всё, что внутри, выполняется одним потоком. Минус — потоки стоят в очереди,
  и под большой нагрузкой это узкое место. Плюс — можно защитить сразу несколько полей **согласованно**
  (сумма по страницам всегда равна `Total`). С `ConcurrentDictionary` + `Interlocked` в момент между двумя действиями
  они могут разойтись на единицу.
- **`Interlocked`** — для одного числа, быстрее всего. Для двух связанных значений не подходит.
- **`ConcurrentDictionary`** — блокирует только часть словаря, разные страницы обновляются параллельно. Ловушка:
  делегат в `AddOrUpdate`/`GetOrAdd` **может выполниться несколько раз** при конфликте — внутри него нельзя делать
  побочных эффектов (запросов в базу, отправки писем).

Правило выбора: начинай с `lock` — его проще проверить. Переходи на lock-free, когда замер показал, что lock — узкое место.

## Почему Snapshot — копия

Отдать наружу ссылку на внутреннюю коллекцию — значит разрешить кому угодно читать её во время изменения (отсюда «Collection was modified»)
и видеть «живые» цифры. Возвращать копию или неизменяемую коллекцию — базовое правило инкапсуляции, а в многопоточном коде ещё и
вопрос корректности. Цена копии — память и время, поэтому снимок берут для отчётов, а не на каждый запрос.

## Как это решают в продакшене

Счётчики в памяти одного процесса пропадают при перезапуске и не складываются между несколькими серверами.
В реальной системе просмотры пишут в Redis (`INCR` атомарен) или копят в памяти и сбрасывают пачками в базу.
Для метрик есть `System.Diagnostics.Metrics` и OpenTelemetry.

---recall
Q: Что такое гонка данных (race condition)?
A: Несколько потоков одновременно читают и меняют общие данные, и результат зависит от порядка их выполнения — например, теряются инкременты.

Q: Чем различаются lock, Interlocked и ConcurrentDictionary?
A: lock — один поток в блоке, можно согласованно менять несколько полей; Interlocked — атомарная операция над одним числом; ConcurrentDictionary — потокобезопасный словарь с частичными блокировками.

Q: Какая ловушка у ConcurrentDictionary.GetOrAdd/AddOrUpdate?
A: Делегат может выполниться несколько раз при конфликте — внутри не должно быть побочных эффектов.
