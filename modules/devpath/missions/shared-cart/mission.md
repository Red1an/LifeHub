Это инцидент безопасности. Покупательница написала в поддержку: в её корзине лежат детские подгузники, которые она не добавляла.
Через час — ещё десять таких же писем. Хуже того, один покупатель **увидел чужую корзину** с адресом доставки.

Днём, когда покупателей мало, всё работает. Ломается в вечерний пик. Разработчик клянётся, что «корзина берётся строго по Id пользователя».

---task
Почини API в `src/CartApi`:

- 20 покупателей одновременно — каждый видит только свои товары;
- корзина сохраняется между запросами одного покупателя;
- запрос без заголовка `X-User` — `401 Unauthorized`.

Маршруты и формат ответа не меняй.

---primer Время жизни сервисов в DI
Контейнер внедрения зависимостей (DI) в ASP.NET Core создаёт объекты сам и раздаёт их тем, кто попросит в конструкторе.
Главный вопрос при регистрации — **как долго живёт объект**:

```csharp
services.AddSingleton<Clock>();      // один на всё приложение, на все запросы сразу
services.AddScoped<UnitOfWork>();    // один на запрос: в рамках запроса тот же, у другого запроса свой
services.AddTransient<Validator>();  // новый каждый раз, когда кто-то просит
```

Singleton видят **все запросы одновременно** — значит, в нём не должно быть данных конкретного запроса или пользователя,
и он должен быть потокобезопасным. Scoped — место для того, что относится к одному запросу: текущий пользователь,
`DbContext`, транзакция.

Ещё одно правило: сервис не может зависеть от сервиса, который живёт **меньше** его. Если singleton получает в конструкторе
scoped-объект, этот объект «застревает» в singleton навсегда — это называется captive dependency.

---debrief
## Что происходило

`CurrentUser` был один на всё приложение. Каждый запрос перезаписывал его `Id`, а `CartService` читал `Id` после `await`,
когда его уже переписал чужой запрос. Днём запросы почти не пересекаются во времени, вечером — постоянно.
Классическая гонка, только спрятанная в настройке DI, а не в коде с потоками.

## Почему именно Scoped

- **Singleton** для данных запроса — то, что сломалось здесь.
- **Transient** для `CurrentUser` тоже не сработает: middleware получил бы **один** экземпляр и записал в него Id,
  а `CartService` — **другой**, пустой. Transient — для лёгких объектов без состояния.
- **Scoped** — ровно один экземпляр на запрос: middleware и `CartService` получают один и тот же объект,
  а у соседнего запроса — свой.

А хранилище остаётся singleton: если сделать его scoped, у каждого запроса будет своё пустое хранилище,
и корзина «потеряется» между запросами (тест 2).

## Captive dependency и проверка при старте

Если бы ты сделал scoped только `CurrentUser`, а `CartService` оставил singleton, приложение упало бы при первом запросе
с ошибкой «Cannot consume scoped service from singleton». ASP.NET Core в окружении Development проверяет это сам (`ValidateScopes`).
Это хорошая ошибка: она ловит гонку до того, как её увидят пользователи. Не выключай эту проверку.

## Как это делают в настоящих приложениях

Текущего пользователя берут не из самописного объекта, а из `HttpContext.User` (заполняется аутентификацией из токена или cookie).
В сервисах он доступен через `IHttpContextAccessor` или передаётся параметром. Заголовок `X-User`, которому верят на слово, —
дыра: любой может подставить чужой Id. Здесь он только для простоты.

## Как искать такие баги

Подозревай singleton, если баг появляется только под нагрузкой и данные «перетекают» между пользователями.
Пройдись по регистрациям: всё, что хранит изменяемое поле, в singleton должно быть потокобезопасным и не про конкретного пользователя.

---recall
Q: Чем отличаются Singleton, Scoped и Transient?
A: Singleton — один на приложение (общий для всех запросов, должен быть потокобезопасным), Scoped — один на запрос, Transient — новый при каждом запросе к контейнеру.

Q: Что такое captive dependency?
A: Сервис с долгим временем жизни (singleton) получает зависимость с коротким (scoped/transient), и она «застревает» в нём навсегда — например, один DbContext на всех.

Q: Почему данные текущего пользователя нельзя хранить в singleton?
A: Его видят все запросы одновременно: запросы перезаписывают данные друг друга, и пользователи видят чужое.
