Локально у разработчика всё было нормально — он добавлял в корзину один и тот же объект. А в приложении каждый запрос
загружает товар из базы заново.

---task
Почини `src/Shop/Cart.cs`:

- количество ≤ 0 — `ArgumentOutOfRangeException`.

Публичные сигнатуры `Cart` и `Product` не меняй.

---primer Равенство объектов
У класса по умолчанию **ссылочное** равенство: два объекта равны, только если это один и тот же объект в памяти,
даже если все поля совпадают.

```csharp
class Point { public int X; public int Y; }
var a = new Point { X = 1, Y = 2 };
var b = new Point { X = 1, Y = 2 };
Console.WriteLine(a.Equals(b)); // False — это два разных объекта
```

`Dictionary` и `HashSet` ищут ключ в два шага: сначала `GetHashCode()` выбирает «корзину», потом `Equals()` сравнивает.
Значит, чтобы два объекта считались одним ключом, нужно переопределить **оба** метода — или взять ключом то,
что уже сравнивается по значению (строку, число).

У `record` равенство по значению есть из коробки:

```csharp
record PointR(int X, int Y);
Console.WriteLine(new PointR(1, 2) == new PointR(1, 2)); // True
```

---debrief
## Почему было две строки

Словарь сравнивал объекты `Product` по ссылке. Два запроса — два объекта — два ключа. Тест разработчика проходил,
потому что он добавлял один и тот же объект. Это классика: тесты, которые не повторяют реальный сценарий («каждый запрос — новый объект»),
не ловят баг.

## Почему ключ — артикул, а не переопределённый Equals

Переопределить `Equals`/`GetHashCode` по `Sku` тоже бы помогло с дублями. Но тогда ключом словаря остаётся
**изменяемый** объект: корзина держит ссылку на товар, и если его цена поменялась, сумма корзины поменяется вслед за ней
(тест 5). А если бы `GetHashCode` зависел от изменяемого поля — например, от `Name`, — объект после переименования
вообще «потерялся» бы внутри словаря: лежит в старой корзине хэшей, а ищут его в новой.

Правило: ключ словаря должен быть **неизменяемым**. Лучший ключ — идентификатор (Id, артикул, email в нормализованном виде).

## Сущность и объект-значение

Это различие из DDD, и оно помогает выбирать:

- **Сущность** (Entity) — у неё есть идентичность: товар, заказ, пользователь. Два товара с одинаковым названием, но разными
  артикулами — разные товары. Сравнивают по Id.
- **Объект-значение** (Value Object) — определяется только значением: деньги, адрес, диапазон дат. 100 ₽ и 100 ₽ равны.
  Для них идеальны `record` — неизменяемые, с равенством по значению.

Строка корзины `Line(Price, Quantity)` — объект-значение, поэтому `record` и `with`.

## Контракт Equals и GetHashCode

Если переопределяешь `Equals` — переопредели и `GetHashCode`, иначе словарь сломается: равные объекты обязаны иметь равный хэш.
Обратное не обязательно: разные объекты могут совпасть по хэшу (коллизия), тогда словарь сравнит их через `Equals`.

---recall
Q: Как Dictionary находит ключ и что нужно переопределить, чтобы два объекта были одним ключом?
A: Сначала GetHashCode выбирает корзину, потом Equals сравнивает. Переопределять оба метода (или брать ключом неизменяемый идентификатор).

Q: Почему ключ словаря должен быть неизменяемым?
A: Хэш считается при добавлении; если поле, от которого он зависит, поменяется, элемент «потеряется» внутри словаря.

Q: Чем сущность отличается от объекта-значения?
A: Сущность имеет идентичность (сравнивается по Id), объект-значение определяется только значением (сравнивается по полям, обычно неизменяемый record).
