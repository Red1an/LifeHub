Админка магазина: таблица «Заказы» по 20 штук на странице. Когда заказов было сто, страница открывалась мгновенно.
Сейчас заказов 3000, страница открывается 6 секунд, а администратор базы прислал скриншот: на **одно** открытие
страницы приложение отправляет **41 запрос** и вдобавок вычитывает всю таблицу заказов целиком.

Через год заказов будет 300 000. Почини, пока не поздно.

---task
Перепиши `OrdersPage.Load` в `src/Orders/OrdersPage.cs`:

- результат тот же: новые заказы сверху, имя клиента, сумма и число позиций;
- не больше **двух** SQL-запросов на страницу (лучше — один);
- пропуск и лимит (`OFFSET`/`LIMIT`) выполняет база, а не C#;
- страница только для чтения — EF не должен отслеживать загруженные объекты;
- `page < 1`, `size < 1` или `size > 100` — `ArgumentOutOfRangeException`.

---primer IQueryable и где выполняется запрос
`db.Orders` — это `IQueryable`: пока ты пишешь `Where`, `OrderBy`, `Skip`, `Take`, `Select`, EF только собирает **SQL**.
Запрос уходит в базу, когда результат материализуют: `ToList()`, `First()`, `Count()`, `foreach`.

```csharp
var q = db.Orders.Where(o => o.Total > 1000).OrderBy(o => o.Id).Take(10);  // SQL ещё не ушёл
var list = q.ToList();  // SELECT … WHERE Total > 1000 ORDER BY Id LIMIT 10
```

Всё, что стоит **после** `ToList()`, выполняется уже в памяти C# — над всеми загруженными строками.

Если внутри `Select` обращаться к связанным данным (`o.Customer.Name`, `o.Lines.Sum(...)`), EF сам сделает `JOIN`
или подзапрос — **в том же** SQL. Это называется проекцией:

```csharp
var rows = db.Orders
    .Select(o => new { o.Id, Customer = o.Customer.Name, Lines = o.Lines.Count })
    .ToList();  // один запрос с JOIN и подзапросом
```

Проекция в DTO не создаёт сущностей, поэтому EF их и не отслеживает. Для запросов сущностей без изменений есть `AsNoTracking()`.

---hypothesis
Откуда берутся 41 запрос на 20 строк? И почему страница становится медленнее с ростом таблицы, хотя показываем всё равно 20 строк?

---hint
Найди в коде `ToList()`. Что выполняется до него (в базе), а что после (в памяти)? А внутри `foreach` — сколько раз ты обращаешься к `db`?

---hint
Один запрос за заказами + по два на каждый заказ (клиент и позиции) = 1 + 2·20. Это «N+1». Чтобы его не было,
связанные данные нужно получить **в том же** запросе. Подумай, как выразить строку таблицы одним `Select` по `db.Orders`,
используя навигационные свойства `o.Customer` и `o.Lines`.

---hint
`db.Orders.OrderByDescending(o => o.CreatedAt).ThenByDescending(o => o.Id).Skip(…).Take(size)
.Select(o => new OrderRow(o.Id, o.Customer.Name, o.CreatedAt, o.Lines.Sum(l => l.PriceKopecks * l.Qty), o.Lines.Sum(l => l.Qty))).ToList()`.
Проверки параметров — `ArgumentOutOfRangeException.ThrowIfLessThan` / `ThrowIfGreaterThan`.

---debrief
## Две проблемы сразу

1. **Пагинация в памяти.** `ToList()` стоял до `Skip/Take`, поэтому база отдавала **все** 3000 заказов, а C# выкидывал 2980.
   Время росло вместе с таблицей. Правило: всё, что сужает выборку (`Where`, `Skip`, `Take`), — до материализации.
2. **N+1.** Один запрос за списком плюс отдельные запросы для каждой строки. Каждый запрос — это поездка по сети в базу
   (в продакшене 0,5–2 мс даже на быстрой сети). 41 поездка вместо одной, а на странице по 100 — 201.

## Проекция, Include или ленивая загрузка

- **Проекция (`Select` в DTO)** — выбрано здесь. В SQL уходят только нужные колонки, суммы считает база, ничего не отслеживается.
  Лучший вариант для чтения: списков, отчётов, API.
- **`Include(o => o.Customer).Include(o => o.Lines)`** — загружает сущности целиком вместе со связанными. Нужен, когда
  сущности будут **меняться** и сохраняться. Для таблицы на чтение — лишние колонки и лишняя работа трекера.
  С несколькими коллекциями ещё и «декартов взрыв»: строки дублируются, тогда помогает `AsSplitQuery()`.
- **Lazy loading** (ленивая загрузка навигаций при обращении) прячет N+1 так, что его не видно в коде. Поэтому в EF Core
  он по умолчанию выключен, и многие команды его запрещают.

## Почему `ThenByDescending(o => o.Id)`

Если у двух заказов одинаковое время, база вправе отдавать их в любом порядке, и один заказ может оказаться на двух страницах
сразу, а другой — ни на одной. Для пагинации порядок должен быть **однозначным**: добавляй уникальный ключ последним.

## Когда OFFSET плохой

`OFFSET 100000` заставляет базу пройти и выбросить 100 000 строк. Для глубоких страниц и бесконечных лент используют
**keyset-пагинацию**: `WHERE (CreatedAt, Id) < (@lastDate, @lastId) ORDER BY … LIMIT 20`. Она быстрая на любой глубине,
но не умеет «прыгнуть на страницу 57». Выбор зависит от интерфейса: номера страниц — OFFSET, лента «показать ещё» — keyset.

## Как ловить такие проблемы

Включи логирование SQL в разработке (`LogTo(Console.WriteLine)` или уровень `Microsoft.EntityFrameworkCore.Database.Command`)
и смотри, сколько запросов делает экран. Тест, который считает запросы, как здесь, ловит N+1 до продакшена.

---recall
Q: Что такое проблема N+1?
A: Один запрос за списком и ещё по запросу на каждый элемент за связанными данными. Лечится проекцией в одном запросе или Include.

Q: Почему важно, где стоит ToList() в запросе EF Core?
A: Всё до ToList выполняется в базе (SQL), всё после — в памяти над всеми загруженными строками. Фильтры и пагинация — до него.

Q: Чем OFFSET-пагинация отличается от keyset?
A: OFFSET — простые номера страниц, но медленнее на глубоких страницах. Keyset (WHERE ключ < последний) быстрый на любой глубине, но без прыжка на произвольную страницу.
