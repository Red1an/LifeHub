Спроектируй ленту, как в соцсети: пользователь подписан на людей, видит их посты по времени (новые сверху), листает вниз.
У обычных пользователей сотни подписчиков, у звёзд — десятки миллионов.

---requirements
- 300 млн активных в день, каждый открывает ленту ~10 раз в день, пишет пост раз в 2 дня.
- Лента открывается быстрее 200 мс p99; новый пост друга появляется в ленте за несколько секунд.
- Можно отставание ленты от реального времени на десятки секунд; посты нельзя терять.

---think
- Собирать ленту при чтении (pull) или раскладывать пост по лентам подписчиков при записи (push / fan-out)? Посчитай, что выходит со звездой.
- Как устроить пагинацию «листай вниз», если сверху появляются новые посты?
- Где хранить ленты и что кэшировать?

---reference
## Нагрузка

Чтения: 300 млн × 10 / 86 400 ≈ 35 000/с (пики ×3). Посты: 150 млн/день ≈ 1700/с. Чтения в 20 раз чаще — оптимизируем чтение.

## Fan-out: при записи или при чтении

- **Fan-out on write (push)**: пост раскладывается id-шником в ленты всех подписчиков (Redis sorted set `feed:{user}`, score = время).
  Чтение ленты — один быстрый запрос. Цена: пост звезды с 50 млн подписчиков — 50 млн записей.
- **Fan-out on read (pull)**: лента собирается при открытии из постов всех, на кого подписан. Запись дешёвая, чтение дорогое (сотни источников, слияние).
- **Гибрид** (так делают в реальности): push для обычных авторов, pull для звёзд — при чтении к готовой ленте домешиваются свежие посты
  нескольких звёзд, на которых подписан пользователь.

## Хранение

Посты — в шардированном хранилище по автору (Cassandra / PostgreSQL с шардами), ленты — списки id в Redis, обрезанные до ~800 последних
(дальше — из pull). Контент постов по id — отдельный кэш (многие ленты ссылаются на один пост). Медиа — объектное хранилище + CDN.

## Раскладка

Пост → событие в Kafka → воркеры fan-out раскладывают по лентам пачками. Асинхронность даёт отставание в секунды, зато пик постов не
тормозит авторов. Неактивных пользователей можно не обслуживать push-ом (ленту соберут при входе).

## Пагинация

Не offset (новые посты сверху сдвигают страницы и дают дубли), а **курсор**: «дай 20 постов старше (score, id) последнего показанного».
Новые посты сверху — отдельным запросом «что новее первого показанного».

## Отказы

Потеря Redis-лент не потеря данных: ленты восстанавливаются из постов (pull). Повторная раскладка идемпотентна (sorted set: тот же id не
дублируется). Горячие ключи (пост звезды) — реплицированный кэш.

## Что спросят дальше

Ранжирование вместо времени (ML-скоринг поверх кандидатов), удаление поста и приватность (удалить из лент или фильтровать при чтении),
блокировки, рекомендации «не от подписок».
