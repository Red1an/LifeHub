Спроектируй сервис коротких ссылок (как bit.ly): пользователь присылает длинный URL, получает короткий `https://sh.rt/aZ3kQ9`,
переход по короткой ссылке перенаправляет на исходную.

---requirements
- 100 млн новых ссылок в месяц, переходов — в 100 раз больше, чем созданий.
- Переход — быстрее 50 мс p99, сервис доступен 99,95%.
- Ссылка живёт 5 лет, можно задать свой код (`sh.rt/sale`), можно задать срок жизни.
- Статистика переходов по дням — не обязательно в реальном времени.

---think
- Сколько это запросов в секунду на чтение и запись и сколько данных за 5 лет? Считай на салфетке.
- Как генерировать код: хэш URL, случайный, счётчик + base62? Что с коллизиями и с «угадыванием» чужих ссылок?
- Какой редирект: 301 или 302 — и как это влияет на статистику?
- Где узкое место при 4000 переходов в секунду и как кэшировать?
- Как считать переходы, не записывая в базу на каждый клик?

---reference
## Оценка нагрузки

100 млн в месяц ≈ 40 созданий/с (пики ×10 — 400/с), переходов ≈ 4000/с (пики 40 000/с). Запись на ссылку ~500 байт →
за 5 лет 6 млрд ссылок ≈ 3 ТБ. Нагрузка — на **чтение**, данные — терабайты: таблица «код → URL», которую надо уметь шардировать.

## API

- `POST /links { url, alias?, expiresAt? }` → `201 { code, shortUrl }`; занятый alias — `409`.
- `GET /{code}` → `302 Location: …`; нет или истекла — `404`.
- `GET /links/{code}/stats?from&to` → переходы по дням.

## Генерация кода

7 символов base62 = 3,5 трлн вариантов — хватает с запасом. Варианты:
- **Хэш URL** (первые 7 символов) — одинаковые URL дают одинаковый код (дедупликация), но коллизии надо проверять и разрешать.
- **Случайный** — проще всего, коллизии редкие, вставка с уникальным индексом и повтор при конфликте.
- **Счётчик + base62** — без коллизий, но коды последовательные (легко перебрать все ссылки) и нужен распределённый счётчик:
  выдавать диапазоны (по 10 000 номеров) каждому экземпляру. Перемешивание (биективная функция) скрывает последовательность.

Выбор для собеседования: случайный 7-символьный с уникальным индексом — просто и безопасно; счётчик с диапазонами — если важна предсказуемая производительность записи.

## Хранение и кэш

Ключ-значение по коду: PostgreSQL с шардированием по хэшу кода или Cassandra/DynamoDB. Переходы — горячие (20% ссылок дают 80% переходов):
кэш Redis «код → URL» с TTL, cache-aside. Плюс CDN/edge-кэш для самых популярных. 4000 переходов/с Redis держит одним узлом.

## Редирект и статистика

**301** кэшируется браузером — следующие переходы не дойдут до сервиса (меньше нагрузки, но статистика неполная). **302** — каждый переход
приходит к нам: выбираем 302, если статистика важна. Клики не пишем в базу синхронно: событие в Kafka (или счётчики в Redis) → агрегатор
раз в минуту пишет `(code, day) += n`. Переход не ждёт статистику.

## Отказы и масштаб

Сервис переходов stateless за балансировщиком; Redis — с репликой; база — реплики на чтение. Упал кэш — нагрузка на базу вырастет в разы:
нужна защита (ограничение конкурентных промахов на один ключ — request coalescing). Удаление истёкших — фоновой задачей, а не при чтении.

## Что спросят дальше

Злоупотребления (фишинг, спам — проверка URL по спискам), rate limit на создание, кастомные домены, GDPR (удаление по запросу).
