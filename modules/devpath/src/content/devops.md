# @devops-linux

## Процессы и сервисы
Всё в Linux — файлы и процессы. У процесса есть PID, родитель, пользователь, открытые файлы, сигналы.
- `ps aux`, `top`/`htop` — что запущено и сколько ест;
- `kill -TERM <pid>` — вежливо попросить завершиться (можно перехватить), `kill -KILL` — убить немедленно;
- **systemd** управляет сервисами: `systemctl status|start|restart myapp`, логи — `journalctl -u myapp -f`.

## Файлы и права
Права `rwx` для владельца, группы, остальных: `-rw-r----- app app config.json`. `chmod 640`, `chown app:app`. Сервисы запускают от отдельного пользователя без прав root.

Полезное: `ls -la`, `find / -name "*.log" -mtime +7`, `du -sh *`, `df -h` (место на дисках), `tail -f`, `less`.

## Текстовые конвейеры
Сила Linux — маленькие утилиты, соединённые `|`:
```bash
# топ-10 IP по числу запросов в логе nginx
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head
# все ошибки за последний час сервиса
journalctl -u orders --since "1 hour ago" | grep -i error
```
`grep`, `sed` (замена), `awk` (колонки), `cut`, `sort`, `uniq`, `xargs`, `jq` (JSON).

## Диагностика
- **Сеть**: `ss -tlnp` (кто слушает порты), `curl -v`, `dig`, `ping`, `traceroute`.
- **Файлы процесса**: `lsof -p <pid>` (утечка дескрипторов?).
- **Системные вызовы**: `strace -p <pid>` — что процесс делает прямо сейчас.
- **Память**: `free -h`, OOM killer в `dmesg`.
- **Нагрузка**: load average в `uptime` — среднее число готовых к выполнению процессов.

# @devops-bash

## Основы скриптов
```bash
#!/usr/bin/env bash
set -euo pipefail   # падать на ошибке, на неизвестной переменной и на ошибке в конвейере

APP=${1:?"укажите имя приложения"}
for host in web1 web2; do
  echo "Деплой $APP на $host"
  ssh "$host" "sudo systemctl restart $APP" || { echo "ошибка на $host"; exit 1; }
done
```
- Переменные в кавычках: `"$var"` — иначе пробелы и `*` сломают логику.
- Код возврата `$?`: 0 — успех, иначе ошибка. `&&` и `||` для условного выполнения.
- Функции, `if [[ -f file ]]`, `case`, массивы, `$(команда)` для подстановки.

## PowerShell
PowerShell передаёт по конвейеру **объекты**, а не текст — не нужно парсить колонки:
```powershell
Get-Process | Where-Object CPU -gt 100 | Sort-Object CPU -Descending | Select-Object -First 5 Name, CPU
Get-ChildItem -Recurse *.log | Where-Object LastWriteTime -lt (Get-Date).AddDays(-7) | Remove-Item
```
Работает и на Linux (pwsh). Удобен для Windows-инфраструктуры, Azure, администрирования.

## Планировщики
- **cron**: `0 3 * * * /opt/backup.sh` — каждый день в 3:00. Поля: минута, час, день месяца, месяц, день недели.
- **systemd timers** — современная альтернатива с логами в journald.
- **Планировщик заданий Windows** / `Register-ScheduledTask`.

Правило: сложная логика — не в bash. Когда скрипт больше 100 строк, пишите на Python/C#/PowerShell или используйте Ansible.

# @devops-git

## Модель Git
Git хранит **снимки** (коммиты) в виде графа. Ветка — просто подвижный указатель на коммит, `HEAD` — где вы сейчас. Три зоны: рабочая директория → индекс (`git add`) → репозиторий (`git commit`).

## Merge vs rebase
- **merge** — создаёт merge-коммит, история правдивая, но ветвистая.
- **rebase** — переносит ваши коммиты поверх другой ветки, история линейная, но коммиты **переписываются** (новые хэши).
Правило: **не делайте rebase опубликованных веток**, которыми пользуются другие. Свою фича-ветку перед PR — можно (`git rebase -i` для чистки коммитов: squash, reword, fixup).

## Спасательные инструменты
- `git reflog` — журнал перемещений HEAD: вернуть «потерянный» коммит после неудачного reset/rebase.
- `git bisect` — бинарный поиск коммита, в котором появился баг.
- `git cherry-pick <sha>` — перенести конкретный коммит (хотфикс в релизную ветку).
- `git stash` — временно убрать изменения.
- `git revert` — отменить коммит новым коммитом (безопасно для общей истории), в отличие от `reset`.

## Процессы
- **Trunk-based development** — короткие ветки (часы/дни), частые мержи в main, feature flags для незаконченного. Основа CI/CD.
- **Git flow** — develop/release/hotfix ветки; тяжеловесен, подходит для редких релизов коробочных продуктов.
- **Conventional commits** (`feat:`, `fix:`, `feat!:`) + **semver** (MAJOR.MINOR.PATCH) позволяют генерировать changelog и версии автоматически.

Q: Чем git revert отличается от git reset?
A: revert создаёт новый коммит, отменяющий изменения указанного, — история сохраняется, безопасно для общих веток. reset перемещает указатель ветки назад, «удаляя» коммиты из истории ветки — переписывает историю.

# @devops-docker

## Образы и контейнеры
**Образ** — неизменяемый шаблон из слоёв (файловая система + метаданные). **Контейнер** — запущенный экземпляр образа со своим записываемым слоем. Контейнер — это обычный процесс Linux, изолированный:
- **namespaces** — что процесс видит (свои PID, сеть, файловая система, hostname);
- **cgroups** — сколько ресурсов может использовать (CPU, память).
Ядро общее с хостом — поэтому контейнер легче виртуальной машины.

## Dockerfile для .NET
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src
COPY *.csproj ./
RUN dotnet restore                      # слой кэшируется, пока не изменился csproj
COPY . .
RUN dotnet publish -c Release -o /app --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:9.0-noble-chiseled   # минимальный образ без shell
WORKDIR /app
COPY --from=build /app .
USER $APP_UID
ENTRYPOINT ["dotnet", "Orders.Api.dll"]
```
- **Multi-stage**: сборка в образе с SDK, в итоговый — только результат. Образ меньше и безопаснее.
- **Кэш слоёв**: сначала копируем то, что меняется редко (csproj → restore), потом код.
- **Не root**, минимальный базовый образ (chiseled/distroless), `.dockerignore` (bin, obj, .git).

## Сети и данные
- Контейнеры в одной пользовательской сети находят друг друга **по имени сервиса**.
- Данные, которые должны пережить контейнер, — в **volumes**. Контейнер эфемерен.

## docker compose
```yaml
services:
  api:
    build: .
    ports: ["8080:8080"]
    environment:
      ConnectionStrings__Db: "Host=db;Database=app;Username=app;Password=secret"
    depends_on:
      db: { condition: service_healthy }
  db:
    image: postgres:17
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: secret, POSTGRES_DB: app }
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD", "pg_isready", "-U", "app"], interval: 5s }
volumes: { pgdata: {} }
```

# @devops-cicd

## CI и CD
- **Continuous Integration** — каждый коммит/PR автоматически собирается и тестируется. Проблемы интеграции находятся за минуты.
- **Continuous Delivery** — каждая сборка main готова к выкладке одной кнопкой.
- **Continuous Deployment** — выкладка в прод автоматически после прохождения проверок.

## Конвейер
```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: 9.0.x }
      - run: dotnet restore
      - run: dotnet build --no-restore -c Release
      - run: dotnet test --no-build -c Release
```
Типичные стадии: сборка → юнит-тесты → статический анализ и проверка зависимостей → сборка образа → интеграционные тесты → публикация артефакта → деплой на staging → smoke-тесты → прод.

Принципы: **собрать артефакт один раз** и продвигать его между окружениями; конвейер быстрый (кэш зависимостей, параллельные джобы); секреты — в хранилище CI, не в репозитории.

## Стратегии выкладки
- **Rolling** — экземпляры обновляются постепенно (по умолчанию в Kubernetes).
- **Blue-green** — две полные среды, переключение трафика целиком; мгновенный откат.
- **Canary** — новая версия получает 1–5% трафика, по метрикам увеличиваем долю или откатываем.
- **Feature flags** — код выкачен, но функция включается флагом (для части пользователей) — деплой отделён от релиза.

A: Отделить деплой от релиза: код выкатывается выключенным, функция включается для части пользователей, можно быстро выключить без отката, делать A/B-тесты и trunk-based development с незавершёнными фичами.

# @devops-k8s

## Архитектура
- **Control plane**: API server (всё общение через него), **etcd** (хранилище состояния), scheduler (куда поставить под), controller manager (приводит реальность к желаемому).
- **Узлы**: kubelet (запускает поды), контейнерный рантайм, kube-proxy (сеть сервисов).

Главная идея — **декларативность**: вы описываете желаемое состояние в YAML, контроллеры непрерывно приводят кластер к нему (reconciliation loop).

## Основные объекты
- **Pod** — один или несколько контейнеров с общей сетью и томами; эфемерен.
- **Deployment** → ReplicaSet → Pod-ы: нужное число реплик, rolling update, откат.
- **Service** — стабильное имя и IP для группы подов (балансировка).
- **Ingress** / Gateway API — HTTP-маршрутизация извне.
- **ConfigMap** / **Secret** — конфигурация и секреты (Secret лишь в base64, не шифрование!).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 3
  selector: { matchLabels: { app: orders } }
  template:
    metadata: { labels: { app: orders } }
    spec:
      containers:
        - name: api
          image: ghcr.io/me/orders:1.4.2
          ports: [{ containerPort: 8080 }]
          resources:
            requests: { cpu: 100m, memory: 256Mi }
            limits: { memory: 512Mi }
          readinessProbe: { httpGet: { path: /health/ready, port: 8080 } }
          livenessProbe: { httpGet: { path: /health/live, port: 8080 } }
```

## Probes и ресурсы
- **readiness** не прошла — под убирают из балансировки; **liveness** — контейнер перезапускают; **startup** — даёт медленному старту время.
- **requests** — гарантированные ресурсы, по ним планировщик размещает поды; **limits** — потолок. Превышение памяти → **OOMKilled**, CPU → троттлинг.

---recall
Q: Чем readiness probe отличается от liveness probe?
A: Readiness определяет, готов ли под принимать трафик: при неудаче его исключают из Service, но не перезапускают. Liveness определяет, жив ли процесс: при неудаче kubelet перезапускает контейнер.

Q: Что такое requests и limits?
A: Requests — ресурсы, которые планировщик резервирует для пода при размещении на узле. Limits — максимум: по памяти превышение приводит к OOMKill, по CPU — к троттлингу.

# @devops-networking

## Сети Docker
- **bridge** (по умолчанию) — изолированная сеть на хосте, NAT наружу, порты публикуются `-p 8080:80`. В пользовательской bridge-сети есть DNS по именам контейнеров.
- **host** — контейнер использует сеть хоста напрямую (быстрее, нет изоляции портов).
- **overlay** — сеть поверх нескольких хостов (Swarm).
- **none** — без сети.

## Сеть Kubernetes
Модель: у каждого пода свой IP, все поды видят друг друга без NAT. Реализуют её **CNI-плагины** (Calico, Cilium, Flannel).

Типы **Service**:
- **ClusterIP** — внутренний виртуальный IP (по умолчанию);
- **NodePort** — порт на каждом узле;
- **LoadBalancer** — внешний балансировщик облака;
- **Headless** (`clusterIP: None`) — DNS возвращает IP подов напрямую (для StatefulSet).

**DNS** в кластере (CoreDNS): `orders.shop.svc.cluster.local` → IP сервиса. Внутри одного namespace достаточно `orders`. **kube-proxy** программирует iptables/IPVS (или eBPF в Cilium) для балансировки.

## Вход снаружи
**Ingress** — правила HTTP-маршрутизации (хост, путь → сервис), реализуется **контроллером** (ingress-nginx, Traefik). Новое поколение — **Gateway API**: более выразительные маршруты, разделение ролей (инфраструктура/приложение).

**NetworkPolicy** ограничивает, какие поды с какими могут общаться (по умолчанию — все со всеми).

# @devops-iac

## Infrastructure as Code
Инфраструктура описывается кодом в git: воспроизводимо, ревьюится, есть история, нет «снежинок», настроенных руками.

## Terraform
Декларативный: описываете ресурсы, Terraform вычисляет разницу с реальностью.
```hcl
resource "azurerm_postgresql_flexible_server" "db" {
  name     = "orders-db"
  sku_name = "B_Standard_B1ms"
  version  = "16"
  # ...
}
```
- `terraform plan` — что изменится; `apply` — применить.
- **State** — сопоставление кода и реальных ресурсов. Хранится **удалённо с блокировкой** (S3 + DynamoDB, Azure Storage, Terraform Cloud), иначе два человека испортят инфраструктуру.
- **Модули** — переиспользуемые блоки.
- **Дрейф** — ручные изменения в облаке; `plan` его показывает.
Альтернативы: OpenTofu (open-source форк), Pulumi (IaC на C#/TypeScript), Bicep (Azure).

## Ansible
Конфигурирует **серверы**: пакеты, файлы, сервисы. Агентов нет — работает по SSH. Плейбуки в YAML, **идемпотентны** (повторный запуск не ломает).

## GitOps
Желаемое состояние кластера — в git-репозитории, **агент в кластере** (Argo CD, Flux) непрерывно синхронизирует. Деплой = merge PR с новым тегом образа; откат = revert; всё аудируется. CI собирает образ, но не ходит в кластер с правами админа.

# @devops-cloud

## Модели
- **IaaS** — виртуальные машины, сети, диски (вы администрируете ОС).

- **Serverless** — функции и контейнеры с оплатой за вызовы (Azure Functions, AWS Lambda, Cloud Run).

# @devops-observability

## Метрики и Prometheus
Prometheus **собирает** (pull) метрики с эндпоинтов `/metrics` и хранит временные ряды с метками:
```
http_server_request_duration_seconds_bucket{route="/orders",status="200",le="0.1"} 1532
```
Типы: counter (только растёт), gauge (текущее значение), histogram (распределение, перцентили).

**PromQL**:
```
sum(rate(http_server_request_duration_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_request_duration_seconds_count[5m]))          # доля ошибок
histogram_quantile(0.95, sum by (le) (rate(http_server_request_duration_seconds_bucket[5m])))  # p95
```
Осторожно с **кардинальностью**: метка с user_id создаст миллионы рядов и положит Prometheus.

## Дашборды и алерты
Grafana — дашборды поверх Prometheus, Loki, Tempo. Алертить нужно на **симптомы**, которые видит пользователь (ошибки, латентность), а не на каждую причину (CPU 80%).

Методы:
- **RED** для сервисов: Rate, Errors, Duration.
- **USE** для ресурсов: Utilization, Saturation, Errors.
- **Four golden signals** (Google SRE): латентность, трафик, ошибки, насыщение.

## Логи и трейсы
- Логи: **Loki** (индексирует только метки, дёшево) или ELK/OpenSearch (полнотекст). Логи структурные, с trace id.
- Трейсы: OpenTelemetry → **Tempo**/Jaeger. Сэмплирование, чтобы не хранить всё.
- **OpenTelemetry Collector** — единая точка приёма, обработки и отправки телеметрии.

# @devops-sre

## SLI, SLO, SLA
- **SLI** — измеримый показатель: доля успешных запросов, доля запросов быстрее 300 мс.
- **SLO** — целевое значение SLI: 99.9% успешных запросов за 30 дней.
- **SLA** — договор с клиентами с последствиями (компенсации); обычно мягче SLO.

## Error budget
Бюджет ошибок = 1 − SLO. При 99.9% за 30 дней это ~43 минуты недоступности. Пока бюджет есть — команда смело выпускает фичи. Бюджет исчерпан — фокус на надёжности, заморозка рискованных релизов. Это превращает спор «скорость vs стабильность» в инженерный расчёт. 100% — неправильная цель: бесконечно дорого и не нужно пользователям.

## Инциденты
- Дежурства (on-call), понятные runbook-и.
- Во время инцидента: роли (координатор, связь, исполнители), сначала **смягчить** (откат, отключить фичу), потом чинить.
- **Постмортем без обвинений**: хронология, причины (5 почему), что помогло, что помешало, конкретные действия с владельцами. Цель — улучшить систему, а не найти виноватого.

## Прочие практики
- **Toil** — ручная повторяющаяся работа; автоматизировать, ограничивать долю (≤50% времени).
- **Capacity planning** — прогноз нагрузки и ресурсов.
- **Chaos engineering** — намеренно вносить сбои (убить под, добавить задержку), чтобы проверить устойчивость до реального инцидента.

Q: Чем SLI, SLO и SLA отличаются друг от друга?
A: SLI — метрика качества сервиса (доля успешных/быстрых запросов). SLO — внутренняя целевая планка для SLI. SLA — внешнее соглашение с клиентом с последствиями за нарушение, обычно менее строгое, чем SLO.

# @devops-security

## Безопасность в конвейере
DevSecOps — встроить безопасность в каждый шаг, а не проверять в конце («shift left»).
- **SAST** — статический анализ кода (Roslyn-анализаторы, SonarQube, Semgrep, CodeQL).
- **SCA** — уязвимые зависимости (`dotnet list package --vulnerable`, Dependabot, Renovate, Snyk).
- **Сканирование образов** — Trivy, Grype.
- **DAST** — атака на работающее приложение (OWASP ZAP).
- **Поиск секретов** в коде и истории git (gitleaks).

## Секреты
Никаких секретов в git, в образах, в логах. Хранилища: HashiCorp Vault, облачные Key Vault/Secrets Manager; в Kubernetes — External Secrets Operator, Sealed Secrets, SOPS. Ротация и короткоживущие учётные данные (динамические секреты Vault).

## Цепочка поставок
Атаки через зависимости и сборку (SolarWinds, xz). Защита:
- **SBOM** — перечень компонентов (CycloneDX, SPDX);
- подписанные образы (**cosign/Sigstore**) и проверка подписи при деплое;
- фиксированные версии, lock-файлы, приватные зеркала пакетов;
- минимальные базовые образы, воспроизводимые сборки.

## Политики
**Policy as code**: OPA/Gatekeeper или Kyverno запрещают в кластере небезопасное (контейнеры от root, образы без подписи, отсутствие лимитов).

# @devops-nginx

## Reverse proxy
Nginx (или Traefik, HAProxy, Envoy, YARP) стоит перед приложениями:
- TLS-терминация и HTTP/2/3;
- балансировка между экземплярами;
- сжатие, кэш, отдача статики;
- лимиты запросов и размеров тела, защита от медленных клиентов.

```nginx
upstream orders { server 10.0.0.11:8080; server 10.0.0.12:8080; }
server {
  listen 443 ssl http2;
  server_name api.example.com;
  ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
  location / {
    proxy_pass http://orders;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

## L4 и L7
- **L4** (TCP/UDP) — балансировка соединений, не видит HTTP.
- **L7** (HTTP) — маршрутизация по хосту, пути, заголовкам, ретраи, куки.
Алгоритмы: round robin, least connections, IP hash (липкость), взвешенные.

## TLS
Сертификаты от Let's Encrypt бесплатно (certbot, cert-manager в Kubernetes), автопродление. Только TLS 1.2+/1.3, HSTS.

## YARP
YARP — reverse proxy как библиотека .NET: конфигурация маршрутов, трансформации, балансировка, health checks — и всё это расширяемо кодом на C#. Хорош для API gateway и BFF на .NET.
