# @sysdesign-method

## Структура ответа (45 минут)
1. **Требования (5–7 мин)**: функциональные (что делает система, 3–5 ключевых сценариев) и нефункциональные (масштаб, латентность, доступность, согласованность). Спрашивайте, не додумывайте.
2. **Оценки (3–5 мин)**: пользователи, RPS чтения/записи, объём хранения, трафик.
3. **API (3–5 мин)**: основные эндпоинты или сообщения.
4. **Модель данных**: сущности, выбор хранилища.
5. **Высокоуровневая схема**: клиенты → балансировщик → сервисы → хранилища, кэши, очереди.
6. **Углубление (15–20 мин)**: узкие места, масштабирование, отказы, компромиссы — то, что интересно интервьюеру.
7. **Итог**: что бы улучшили дальше.

## Оценки на салфетке
- В сутках ~10⁵ секунд: 100 млн запросов в сутки ≈ 1 200 RPS в среднем, пик ×2–5.
- Твит 300 байт × 500 млн в сутки ≈ 150 ГБ/сутки ≈ 55 ТБ/год.
- Один сервер приложения: тысячи RPS простых запросов; PostgreSQL на хорошем железе — десятки тысяч простых запросов в секунду; Redis — сотни тысяч операций в секунду.
- Соотношение чтения к записи часто 10:1 – 100:1 → кэши и реплики.

## Строительные блоки
Балансировщик, stateless-сервисы, кэш (Redis), SQL/NoSQL, реплики и шарды, очередь (Kafka/RabbitMQ), объектное хранилище, CDN, поиск (Elasticsearch), фоновые воркеры, rate limiter, сервис уведомлений.

## Что оценивают
Не «правильную» схему (её нет), а умение: уточнить требования, считать, обосновывать выбор **компромиссами** («SQL, потому что нужны транзакции для оплаты; ценой будет сложное шардирование»), находить узкие места и отказы, вести диалог.

# @sysdesign-shortener

## Требования
Создать короткую ссылку, редирект по ней, (опционально) свой алиас, срок жизни, статистика. Нагрузка: 100 млн новых ссылок в месяц, чтение в 100 раз чаще — ~4 000 RPS редиректов в среднем. Хранение: 100 млн × 12 мес × 5 лет × ~500 байт ≈ 3 ТБ.

## Генерация кода
- **Base62** (a-z, A-Z, 0-9): 7 символов = 62⁷ ≈ 3.5 трлн вариантов — хватит.
- Варианты:
  1. **Счётчик + base62** — нет коллизий, но коды предсказуемы и нужен распределённый счётчик (выдавать диапазоны id каждому серверу, Snowflake-подобные id).
  2. **Хэш URL** (первые 7 символов) — коллизии надо проверять и разрешать.
  3. **Случайный код** + проверка уникальности (уникальный индекс, повтор при конфликте).

## Схема
`POST /links` → сервис → БД (`code PK, long_url, created, expires`). `GET /{code}` → кэш (Redis, горячие ссылки) → при промахе БД → **301 или 302**. 301 кэшируется браузером (меньше нагрузки, но теряем статистику), 302 — каждый переход идёт к нам.

## Масштабирование
- Чтение: кэш с LRU (20% ссылок дают 80% трафика), реплики БД, CDN/edge для самых горячих.
- Хранилище: key-value (DynamoDB/Cassandra) или шардированный Postgres по code.
- Статистика: не писать в БД синхронно на каждый клик — событие в Kafka → агрегирование в аналитическом хранилище (ClickHouse).
- Защита: rate limiting создания, проверка URL на фишинг.

# @sysdesign-ratelimiter

## Требования
Ограничить число запросов клиента (по ключу API, пользователю, IP): например, 100 в минуту. Распределённо — много экземпляров API. Минимальная задержка, отказоустойчивость, понятные ответы 429 с заголовками (`Retry-After`, `X-RateLimit-Remaining`).

## Алгоритмы
- **Fixed window** — счётчик на минуту; просто, но на стыке окон пропускает 2× лимит.
- **Sliding window log** — хранить метки всех запросов; точно, но дорого по памяти.
- **Sliding window counter** — взвешенная комбинация двух соседних окон; дёшево и достаточно точно.
- **Token bucket** — корзина с токенами пополняется с постоянной скоростью; допускает всплески до размера корзины. Самый популярный.
- **Leaky bucket** — очередь с постоянной скоростью вытекания; сглаживает трафик.

## Распределённое состояние
Счётчики в **Redis**: атомарность через Lua-скрипт или `INCR` + `EXPIRE`. Задержка — один сетевой вызов. Варианты оптимизации: локальные приблизительные счётчики с периодической синхронизацией, шардирование ключей.

Отказ Redis: **fail open** (пропускать — риск перегрузки) или **fail closed** (отказывать — риск простоя). Обычно fail open + локальный лимит.

## Где ставить
На API gateway (единая точка, до бизнес-логики), в самом сервисе (тонкие правила), на уровне CDN/WAF (защита от DDoS). В ASP.NET Core — встроенный rate limiting middleware (локально) или кастомный на Redis.

Q: Как работает алгоритм token bucket?
A: У клиента корзина ёмкостью N токенов, пополняемая со скоростью R токенов в секунду. Каждый запрос забирает токен; нет токенов — отказ (429). Допускает всплески до N и ограничивает среднюю скорость значением R.

# @sysdesign-chat

## Требования
Личные и групповые чаты, доставка в реальном времени, история, статусы (отправлено, доставлено, прочитано), онлайн-статус, пуши офлайн-пользователям. Масштаб: сотни миллионов пользователей, десятки миллиардов сообщений в день.

## Соединения
Клиенты держат **WebSocket** к **gateway-серверам**. Каждый сервер держит сотни тысяч соединений. Нужен **реестр сессий**: пользователь → на каком gateway (Redis). Отправка: сервис сообщений сохраняет сообщение, находит gateway получателя и отправляет через него; если офлайн — пуш-уведомление.

## Хранение
Нагрузка — огромная запись, чтение последних сообщений чата. Подходит **wide-column** (Cassandra/ScyllaDB — так делал Discord): ключ партиции `chat_id` (+ временной бакет), кластеризация по `message_id` (упорядоченный по времени, Snowflake). Порядок сообщений — по серверному id внутри чата.

## Группы и статусы
- Маленькие группы — fan-out: сообщение отправляется каждому участнику.
- Огромные каналы — участники подтягивают сообщения сами (pull), без рассылки миллионам.
- Статусы «доставлено/прочитано» — лёгкие события, агрегировать для групп.
- Онлайн-статус — heartbeat, TTL в Redis, рассылка только друзьям/активным чатам (иначе шторм событий).

## Надёжность
At-least-once доставка + дедупликация по client message id; клиент досинхронизирует пропущенное после переподключения (по последнему полученному id).

# @sysdesign-feed

## Задача
Лента: посты тех, на кого подписан пользователь, свежие сверху (или ранжированные). Чтений ленты намного больше, чем публикаций.

## Fan-out on write (push)
При публикации пост записывается в заранее подготовленные ленты всех подписчиков (в Redis — список id постов на пользователя). Чтение ленты — мгновенное. Проблема — **знаменитости**: пост аккаунта с 50 млн подписчиков = 50 млн записей.

## Fan-out on read (pull)
При открытии ленты собираем посты всех, на кого подписан, и сортируем. Публикация дешёвая, чтение дорогое (сотни подписок).

## Гибрид
Обычные авторы — push; знаменитости — pull: при чтении ленты их свежие посты подмешиваются к готовой ленте. Неактивным пользователям ленту не предрассчитываем.

## Ранжирование и остальное
- Лента из id → **гидрация** данными постов из кэша (батчами).
- Ранжирование: кандидаты → модель (вероятность интереса) → разнообразие.
- Пагинация курсором, а не offset.
- Медиа — в объектном хранилище + CDN.

Q: Сравни fan-out on write и fan-out on read.
A: On write (push) — при публикации пост копируется в ленты подписчиков: чтение быстрое, запись дорогая, проблема знаменитостей. On read (pull) — лента собирается при чтении: запись дешёвая, чтение дорогое. На практике — гибрид.

# @sysdesign-notifications

## Требования
Отправка push, email, SMS, in-app; шаблоны и локализация; настройки пользователя (каналы, тихие часы, отписка); миллионы уведомлений в час; надёжная доставка без дублей и спама.

## Архитектура
Сервисы-источники публикуют события («заказ отправлен») → **сервис уведомлений**:
1. проверяет настройки и ограничения пользователя;
2. рендерит шаблон;
3. кладёт задание в **очередь по каналу** (приоритеты: одноразовые коды — срочно, маркетинг — фоном);
4. воркеры канала отправляют через провайдеров (APNs/FCM, почтовый сервис, SMS-шлюз).

## Надёжность
- Ретраи с backoff для временных ошибок провайдера, DLQ для безнадёжных.
- **Дедупликация**: ключ идемпотентности уведомления, чтобы ретрай не отправил SMS дважды.
- **Rate limits** провайдеров и пользователя (не больше N пушей в час).
- Фолбэк между каналами (push не доставлен → SMS для критичных).
- Трекинг: отправлено, доставлено, открыто — через колбэки провайдеров.

## Масштаб
Массовые рассылки — батчами, с растягиванием во времени; отдельные очереди, чтобы маркетинг не задерживал коды входа.

# @sysdesign-booking

## Задача
Бронирование мест (кино, концерт, самолёт): нельзя продать одно место дважды; на популярные события — пиковый наплыв (все хотят в первые минуты).

## Двойное бронирование
Варианты защиты:
- **Пессимистично**: `SELECT ... FOR UPDATE` на место в транзакции.
- **Оптимистично**: `UPDATE seats SET status='held', holder=@u WHERE id=@id AND status='free'` — обновилась 1 строка → успех, 0 → место заняли.
- Уникальный индекс на (событие, место) в таблице броней.

## Временный резерв
Пользователь выбирает место → **hold** на 10 минут (статус + `expires_at` или ключ в Redis с TTL) → оплата → confirmed. Истёкшие резервы освобождаются фоновой задачей или проверкой `expires_at` при выборе. Оплата — через идемпотентный платёжный вызов; если оплата прошла после истечения резерва — возврат или приоритетное удержание.

## Пиковый трафик
- **Виртуальная очередь** (waiting room): пользователи становятся в очередь и пускаются порциями.
- Кэш схемы зала и доступности (с небольшой задержкой), точная проверка — только при бронировании.
- Шардирование по событию; горячее событие — отдельные ресурсы.
- Защита от ботов: rate limiting, CAPTCHA, лимит мест на пользователя.

# @sysdesign-payments

## Главные требования
Корректность важнее скорости: **нельзя потерять и нельзя списать дважды**. Аудит каждого движения, соответствие регуляциям, интеграция с внешними платёжными провайдерами, которые тоже ненадёжны.

## Идемпотентность
Каждая платёжная операция имеет **ключ идемпотентности** от клиента. Сервер хранит ключ, статус и результат; повтор возвращает сохранённый результат. Внутренние вызовы провайдеру — тоже с ключом (Stripe, большинство эквайеров поддерживают).

## Двойная запись (ledger)
Деньги не «меняются», а **двигаются**: каждая операция — проводки с дебетом и кредитом на счетах, сумма всегда ноль. Баланс = сумма проводок. Записи неизменяемы: ошибка исправляется сторнирующей проводкой. Это даёт аудит и защиту от «исчезновения» денег.

## Статусы и неопределённость
Платёж проходит состояния: created → pending → succeeded/failed. Таймаут от провайдера — **неизвестный исход**: нельзя считать платёж неуспешным и повторять с новым ключом. Нужно запросить статус у провайдера или дождаться вебхука.

## Сверка
**Reconciliation**: ежедневно сравнивать свои записи с отчётами провайдеров и банков. Расхождения неизбежны (таймауты, ручные операции) — их находят и разбирают. Это последняя линия защиты.

# @sysdesign-storage

## Требования (Dropbox/Google Drive)
Загрузка и скачивание файлов любого размера, синхронизация между устройствами, общий доступ, версии. Миллионы пользователей, петабайты данных.

## Разбиение на блоки
Файлы режутся на **чанки** (например, 4 МБ), для каждого — хэш:
- **возобновляемая загрузка** — оборвалось на 70% — догружаем остаток;
- **дедупликация** — одинаковые блоки (у разных пользователей или версий) хранятся один раз;
- **дельта-синхронизация** — изменили часть файла — передаём только изменённые блоки.

## Метаданные и блоки раздельно
- **Метаданные** (файлы, папки, версии, права, список блоков) — в БД с транзакциями (шардирование по пользователю/workspace).
- **Блоки** — в объектном хранилище (S3), адрес = хэш.
Клиент загружает блоки **напрямую** в хранилище по подписанным URL (pre-signed), минуя серверы приложения, затем фиксирует версию в метаданных.

## Синхронизация
Клиент следит за локальными изменениями, сервер уведомляет о чужих (long polling/WebSocket), клиент запрашивает журнал изменений с последнего курсора. **Конфликты** (файл изменён на двух устройствах офлайн) — сохранить обе версии («копия с конфликтом»), а не молча перезаписывать.

Q: Как разрешать конфликты при синхронизации файлов?
A: Отслеживать версию, от которой сделано изменение; если сервер уже содержит более новую версию от другого устройства — не перезаписывать, а сохранить обе (конфликтная копия) и дать пользователю выбрать; для некоторых типов данных возможно автоматическое слияние.

# @sysdesign-search

## Автодополнение (typeahead)
Требования: подсказки после каждой буквы за < 100 мс, топ-5–10 популярных запросов с этим префиксом, учёт свежих трендов.

**Trie** — префиксное дерево, в каждом узле храним **заранее вычисленный топ-K** запросов поддерева: ответ = найти узел префикса и отдать его список, O(длина префикса). Обновление популярности — не на каждый запрос, а пакетно: логи запросов → агрегация (раз в час/сутки) → перестроение trie → раскатка. Горячие префиксы кэшируются (в том числе в CDN/браузере). Шардирование по префиксу.

## Поисковая система
- **Индексация**: документы → анализатор → инвертированный индекс (слово → список документов с позициями).
- **Шардирование** индекса по документам; запрос идёт во все шарды (scatter-gather), результаты сливаются.
- **Ранжирование**: BM25 (текстовая релевантность) + сигналы (популярность, свежесть, персонализация), часто learning-to-rank моделью на топ-N кандидатов.
- Обновление: near-real-time (сегменты, как в Lucene), синхронизация из источника через очередь/CDC.

Q: Как устроен распределённый полнотекстовый поиск?
A: Документы анализируются и попадают в инвертированный индекс, разбитый на шарды с репликами. Запрос рассылается по шардам, каждый возвращает свой топ, координатор сливает и переранжирует. Индекс обновляется потоком изменений из источника данных.
