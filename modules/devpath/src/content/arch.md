# @arch-solid

## Пять принципов
- **S — Single Responsibility**: у модуля одна причина для изменения (один «владелец» требований). Не «один метод», а одна ответственность перед одной группой пользователей.
- **O — Open/Closed**: расширяем поведение, не меняя проверенный код (стратегии, декораторы, плагины).
- **L — Liskov Substitution**: наследник заменяет базовый тип без сюрпризов — не усиливает предусловия, не ослабляет постусловия, не бросает неожиданных исключений.
- **I — Interface Segregation**: много маленьких интерфейсов лучше одного «божественного».
- **D — Dependency Inversion**: высокоуровневая политика не зависит от деталей; обе зависят от абстракций, а абстракция принадлежит высокому уровню.

## Нарушения на практике
```csharp
public class ReadOnlyList<T> : List<T>
{
    public new void Add(T item) => throw new NotSupportedException();  // нарушение LSP
}
```
Код, работающий с `List<T>`, внезапно падает. Правильно — реализовать `IReadOnlyList<T>`.

Типичное нарушение SRP — класс `OrderService` на 3000 строк: расчёт цен, отправка писем, генерация PDF, логирование.

## Связность и зацепление
Цель всех принципов — **высокая связность** (cohesion: то, что меняется вместе, лежит вместе) и **низкое зацепление** (coupling: модули мало знают друг о друге). Сюда же **закон Деметры**: общайся с ближайшими друзьями — `order.Customer.Address.City.Name` говорит о слишком глубоком знании структуры.

## Когда принципы вредят
Принципы — эвристики, а не законы. Интерфейс на каждый класс «для DIP», абстрактные фабрики фабрик, 15 файлов ради одной операции — это **преждевременная абстракция**. KISS и YAGNI: не делай того, что не нужно сейчас; абстракцию вводят, когда появилась вторая реализация или реальная потребность в подмене.

---recall
Q: Сформулируй SRP правильно.
A: У модуля должна быть одна причина для изменения — он отвечает перед одной группой заинтересованных лиц (одним источником требований). Это не «класс делает одну вещь», а «класс меняется по одной причине».

Q: Когда следование SOLID вредит?
A: Когда абстракции вводятся преждевременно: интерфейсы с единственной реализацией без нужды, лишние слои, паттерны ради паттернов. Код становится сложнее без выгоды. Баланс с KISS и YAGNI.

# @arch-patterns

## Порождающие
- **Factory Method / Abstract Factory** — создание объектов без привязки к конкретному классу. В .NET: `IHttpClientFactory`, `ILoggerFactory`.
- **Builder** — пошаговая сборка сложного объекта: `WebApplication.CreateBuilder`, `StringBuilder`, `HostBuilder`.
- **Singleton** — в современном коде почти всегда через DI (`AddSingleton`), а не статическое поле.

## Структурные
- **Decorator** — добавить поведение, обернув объект с тем же интерфейсом: кэш, логирование, ретраи вокруг репозитория. `Stream` → `BufferedStream` → `GZipStream`.
- **Adapter** — привести чужой интерфейс к нужному (обёртка над SDK внешнего сервиса).
- **Facade** — простой интерфейс к сложной подсистеме.
- **Proxy** — объект-заместитель (ленивая загрузка, прокси EF для lazy loading, клиенты gRPC).

## Поведенческие
- **Strategy** — взаимозаменяемые алгоритмы за общим интерфейсом (расчёт доставки разными службами).
- **Observer** — подписка на события (`event`, `IObservable`, доменные события).
- **Chain of Responsibility** — цепочка обработчиков: конвейер middleware, `DelegatingHandler` в HttpClient.
- **Mediator** — объекты общаются через посредника (MediatR).
- **Command** — действие как объект (очередь задач, undo).
- **Template Method** — скелет алгоритма в базовом классе, шаги — в наследниках (`BackgroundService.ExecuteAsync`).
- **State** — поведение меняется вместе с состоянием (статусы заказа).

## Как применять
Паттерн — **словарь для обсуждения** решений, а не цель. Сначала видишь проблему (много if по типу доставки), потом узнаёшь паттерн (Strategy), а не наоборот.

```csharp
public interface IShippingCalculator { string Carrier { get; } decimal Calc(Parcel p); }
// Все реализации регистрируются в DI, выбор — по Carrier:
var calc = calculators.Single(c => c.Carrier == order.Carrier);
```

Q: Чем Decorator отличается от Adapter?
A: Decorator сохраняет тот же интерфейс и добавляет поведение вокруг объекта. Adapter меняет интерфейс: приводит несовместимый интерфейс к ожидаемому.

# @arch-refactoring

## Что такое рефакторинг
Изменение структуры кода **без изменения поведения**. Маленькими шагами, каждый — с зелёными тестами. Рефакторинг — не отдельная задача «на потом», а часть работы: «сначала сделай изменение простым, потом сделай простое изменение» (Кент Бек).

## Запахи кода
- **Длинный метод**, **большой класс**;
- **дублирование**;
- **длинный список параметров** → объект-параметр;
- **стрельба дробью** — одно изменение требует правок в десяти местах;
- **завистливая функция** — метод больше работает с данными другого класса;
- **одержимость примитивами** — `string email`, `decimal amount` вместо `Email`, `Money`;
- **switch по типу** → полиморфизм;
- **комментарии, объясняющие «что»** → лучше понятное имя.

## Приёмы
Extract Method, Rename, Introduce Parameter Object, Replace Conditional with Polymorphism, Move Method, Extract Class, Replace Magic Number with Constant, Introduce Value Object. IDE (Rider, Visual Studio) делает большинство безопасно — пользуйтесь автоматическими рефакторингами.

## Легаси
Легаси по Майклу Физерсу — **код без тестов**. Алгоритм изменения:
1. найти точку изменения;
2. найти **шов** (seam), где можно подменить поведение;
3. разорвать зависимости (выделить интерфейс, внедрить через параметр);
4. написать **характеризационные тесты** — фиксируют текущее поведение, даже если оно странное;
5. изменить и отрефакторить.

Для больших систем — **strangler fig**: новая функциональность строится рядом, старая постепенно отмирает.

# @arch-layers

## Классическая слоистая архитектура
UI → Business Logic → Data Access. Проблема: бизнес-логика **зависит от доступа к данным**, в итоге домен пропитан EF-атрибутами, а логика растекается по сервисам и хранимым процедурам.

## Чистая / луковая / гексагональная
Общая идея — **зависимости направлены внутрь**, к домену:
- **Domain** — сущности, value objects, доменные правила. Никаких зависимостей от фреймворков.
- **Application** — сценарии использования (use cases), порты (интерфейсы репозиториев, шлюзов).
- **Infrastructure** — адаптеры: EF Core, HTTP-клиенты, брокеры, реализуют порты.
- **Presentation/API** — контроллеры, Minimal API.

Гексагональная (Ports & Adapters) формулирует так: приложение в центре, **порты** — его интерфейсы, **адаптеры** — подключение внешнего мира (входящие: HTTP, очередь; исходящие: БД, почта).

## Vertical Slice Architecture
Вместо горизонтальных слоёв — **срезы по фичам**: папка `Features/Orders/CreateOrder` содержит эндпоинт, команду, обработчик, валидацию. Меньше абстракций, изменения локальны, каждая фича может быть устроена по-своему (простая — прямой SQL, сложная — доменная модель).

## Как выбрать
- Небольшой CRUD — простая структура, не усложняйте.
- Богатая бизнес-логика — Clean/Hexagonal + DDD.
- Много независимых фич — Vertical Slices.
Соблюдение границ проверяйте тестами архитектуры (NetArchTest, ArchUnitNET), а не договорённостями.

A: Бизнес-логика в центре и не зависит от фреймворков, БД и UI; зависимости направлены внутрь; внешний мир подключается через порты (интерфейсы, объявленные внутри) и адаптеры (реализации снаружи). Это даёт тестируемость и заменяемость инфраструктуры.

# @arch-ddd

## Стратегический DDD
- **Ubiquitous language** — единый язык команды и бизнеса, он же в коде: если бизнес говорит «отгрузка», в коде нет `Delivery2`.
- **Bounded context** — граница, внутри которой термины однозначны. «Товар» в каталоге (описание, фото) и на складе (остатки, ячейки) — разные модели, и это нормально.
- **Context map** — как контексты связаны: partnership, customer-supplier, conformist, **anti-corruption layer** (переводчик, защищающий модель от чужой).
- **Event storming** — воркшоп с бизнесом на стикерах: доменные события → команды → агрегаты → границы контекстов.

## Тактический DDD
- **Entity** — имеет идентичность, живёт и меняется (`Order`).
- **Value Object** — определяется значением, неизменяем (`Money`, `Address`, `Email`).
- **Aggregate** — кластер объектов с **корнем**, который охраняет инварианты. Это граница транзакционной согласованности.
- **Domain Event** — факт, произошедший в домене (`OrderPaid`).
- **Repository** — коллекция агрегатов (по одному на агрегат).
- **Domain Service** — логика, которая не принадлежит одной сущности.

## Правила агрегатов
1. Изменения — только через методы корня: `order.AddLine(product, qty)`, а не `order.Lines.Add(...)`.
2. **Одна транзакция — один агрегат.** Другие агрегаты обновляются через доменные события (eventual consistency).
3. Ссылки на другие агрегаты — **по id**, а не объектами.
4. Агрегаты маленькие: большой агрегат = конфликты конкуренции и медленная загрузка.

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyList<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; }

    public void AddLine(ProductId product, int qty, Money price)
    {
        if (Status != OrderStatus.Draft) throw new DomainException("Заказ уже оформлен");
        if (qty <= 0) throw new DomainException("Количество должно быть положительным");
        _lines.Add(new OrderLine(product, qty, price));
    }
}
```

Q: Чем Entity отличается от Value Object?
A: Entity имеет идентичность, сохраняющуюся при изменении атрибутов (заказ №42 остаётся собой). Value Object определяется только значениями, неизменяем и сравнивается по значению (100 рублей = 100 рублей).

# @arch-testing

## Пирамида и трофей
Пирамида (много юнит, меньше интеграционных, мало E2E) хороша для богатой логики. Для типичных веб-сервисов — **трофей**: основной вес на интеграционных тестах через HTTP с реальной БД. Выбор зависит от того, где живёт риск.

## Тестовые двойники
- **Dummy** — заглушка, чтобы заполнить параметр.
- **Stub** — возвращает заранее заданные ответы.
- **Fake** — рабочая упрощённая реализация (in-memory репозиторий, FakeTimeProvider).
- **Mock** — проверяет, что с ним взаимодействовали определённым образом.
- **Spy** — записывает вызовы для последующей проверки.

Правило: мокайте **внешние границы**, которыми не владеете (платёжный шлюз, SMTP), а не свои внутренние классы.

## Тестируйте поведение, а не реализацию
Хрупкий тест проверяет, какие методы вызывались и в каком порядке. Устойчивый — наблюдаемый результат через публичный API: ответ, состояние, опубликованное событие. Тогда рефакторинг не ломает тесты.

## Тестируемая архитектура
Код легко тестировать, если:
- логика отделена от ввода-вывода (функциональное ядро, императивная оболочка);
- зависимости внедряются (время — `TimeProvider`, случайность, HTTP);
- нет статического состояния и скрытых синглтонов.

Архитектурные правила фиксируйте тестами:
```csharp
var result = Types.InAssembly(typeof(Order).Assembly)
    .Should().NotHaveDependencyOn("Microsoft.EntityFrameworkCore").GetResult();
Assert.True(result.IsSuccessful);
```

# @arch-cqrs

## CQRS
**Command Query Responsibility Segregation** — разные модели для записи и чтения.
- Уровень 1: разделение в коде (команды через домен, запросы — проекции/SQL). Дёшево и почти всегда полезно.
- Уровень 2: разные хранилища — запись в нормализованную БД, чтение из денормализованных **read-моделей** (другие таблицы, Elasticsearch, Redis), обновляемых по событиям. Даёт масштаб чтения, но добавляет **eventual consistency**.

## Event Sourcing
Вместо текущего состояния хранится **последовательность событий**: `AccountOpened`, `MoneyDeposited(100)`, `MoneyWithdrawn(30)`. Состояние = свёртка (fold) событий.

Плюсы:
- полный аудит и история «почему так»;
- можно построить новые проекции задним числом;
- естественная интеграция через события;
- отладка «путешествием во времени».

Минусы:
- **версионирование событий** (события вечны, схема меняется — upcasting);
- пересборка состояния (нужны **снапшоты** для длинных потоков);
- запросы только через проекции;
- сложность обучения команды.

## Когда оправдано
Event Sourcing — для доменов, где история — это суть: финансы, бухгалтерия, аудит, заказы со сложным жизненным циклом. Для CRUD-справочников — оверкилл. Инструменты в .NET: Marten (на PostgreSQL), EventStoreDB/KurrentDB.

A: Модель записи защищает инварианты, модели чтения оптимизированы под конкретные экраны и масштабируются отдельно. Цена — eventual consistency (чтение отстаёт), инфраструктура синхронизации, сложность.

# @arch-monolith

## Монолит — не ругательство
Один деплой, одна БД, вызовы — обычные методы: просто разрабатывать, отлаживать, транзакции работают. Проблемы начинаются, когда нет **внутренних границ** — «большой ком грязи»: всё зависит от всего.

## Модульный монолит
Один процесс, но код разделён на **модули по бизнес-возможностям** (Заказы, Каталог, Платежи) с явными границами:
- каждый модуль имеет публичный контракт (интерфейс/сообщения), внутренности `internal`;
- свои таблицы/схема БД, никаких джойнов в чужие таблицы;
- общение через контракты или внутренние события.
Это даёт большую часть пользы микросервисов без распределённой сложности, и модуль легко вынести в отдельный сервис позже.

## Микросервисы
Сервисы деплоятся независимо, у каждого своя БД, общение по сети.
Плюсы: независимые релизы и масштабирование, автономия команд, изоляция отказов, разные технологии.
Цена: сеть ненадёжна, распределённые транзакции, eventual consistency, наблюдаемость, инфраструктура (CI/CD, оркестрация), сложность локальной разработки.

**Закон Конвея**: архитектура повторяет структуру коммуникаций организации. Микросервисы решают прежде всего **организационную** проблему — много команд мешают друг другу.

## Распределённый монолит
Худший вариант: сервисы нельзя деплоить независимо, общая БД, синхронные цепочки вызовов A → B → C → D. Все минусы обоих подходов.

Миграция из монолита — **strangler fig**: новый функционал отдельно, трафик постепенно переключается через фасад/gateway.

A: Одно развёртываемое приложение, внутри разделённое на модули по бизнес-возможностям с явными контрактами и собственными данными. Простота монолита (один деплой, локальные вызовы, транзакции) плюс управляемые границы; модули можно позже вынести в сервисы.

# @arch-microservices

## Точки входа
- **API Gateway** — единая точка входа: маршрутизация, аутентификация, rate limiting, агрегация (YARP, Ocelot, Kong, облачные шлюзы).
- **BFF (Backend for Frontend)** — отдельный шлюз под каждый тип клиента (веб, мобильное приложение).

## Данные
**Database per service** — сервис владеет своими данными, другие получают их только через API или события. Без этого — распределённый монолит.

Как получить чужие данные:
- синхронный запрос (просто, но связывает доступность);
- **локальная копия** по событиям (быстро и автономно, eventual consistency);
- композиция на gateway/BFF.

## Согласованность
- **Saga** — длинная бизнес-операция как последовательность локальных транзакций с **компенсациями**. Оркестрация (центральный координатор) или хореография (сервисы реагируют на события друг друга).
- **Transactional outbox** — событие пишется в таблицу outbox в той же транзакции, что и данные; отдельный процесс публикует его в брокер. Решает проблему «сохранили в БД, но не отправили сообщение».
- **Inbox** — потребитель запоминает обработанные сообщения, чтобы повтор не выполнил действие дважды.

## Инфраструктура
Service discovery, конфигурация, централизованные логи и трейсы, **service mesh** (Istio, Linkerd): mTLS, ретраи и метрики на уровне сети без изменения кода. В .NET удобно: MassTransit/NServiceBus/Wolverine (саги, outbox), Dapr, Aspire.

# @arch-api

## REST, gRPC, GraphQL
- **REST** — ресурсы и HTTP-семантика; кэшируемость, простота, повсеместная поддержка.
- **gRPC** — строгий контракт, бинарный протокол, стриминг; для внутренних вызовов.
- **GraphQL** — клиент сам выбирает поля и связи одним запросом; удобно для сложных UI, но сложнее кэширование, авторизация на уровне полей и защита от тяжёлых запросов.

## Эволюция без поломок
Обратно совместимые изменения: добавить необязательное поле, новый эндпоинт, новое значение enum (если клиенты к этому готовы).
Ломающие: удалить/переименовать поле, изменить тип или смысл, сделать поле обязательным.

Правило **Постела** для клиентов: игнорируйте неизвестные поля. Для сервера: не удаляйте поля, пока их кто-то использует (метрики использования, deprecation-заголовки, сроки).

## Идемпотентность
Сеть ненадёжна — клиент повторит запрос. Для POST-операций с последствиями (платёж, заказ) клиент передаёт `Idempotency-Key`; сервер хранит ключ и результат и на повтор возвращает тот же ответ.

## Contract testing
Интеграционные тесты между сервисами дороги. **Consumer-driven contracts** (Pact): потребитель описывает, какие запросы и ответы ему нужны; провайдер в своей CI проверяет, что контракт не нарушен. Ломающее изменение ловится до деплоя.

A: Потребители API фиксируют ожидания (запросы и нужные поля ответов) в контракте; провайдер проверяет контракты в своей CI. Ломающие изменения обнаруживаются без дорогих сквозных интеграционных тестов.

# @arch-quality

## Нефункциональные требования
Архитектуру определяют не фичи, а **атрибуты качества**: производительность (латентность p99), масштабируемость, доступность (99.9%?), надёжность, безопасность, сопровождаемость, стоимость, time-to-market. Их надо **уточнять числами**: «быстро» ничего не значит, «p95 < 200 мс при 500 RPS» — значит.

## Архитектурные решения
Каждое решение — компромисс (trade-off). Хорошая практика — **ADR** (Architecture Decision Record):
- контекст и проблема;
- рассмотренные варианты;
- решение и почему;
- последствия (плюсы, минусы, риски).
Хранится в репозитории рядом с кодом. Через год ответ на «почему у нас так?» — в ADR, а не в памяти ушедшего сотрудника.

## Визуализация: C4
Четыре уровня зума:
1. **Context** — система и её окружение (пользователи, внешние системы);
2. **Container** — развёртываемые части: API, БД, фронтенд, брокер;
3. **Component** — модули внутри контейнера;
4. **Code** — классы (редко нужен).
Инструменты: Structurizr, PlantUML C4, draw.io, Mermaid.

## Фитнес-функции
Автоматические проверки, что архитектура не деградирует: тесты зависимостей между модулями, бюджеты производительности в CI, лимиты размера бандла, проверки безопасности. Эволюционная архитектура — изменения допустимы, пока фитнес-функции зелёные.

Q: Почему нефункциональные требования важнее для архитектуры, чем функциональные?
A: Одну и ту же функциональность можно реализовать почти любой архитектурой; выбор между монолитом и сервисами, синхронным и асинхронным взаимодействием, БД определяется требованиями к нагрузке, доступности, безопасности, стоимости и скорости изменений.

# @arch-integration

## Способы интеграции
- **Файловый обмен** — старо, но живо (выгрузки, SFTP).
- **Общая БД** — быстро сделать, больно жить: скрытая связанность.
- **Синхронный RPC/REST** — просто, но доступность систем связана.
- **Асинхронный обмен сообщениями** — развязка по времени и доступности, буферизация нагрузки.

## Enterprise Integration Patterns
Классический язык (Хоуп и Вульф):
- **Message Channel** — канал (очередь/топик);
- **Content-based Router** — маршрутизация по содержимому;
- **Message Translator** — преобразование форматов;
- **Splitter / Aggregator** — разбить и собрать сообщения;
- **Dead Letter Channel** — куда уходят необработанные;
- **Claim Check** — большое тело в хранилище, в сообщении — ссылка;
- **Idempotent Receiver** — безопасная повторная обработка.

## Получение изменений
- **Polling** — периодически спрашивать «что нового?» (просто, но задержка и лишняя нагрузка);
- **Webhooks** — система сама вызывает ваш URL (подписывайте запросы, делайте ретраи и идемпотентность);
- **CDC** — поток изменений из журнала БД.

## Схемы сообщений
Сообщения живут дольше кода. Договоритесь о формате (JSON Schema, Avro, Protobuf) и правилах эволюции (только добавлять необязательные поля). **Schema Registry** проверяет совместимость при публикации.

Q: Почему интеграция через общую базу данных считается плохой практикой?
