# @devops-linux

## Глубже: производительность и ядро
**Методология USE для сервера** (Брендан Грегг): для каждого ресурса — утилизация, насыщение, ошибки. Команды за 60 секунд: `uptime`, `dmesg -T | tail`, `vmstat 1`, `mpstat -P ALL 1`, `pidstat 1`, `iostat -xz 1`, `free -m`, `sar -n DEV 1`, `sar -n TCP,ETCP 1`, `top`.

**Память**: page cache — «свободная» память, занятая кэшем диска, это нормально; смотрите `available`. OOM killer выбирает процесс по `oom_score`; в контейнере — лимит cgroup.

**Файловые дескрипторы**: `ulimit -n`, «Too many open files» при утечке сокетов; `ss -s` — сводка соединений, много TIME_WAIT/CLOSE_WAIT — признак проблем в коде.

**eBPF**: наблюдение внутри ядра без изменения приложений (bpftrace, BCC-утилиты `execsnoop`, `opensnoop`, `tcplife`) — современный уровень диагностики.

**systemd**: unit-файлы с `Restart=on-failure`, лимиты (`MemoryMax`), sandboxing (`ProtectSystem`, `NoNewPrivileges`), таймеры вместо cron.

# @devops-bash

## Глубже: надёжные скрипты
**Ловушки bash**: пробелы в именах (всегда кавычки), `for f in $(ls)` (используйте глоббинг `for f in *.log`), разбор вывода `ls`, `[ ]` vs `[[ ]]`, неинициализированные переменные (`set -u`), ошибки в конвейере (`set -o pipefail`), `cd` без проверки.

**Очистка**: `trap 'rm -rf "$tmp"' EXIT` — удалить временные файлы при любом выходе. Временные файлы — `mktemp`.

**ShellCheck** — линтер, ловящий большинство ошибок; включайте в CI.

**Идемпотентность**: скрипт можно запускать повторно без вреда (`mkdir -p`, проверки перед созданием).

**PowerShell глубже**: `$ErrorActionPreference = 'Stop'`, `try/catch`, объекты `[pscustomobject]`, `ConvertTo-Json`, удалённое выполнение (`Invoke-Command`), модули; кросс-платформенный pwsh.

**Когда пора уйти из bash**: сложная логика, структуры данных, JSON, обработка ошибок — Python, C#-скрипты (dotnet-script, file-based apps в .NET 10), или Ansible для конфигурации серверов.

# @devops-git

## Глубже: git изнутри
**Объектная модель**: blob (содержимое файла), tree (каталог), commit (снимок дерева + родители + автор), tag. Всё адресуется хэшем содержимого (SHA-1 → SHA-256). Ветка — файл с хэшем коммита. Поэтому git быстр и надёжен: одинаковое содержимое хранится один раз.

**Слияние**: трёхстороннее (общий предок + две версии); стратегии ort (по умолчанию), `-X ours/theirs`; `rerere` запоминает разрешения конфликтов.

**Большие репозитории**: shallow clone (`--depth`), partial clone (`--filter=blob:none`), sparse checkout, Git LFS для бинарников, `git maintenance`.

**Практики команды**: защищённые ветки, обязательные ревью и CI, squash или rebase merge для чистой истории, подписанные коммиты, conventional commits → автоматический changelog и semver (semantic-release, GitVersion).

**Monorepo vs polyrepo**: монорепозиторий — атомарные изменения во многих проектах, общий CI, но нужны инструменты (affected builds); полирепо — независимость, но синхронизация версий.

Q: Как git хранит данные и почему это эффективно?
A: Как контентно-адресуемую базу объектов: blob для содержимого файлов, tree для каталогов, commit для снимков с родителями. Объекты адресуются хэшем содержимого, поэтому одинаковые файлы хранятся один раз, целостность проверяется хэшами, а ветки — лишь указатели.

# @devops-docker

## Глубже: образы как код безопасности и скорости
**Размер и поверхность атаки**: chiseled/distroless-образы без shell и пакетного менеджера; `dotnet publish` с trimming/AOT для самодостаточных бинарников; `--no-install-recommends` и очистка кэшей в одном RUN.

**BuildKit**: параллельные стадии, кэш-маунты (`RUN --mount=type=cache,target=/root/.nuget/packages dotnet restore`), секреты при сборке (`--mount=type=secret`) — не попадают в слои; multi-platform (`docker buildx --platform linux/amd64,linux/arm64`).

**Воспроизводимость**: фиксировать базовый образ по digest (`@sha256:…`), обновлять автоматически (Renovate) и пересобирать.

**Безопасность рантайма**: `USER` не root, read-only root filesystem, `--cap-drop ALL`, без `--privileged`, ресурсы лимитированы. Сканирование (Trivy/Grype) в CI, подпись (cosign).

**Как устроено**: overlayfs склеивает слои; `docker history` показывает слои и их размер; секрет, добавленный и удалённый в разных слоях, остаётся в образе навсегда.

# @devops-cicd

## Глубже: конвейер как продукт
**DORA-метрики** (исследование Accelerate): частота деплоев, время от коммита до прода, доля неудачных изменений, время восстановления. Лучшие команды деплоят много раз в день с малой долей откатов — скорость и стабильность не противоречат друг другу.

**Скорость конвейера**: кэш зависимостей, сборка затронутых проектов, параллельные тесты, быстрые юнит-тесты в PR, тяжёлые — после мержа; цель — фидбек за 5–10 минут.

**Безопасность CI**: секреты с минимальными правами и только для доверенных веток; OIDC-федерация вместо долгоживущих ключей облака (GitHub Actions → Azure/AWS); фиксация сторонних actions по SHA; осторожно с `pull_request_target`.

**Прогрессивная доставка**: canary с автоматическим анализом метрик (Argo Rollouts, Flagger) — автооткат при росте ошибок.

**Артефакты**: собрать один раз, версионировать (semver + sha), подписать, продвигать между окружениями без пересборки.

**Environments и approvals**: ручное подтверждение только там, где оно реально что-то проверяет.

# @devops-k8s

## Глубже: как Kubernetes принимает решения
**Планировщик**: фильтрует узлы (ресурсы, taints/tolerations, nodeSelector, affinity), затем оценивает и выбирает лучший. `podAntiAffinity` или **topologySpreadConstraints** разносят реплики по узлам и зонам — иначе все реплики окажутся на одном узле.

**QoS-классы**: Guaranteed (requests = limits), Burstable, BestEffort — при нехватке памяти вытесняются в обратном порядке.

**CPU limits**: троттлинг CFS может увеличивать латентность даже при средней загрузке; многие команды ставят requests и не ставят CPU limits (но ставят memory limits).

**PodDisruptionBudget**: сколько подов может быть недоступно при добровольных нарушениях (обновление узлов) — защищает от одновременного выселения всех реплик.

**Контроллеры и reconciliation**: Deployment → ReplicaSet → Pods; всё — циклы «наблюдаемое → желаемое». `kubectl describe` и события (`kubectl get events`) — первое место при проблемах: `ImagePullBackOff`, `CrashLoopBackOff`, `Pending` (нет ресурсов), `OOMKilled`.

**Отладка**: `kubectl logs --previous`, `kubectl exec`, эфемерные debug-контейнеры (`kubectl debug`).

# @devops-networking

## Глубже: сеть Kubernetes изнутри
**Путь пакета** к Service: kube-proxy (iptables/IPVS) или eBPF (Cilium) переписывает виртуальный IP сервиса на IP одного из подов (DNAT). Сам ClusterIP нигде не «живёт» — это правило в ядре узла.

**CNI**: Flannel (простая overlay), Calico (BGP, NetworkPolicy), **Cilium** (eBPF: быстрее, L7-политики, наблюдаемость через Hubble, замена kube-proxy).

**NetworkPolicy**: по умолчанию все поды видят всех. Практика: default deny на namespace + явные разрешения (egress тоже, включая DNS). Нужна поддержка CNI.

**DNS**: `ndots:5` в resolv.conf подов порождает лишние запросы для внешних имён — FQDN с точкой в конце или настройка ndots; NodeLocal DNSCache разгружает CoreDNS.

**Gateway API**: GatewayClass/Gateway (инфраструктура) + HTTPRoute (команда приложения) — разделение ответственности, трафик-сплит, заголовки, mTLS.

**Service mesh**: sidecar (Istio, Linkerd) или ambient/без sidecar (Istio ambient, Cilium) — mTLS, ретраи, телеметрия.

# @devops-cloud

## Глубже: архитектура в облаке
**Well-Architected Framework** (Azure, AWS, Google) — пять-шесть опор: надёжность, безопасность, стоимость, операционное совершенство, производительность (+ устойчивость). Используйте их чек-листы при ревью архитектуры.

**Надёжность**: зоны доступности для каждого слоя; RPO/RTO определяют стратегию резервирования (бэкапы, горячий резерв, active-active между регионами).

**Сети**: приватные эндпоинты для PaaS-сервисов (БД недоступна из интернета), выход через NAT с фиксированным IP, WAF перед публичными сервисами.

**Идентичность**: managed identity / IAM roles для сервисов, никаких ключей в конфигурации; условный доступ для людей; break-glass учётки.

**Стоимость**: тегирование ресурсов по команде/продукту, бюджеты и алерты, reserved/savings plans для постоянной нагрузки, spot для прерываемой, выключение dev-окружений, lifecycle-политики хранилищ, мониторинг egress-трафика (часто скрытая статья).

**Serverless**: хорошо для событийных и неравномерных нагрузок; ограничения — холодный старт (Native AOT помогает .NET), лимиты времени, сложность локальной отладки.

# @devops-observability

## Глубже: алерты, которые не будят зря
**Алерты по SLO** (burn rate): алертить, когда бюджет ошибок сжигается слишком быстро — многоокновые правила (быстрое сжигание за 1 ч и 5 мин → страница; медленное за 6 ч → тикет). Это резко снижает шум по сравнению с порогами «ошибок > 1%».

**Каждый алерт** должен быть: срочным, требующим действия человека, с runbook-ссылкой и понятным названием. Не требующее действия — в дашборды и отчёты.

**PromQL глубже**: `rate` для счётчиков (а не `irate` в алертах), `histogram_quantile` по bucket'ам, `by (le)`, recording rules для тяжёлых выражений, `absent()` — алерт на пропажу метрики.

**Логи**: структурные JSON, уровни, correlation id; хранение горячих логов недолго, архив — в объектное хранилище.

**Профили и continuous profiling** как четвёртый сигнал; **RUM** (мониторинг реальных пользователей в браузере) и **синтетика** (проверки извне).

**Стек**: Prometheus/Mimir (метрики), Loki (логи), Tempo (трейсы), Grafana, OpenTelemetry Collector как единая точка сбора.

# @devops-sre

## Глубже: SRE-практики в команде
**Выбор SLI**: доля «хороших» событий от всех — доступность (успешные ответы), латентность (доля быстрее порога), свежесть данных, корректность. Измерять как можно ближе к пользователю (балансировщик, RUM).

**SLO-документ**: SLI, цель, окно (28–30 дней), политика бюджета ошибок (что делаем при исчерпании), владельцы. Согласован с продуктом.

**Инциденты**: уровни серьёзности, роли (incident commander, communications, operations), каналы связи, статус-страница, таймлайн. После — **blameless postmortem** с action items и сроками; повторяющиеся причины — приоритет в бэклоге.

**Capacity planning**: прогноз по трендам и событиям (распродажи), нагрузочные тесты, запас 30–50% на пики и отказ зоны.

**Toil** — ручная, повторяемая, автоматизируемая, без долгосрочной ценности работа; SRE ограничивают её долей времени и автоматизируют.

**Production readiness review**: чек-лист перед запуском сервиса — мониторинг, алерты, runbooks, SLO, бэкапы, нагрузочные тесты, план отката.

## Глубже: безопасность конвейера и рантайма
**SLSA** (Supply-chain Levels for Software Artifacts) — уровни зрелости цепочки поставок: сборка в изолированном CI, provenance (подписанные сведения, как и из чего собран артефакт), проверка при деплое.

**Сканирование**: SAST (CodeQL, Semgrep, Sonar), SCA (Dependabot, OWASP Dependency-Check), IaC (checkov, tfsec), образы (Trivy), DAST (ZAP baseline в CI).

**Управление уязвимостями**: не все CVE одинаковы — приоритизируйте по достижимости и эксплуатируемости (EPSS, KEV-каталог CISA), SLA на исправление по критичности.

# @devops-nginx

## Глубже: прокси под нагрузкой
**Тюнинг Nginx**: `worker_processes auto`, `worker_connections`, keep-alive к upstream (`keepalive 64` + `proxy_http_version 1.1` + пустой `Connection`) — иначе на каждый запрос новое TCP-соединение к Kestrel.

**Буферизация**: `proxy_buffering` защищает бэкенд от медленных клиентов; для SSE/стриминга — выключить (`proxy_buffering off` или `X-Accel-Buffering: no`).

**Таймауты и лимиты**: `client_max_body_size`, `proxy_read_timeout` (для долгих запросов), `limit_req` (rate limiting) и `limit_conn`.

**TLS**: TLS 1.2/1.3, OCSP stapling, session resumption, HTTP/2 и HTTP/3 (QUIC), сертификаты через cert-manager/certbot.

**Health checks**: пассивные (max_fails) в open-source Nginx, активные — в Nginx Plus, Envoy, HAProxy.

**YARP**: конфигурация маршрутов и кластеров из appsettings или кода, трансформации запросов, активные/пассивные health checks, session affinity, интеграция с аутентификацией ASP.NET Core — удобен для BFF и API gateway на .NET.

**Envoy** — прокси с динамической конфигурацией (xDS), основа Istio и многих gateway.

Q: Какие настройки reverse proxy критичны для производительности и корректности?
