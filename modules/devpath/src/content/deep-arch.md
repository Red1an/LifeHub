# @arch-solid

## Глубже: принципы на уровне компонентов
SOLID описывает классы; для модулей и сборок у Роберта Мартина есть **принципы компонентов**:
- **REP/CCP/CRP** — что класть в один компонент: то, что выпускается вместе, меняется вместе и используется вместе;
- **ADP** (ацикличные зависимости) — граф зависимостей между модулями без циклов;
- **SDP** (стабильные зависимости) — зависеть в сторону более стабильного;
- **SAP** (стабильные абстракции) — стабильный компонент должен быть абстрактным.

**Связанность (coupling) бывает разной** — по «Balancing Coupling» (Влад Хононов): по интеграции (знание о реализации, модели, контракте), по расстоянию (в одном методе или в разных сервисах) и по изменчивости. Сильная связанность допустима между близкими и стабильными частями; опасна — между далёкими и часто меняющимися.

Принцип открытости/закрытости на практике чаще реализуется **точками расширения**, появившимися по реальной потребности (вторая реализация), а не заранее. «Правило трёх»: абстрагируй на третьем повторении.

# @arch-patterns

## Глубже: паттерны уровня предприятия
Кроме GoF, в .NET-проектах постоянно встречаются паттерны из «Patterns of Enterprise Application Architecture» (Фаулер):
- **Repository** и **Unit of Work** — DbSet и DbContext уже ими являются; свой репозиторий поверх EF оправдан для агрегатов DDD, а не как «обёртка ради обёртки»;
- **Specification** — бизнес-правило отбора как объект (`ActiveCustomersSpec`), комбинируемое и переиспользуемое в запросах;
- **Result/Notification** — сбор ошибок валидации вместо исключений;
- **Null Object** — объект-заглушка вместо проверок на null;
- **Pipeline/Chain** — конвейеры обработки (middleware, MediatR behaviors);
- **Options, Factory, Decorator** — основа конфигурации и расширения в .NET.

Антипаттерны: **Anemic Domain Model** (сущности без поведения, логика в сервисах) — не всегда плохо для простого CRUD; **Service Locator**; **God Object**; **Singleton с изменяемым состоянием**.

Функциональные приёмы в C#: неизменяемые записи, чистые функции, pattern matching вместо Visitor в простых случаях.

# @arch-refactoring

## Глубже: рефакторинг больших систем
**Параллельное изменение (expand/contract) в коде**: добавить новый метод/интерфейс рядом, перевести вызывающих по одному, удалить старое — каждый шаг зелёный и деплоится отдельно.

**Branch by abstraction**: ввести абстракцию над заменяемым компонентом, две реализации за флагом, постепенно переключать, удалить старую — без долгоживущих веток.

**Mikado method**: попытаться сделать изменение → записать, что сломалось (предусловия) → откатить → сначала сделать предусловия. Получается граф шагов для большого рефакторинга.

**Автоматизация**: Roslyn-анализаторы и code fixes для массовых механических правок, OpenRewrite-подобные инструменты, ИИ-агенты для серий однотипных изменений под контролем тестов.

**Метрики «где рефакторить»**: пересечение сложности и частоты изменений (hotspots: `git log` по файлам × цикломатическая сложность) — рефакторить стоит часто меняемый сложный код, а не старый стабильный.

# @arch-layers

## Глубже: где кончается чистота
**Типичные ошибки Clean Architecture в .NET**:
- «Слои ради слоёв»: DTO → Command → Entity → DataModel с маппингом на каждом шаге, а логики нет;
- репозитории, повторяющие DbSet;
- Application-слой, знающий об HTTP (`IFormFile`, статус-коды);
- домен, зависящий от EF-атрибутов (конфигурация должна быть снаружи — `IEntityTypeConfiguration`).

**Прагматичный вариант**: домен чистый; Application использует EF Core напрямую для запросов (DbContext — уже абстракция), а интерфейсы — для действительно внешнего (почта, платёжка, время).

**Модули внутри**: большие системы делят не только горизонтально (слои), но и вертикально — по bounded context; внутри модуля может быть своя структура.

**Проверка правил**: NetArchTest/ArchUnitNET в тестах; `InternalsVisibleTo` и `internal` по умолчанию; отдельные сборки как жёсткая граница.

**Функциональное ядро, императивная оболочка**: логика — чистые функции без I/O, оболочка — загрузка данных, вызов ядра, сохранение. Тестируемость без моков.

Q: Что такое прагматичная чистая архитектура в .NET?
A: Домен без зависимостей от инфраструктуры и фреймворков, конфигурация EF снаружи, Application-слой использует DbContext напрямую для запросов (без лишних репозиториев), интерфейсы — только для действительно внешних систем, минимум маппинга, вертикальное деление по модулям, правила проверяются архитектурными тестами.

# @arch-ddd

## Глубже: стратегический дизайн
**Типы поддоменов**: **core** (конкурентное преимущество — вкладываемся, DDD, лучшие люди), **supporting** (нужно бизнесу, но не уникально — проще), **generic** (решено рынком — купить/взять готовое: платежи, авторизация). Ошибка — строить сложную модель в generic-поддомене.

**Отношения контекстов** (context map): partnership, shared kernel (общий код — опасно), customer–supplier, conformist (принимаем чужую модель как есть), anti-corruption layer, open host service + published language (стабильный публичный контракт).

**Размер агрегата**: правило Вернона — маленькие агрегаты, ссылки по id, eventual consistency между агрегатами; большой агрегат = конфликты оптимистичной блокировки и медленная загрузка. Спросите бизнес: «должно ли это правило соблюдаться мгновенно?» — часто нет.

**Доменные vs интеграционные события**: доменные — внутри контекста, богатые, могут меняться; интеграционные — публичный контракт между контекстами, версионируются.

**Event Storming** уровни: big picture → process modeling → software design. Результат — события, команды, агрегаты, политики, границы.

Q: Какие типы поддоменов выделяют в DDD и как к ним подходить?

# @arch-testing

## Глубже: стратегия тестирования системы
**Что тестировать где**:
- доменные правила — юнит-тесты без инфраструктуры;
- use cases с БД — интеграционные тесты через API или обработчики с Testcontainers;
- взаимодействие сервисов — контрактные тесты (Pact);
- критичные пользовательские сценарии — небольшой набор E2E (Playwright);
- нефункциональное — нагрузочные тесты и chaos-эксперименты.

**Школы**: лондонская (моки всех зависимостей, «юнит» = класс) против классической/детройтской (юнит = поведение, реальные объекты внутри, моки только на границах). Классическая даёт тесты, устойчивые к рефакторингу.

**Тесты как документация**: имена в стиле `Order_cannot_be_paid_twice`, Given/When/Then, builders для тестовых данных (`new OrderBuilder().WithLines(3).Paid().Build()`).

**Покрытие** — индикатор непроверенного кода, а не цель. 100% покрытия со слабыми ассертами хуже 70% с сильными; мутационное тестирование показывает силу тестов.

**Скорость**: полный прогон в CI за минуты; медленные тесты — в отдельные стадии.

## Глубже: event sourcing в деталях
**Хранилище событий**: поток событий на агрегат (`order-42`), оптимистичная конкуренция через ожидаемую версию потока при добавлении.

**Проекции**: подписчики строят read-модели; **inline** (в той же транзакции — согласованно, но медленнее) и **async** (с задержкой). Проекции можно пересобрать с нуля — это суперсила ES, но нужна идемпотентность и время.

**Версионирование событий**: только добавлять поля; **upcasting** — преобразование старых событий в новую форму при чтении; новые типы событий вместо изменения старых; «копировать и заменить» поток при крупных изменениях.

**Снапшоты** — для длинных потоков (каждые N событий), это кэш, не источник правды.

**GDPR и ES**: событие нельзя изменить → персональные данные шифруют отдельным ключом на пользователя и «удаляют» уничтожением ключа (crypto-shredding).

**В .NET**: Marten (PostgreSQL как хранилище событий и документов), EventStoreDB/KurrentDB, Wolverine для обработки.

# @arch-monolith

## Глубже: как строить модульный монолит
**Границы модулей** — по bounded context. Каждый модуль:
- своя схема БД (`orders.*`, `catalog.*`), никаких внешних ключей и JOIN между схемами модулей;
- публичный API: интерфейсы или сообщения в отдельной сборке `Orders.Contracts`;
- всё остальное — `internal`;
- интеграция — синхронно через контракт или асинхронно через **внутреннюю шину** с outbox (модуль узнаёт о событиях другого, не зная его устройства).

**Проверка границ**: архитектурные тесты «модуль A не ссылается на внутренности B».

**Выделение в сервис**, когда: нужно независимое масштабирование, отдельная команда, другой цикл релизов, другие требования к надёжности. Благодаря контрактам и отдельной схеме выделение — механическое.

**Metrics**: монолит проще в наблюдаемости, отладке, транзакциях. Shopify, GitHub, Basecamp долго живут на модульных монолитах.

# @arch-microservices

## Глубже: паттерны данных и надёжности
**Запросы по данным нескольких сервисов**: API composition (шлюз собирает ответы), CQRS-проекции (сервис держит read-модель из событий других), и никогда — общая база.

**Outbox в деталях**: таблица outbox в БД сервиса; публикатор — polling или CDC (Debezium); упорядочивание по агрегату; очистка отправленного. Inbox на стороне потребителя для идемпотентности.

**Сага: оркестрация** — явный координатор с состоянием (MassTransit state machine, Temporal, Durable Task) — видно, где застряла операция; **хореография** — проще для 2–3 шагов, но процесс «размазан».

**Service mesh** (Istio, Linkerd): mTLS между сервисами, ретраи, таймауты, circuit breaking, телеметрия — без изменения кода. Цена — сложность и ресурсы.

**Страшные сны микросервисов**: синхронные цепочки из 5 вызовов (латентность и отказы перемножаются), «распределённые транзакции» через HTTP, общая библиотека моделей для всех сервисов, отсутствие трассировки.

**Temporal / Durable Functions** — durable execution: код процесса как обычная функция, а рантайм сохраняет состояние и переживает сбои.

# @arch-api

## Глубже: GraphQL, AsyncAPI и API-first
**API-first**: контракт (OpenAPI/Protobuf/AsyncAPI) пишется и ревьюится до реализации; из него генерируются серверные заглушки, клиенты, моки и документация. Команды фронта и бэка работают параллельно.

**GraphQL в .NET** (Hot Chocolate): схема, резолверы, DataLoader для борьбы с N+1, ограничения глубины и стоимости запросов (защита от тяжёлых запросов), persisted queries. Хорош для BFF с разнообразными клиентами; кэширование HTTP сложнее.

**AsyncAPI** — «OpenAPI для событий»: описание каналов, сообщений и схем для брокеров.

**Совместимость**: правила Постела; semver для API; «tolerant reader» на клиенте; для событий — Schema Registry с проверкой совместимости (backward/forward/full).

**Pagination и фильтрация** по стандартам (JSON:API, OData) или своим правилам — главное, единообразно во всём API.

**Качество API**: линтеры спецификаций (Spectral) в CI проверяют именование, коды ответов, наличие описаний.

## Глубже: как принимать архитектурные решения
**ATAM-подход в миниатюре**: выпишите атрибуты качества сценариями («при отказе одного ДЦ заказы продолжают приниматься, потеря не более 1 минуты данных»), для каждого варианта архитектуры оцените, какие сценарии он поддерживает и с какими рисками.

**Обратимость решений**: двусторонние двери (легко откатить — решаем быстро) и односторонние (выбор БД для core, публичный API — решаем тщательно). Откладывайте необратимые решения до момента, когда информации больше (last responsible moment).

**Fitness functions**: автоматически проверяемые свойства — время ответа в нагрузочном тесте, отсутствие циклов модулей, размер образа, число уязвимостей. Архитектура «эволюционирует», пока функции зелёные.

**C4 на практике**: Context и Container — для всех; Component — для сложных контейнеров; всё как код (Structurizr DSL) рядом с репозиторием; одна модель — много представлений.

**Роль архитектора**: не рисовать схемы в одиночку, а создавать условия для хороших решений команд — принципы, ADR, ревью, технический радар.

# @arch-integration

## Глубже: надёжная интеграция
**Контракты сообщений**: конверт (id, тип, версия, время, correlation id, causation id) + тело. Correlation id связывает всю цепочку, causation — «какое сообщение породило это».

**Порядок и дубли**: брокеры гарантируют порядок в пределах партиции/очереди; потребитель идемпотентен; для строгого порядка — версия сущности в сообщении и отбрасывание устаревших.

**Эволюция схем**: Avro/Protobuf со Schema Registry; для JSON — JSON Schema и правило «только добавлять необязательные поля»; при несовместимом изменении — новый тип сообщения и период параллельной публикации.

**Вебхуки как отправитель**: подпись HMAC, ретраи с экспоненциальной задержкой, журнал доставок, возможность для клиента переотправить, отключение «мёртвых» подписчиков.

**Интеграция с легаси**: anti-corruption layer, CDC из старой БД вместо изменения старого кода, шлюз-фасад со strangler fig.

**iPaaS и ESB**: централизованные шины с логикой — источник узких мест; современный подход — «умные конечные точки, тупые трубы».

Q: Как обеспечить правильный порядок обработки событий об одной сущности?
A: Публиковать события сущности в одну партицию/очередь (ключ = id сущности), хранить в событиях версию сущности и отбрасывать устаревшие версии на потребителе, делать обработку идемпотентной; не полагаться на глобальный порядок между сущностями.
