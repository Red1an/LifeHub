# @data-sql

## Глубже: как оптимизатор исполняет запрос
SQL декларативен: оптимизатор перебирает **планы** (порядок соединений, методы доступа) и выбирает дешёвый по оценке стоимости на основе **статистики** (гистограммы значений, число различных значений, корреляции). Ошибки оценки кардинальности — корень большинства плохих планов.

Приёмы, которые стоит знать:
- **Sargable-условия**: `WHERE created_at >= '2026-01-01'` использует индекс, `WHERE YEAR(created_at) = 2026` — нет.
- **EXISTS vs IN vs JOIN**: для полусоединения («есть ли заказы») `EXISTS` останавливается на первом совпадении.
- **LATERAL / CROSS APPLY** — подзапрос для каждой строки: «топ-3 заказа каждого клиента» с индексом.
- **Оконные функции с фреймами**: `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` — скользящее среднее за 7 дней.
- **GROUPING SETS / ROLLUP** — итоги по нескольким разрезам одним проходом.
- **Параметризация и планы**: переиспользуемые планы экономят компиляцию, но параметр-сниффинг в SQL Server может закрепить план, плохой для других значений.

Q: Что такое саржабельное (sargable) условие?
A: Условие, которое можно вычислить поиском по индексу: колонка сравнивается с выражением без применения к ней функций и преобразований (col >= X, col = X, col LIKE 'abc%'). Функции над колонкой, неявные приведения типов и ведущий % делают условие несаржабельным.

# @data-indexes

## Глубже: как B-tree работает на диске
B-tree хранится **страницами** (8 КБ в PostgreSQL и SQL Server): корень → внутренние страницы → листья, в листьях — ключи и ссылки на строки (TID в Postgres) или сами строки (кластерный индекс в SQL Server/InnoDB). Высота дерева для миллиарда строк — 4–5 уровней.

**Кластерный индекс** (SQL Server, MySQL InnoDB) — таблица и есть индекс, упорядоченный по ключу; вторичные индексы хранят ключ кластерного. В PostgreSQL таблица — куча (heap), все индексы вторичные; `CLUSTER` упорядочивает однократно.

**Index-only scan** в Postgres требует актуальной **visibility map** (иначе всё равно читается таблица) — ещё одна причина для VACUUM.

**Частичные и функциональные индексы**, **INCLUDE** для покрытия, **BRIN** для огромных естественно упорядоченных таблиц.

**Когда индекс вредит**: много индексов замедляют запись и VACUUM; неиспользуемые индексы находите через `pg_stat_user_indexes` (idx_scan = 0). Составной индекс заменяет индекс по его префиксу — дубликаты удаляйте.

**Создание на проде**: `CREATE INDEX CONCURRENTLY` не блокирует запись.

Q: Почему много индексов — это плохо?
A: Каждый индекс обновляется при вставке, изменении индексированных колонок и удалении, занимает место, увеличивает нагрузку на VACUUM и кэш; оптимизатору сложнее выбирать. Оставляют индексы, реально нужные запросам, удаляя неиспользуемые и дублирующие префиксы.

# @data-transactions

## Глубже: изоляция в PostgreSQL и SQL Server
**PostgreSQL**: Read Committed — каждый оператор видит снимок на момент своего начала; Repeatable Read — снимок на начало транзакции (**snapshot isolation**), конфликт записи → ошибка сериализации; Serializable — **SSI** (Serializable Snapshot Isolation) отслеживает опасные зависимости чтения-записи и откатывает одну из транзакций. Приложение **обязано** повторять транзакции при ошибке `40001`.

**SQL Server**: по умолчанию Read Committed на блокировках (читатели ждут писателей); `READ_COMMITTED_SNAPSHOT ON` включает версионирование в tempdb — поведение ближе к Postgres. `SNAPSHOT` — отдельный уровень.

**Блокировки строк** в Postgres: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `SKIP LOCKED`, `NOWAIT`. **Advisory locks** — пользовательские блокировки по числу (например, «только один экземпляр выполняет задачу»).

**Длинные транзакции** — зло: держат блокировки, мешают VACUUM, раздувают WAL. Никакого сетевого I/O и ожидания пользователя внутри транзакции.

**Дедлоки**: Postgres обнаруживает их через `deadlock_timeout` и убивает одну транзакцию — логируйте и повторяйте.

Q: Что такое Serializable Snapshot Isolation в PostgreSQL?
A: Реализация уровня Serializable поверх снимков: транзакции работают без дополнительных блокировок чтения, а система отслеживает зависимости чтения-записи между параллельными транзакциями и при обнаружении опасной структуры (возможной аномалии) откатывает одну из них с ошибкой сериализации, которую приложение повторяет.

# @data-postgres

## Глубже: эксплуатация PostgreSQL
**Autovacuum** настраивается по таблицам: для горячих — `autovacuum_vacuum_scale_factor = 0.01` вместо 0.2. **HOT-обновления** (heap-only tuple) не трогают индексы, если меняются неиндексированные колонки и есть место на странице (`fillfactor`).

**WAL и контрольные точки**: все изменения сначала в журнал; `checkpoint` сбрасывает страницы на диск. Частые чекпоинты — пики записи; `max_wal_size` сглаживает.

**Память**: `shared_buffers` (~25% RAM), `work_mem` (на каждую сортировку/хэш в каждом запросе — осторожно с большими значениями), `effective_cache_size` (подсказка планировщику).

**Партиционирование**: декларативное по диапазону/списку/хэшу; удаление старых данных `DROP PARTITION` мгновенно, в отличие от `DELETE`.

**Репликация**: физическая (streaming) — копия всего кластера; **логическая** — выборочные таблицы, между версиями, основа CDC.

**Наблюдение**: `pg_stat_statements`, `pg_stat_activity` (кто висит, `idle in transaction`), `auto_explain` для медленных планов, `pg_locks`.

# @data-modeling

## Глубже: модели для реальных задач
**Время и история**: 
- «как было на дату» — **SCD Type 2**: строка с `valid_from`/`valid_to`; или temporal tables (SQL Server `SYSTEM_VERSIONING`);
- снимки в документах (цена в строке заказа на момент покупки) — это не денормализация, а бизнес-правило.

**Иерархии**: adjacency list (`parent_id`) + рекурсивный CTE; materialized path (`/1/5/12/`) — быстрый поиск поддерева по префиксу; `ltree` в Postgres; closure table для частых запросов по предкам.

**Полиморфные связи** (`commentable_type`, `commentable_id`) ломают внешние ключи — лучше отдельные таблицы связей или общий супертип.

**EAV** (entity-attribute-value) для «произвольных атрибутов» — почти всегда хуже JSONB: нет типов, ужасные запросы.

**Ограничения в БД** — последняя линия защиты целостности: `NOT NULL`, `CHECK`, `UNIQUE`, внешние ключи, exclusion constraints (непересекающиеся интервалы бронирования в Postgres).

**Идентификаторы**: bigint identity — компактно и быстро; UUID v7 — генерация на клиенте, без раскрытия количества; наружу можно отдавать отдельный публичный id.

# @data-efcore

## Глубже: change tracker и производительность
**Как работает трекинг**: при загрузке EF создаёт снимок значений; `SaveChanges` вызывает `DetectChanges`, сравнивая все отслеживаемые сущности со снимками — O(число сущностей). Тысячи отслеживаемых объектов в долгоживущем контексте → медленные `SaveChanges`. Контекст должен быть коротким.

**Identity resolution**: в одном контексте одна строка = один объект. `AsNoTrackingWithIdentityResolution` — без трекинга, но с дедупликацией объектов.

**Картезианский взрыв**: `Include(o => o.Lines).Include(o => o.Payments)` — JOIN двух коллекций даёт произведение строк. `AsSplitQuery()` — отдельные запросы на коллекции (цена — несколько круговых поездок и возможная несогласованность без транзакции).

**Пакетирование**: SaveChanges отправляет изменения пачками (по 42 команды для SQL Server по умолчанию). **Массовая вставка** миллионов строк — `COPY` в Postgres (Npgsql BinaryImporter) или EFCore.BulkExtensions.

**Конкуренция**: `[ConcurrencyCheck]`/`IsRowVersion` → `DbUpdateConcurrencyException`; в Postgres — системная колонка `xmin` как токен версии.

**Логи и диагностика**: `LogTo(Console.WriteLine, LogLevel.Information)`, `EnableSensitiveDataLogging` только локально, `TagWith("Dashboard query")` — метка в SQL для поиска в pg_stat_statements.

# @data-efcore-adv

## Глубже: EF Core как часть архитектуры
**Доменная модель и EF**: приватные сеттеры, поля-коллекции (`_lines` с `UsePropertyAccessMode(PropertyAccessMode.Field)`), конструкторы с параметрами — EF умеет работать с богатыми моделями без публичных сеттеров. Value objects — owned types или complex types (EF Core 8).

**Перехватчики** (`SaveChangesInterceptor`): аудит (кто/когда изменил), soft delete, сбор доменных событий из агрегатов и запись в outbox в той же транзакции.

**Compiled models** (`dotnet ef dbcontext optimize`) — ускоряют старт больших моделей и нужны для AOT.

**Миграции в команде**: одна миграция на изменение, ревью SQL, `migrations bundle` для CI/CD; конфликты миграций в параллельных ветках решайте пересозданием последней.

**Raw SQL**: `SqlQuery<T>` для скаляров и DTO (EF Core 8), `FromSql` с интерполяцией (параметризуется), представления и функции БД через маппинг.

# @data-nosql

## Глубже: как устроены NoSQL-хранилища
**LSM-дерево** (Cassandra, ScyllaDB, RocksDB): запись в память (memtable) + журнал → сброс в неизменяемые отсортированные файлы (SSTable) → фоновое слияние (compaction). Запись очень быстрая, чтение может проверять несколько файлов (помогают bloom-фильтры). B-tree (классические СУБД) — быстрее чтение, медленнее запись. Это главный компромисс хранилищ.

**Cassandra**: ключ партиции определяет узел, clustering-ключи — порядок внутри партиции; настраиваемая согласованность на запрос (`ONE`, `QUORUM`, `ALL`); tombstones от удалений замедляют чтение.

**MongoDB**: документы до 16 МБ, агрегационный конвейер, многодокументные транзакции (с репликасетом), шардинг по ключу.

**DynamoDB**: single-table design — несколько типов сущностей в одной таблице с продуманными ключами под шаблоны доступа.

**Графовые БД**: Cypher-запросы на обход связей — «друзья друзей» за константное время на шаг.

Выбор — по **шаблонам доступа и масштабу**, а не по моде.

# @data-redis

## Глубже: Redis в продакшене
**Однопоточность**: одна медленная команда блокирует всех. Опасны `KEYS *`, `SMEMBERS` огромного множества, `DEL` большого ключа (используйте `SCAN`, `UNLINK`). `SLOWLOG` показывает медленные команды.

**Память**: `maxmemory` + политика вытеснения (`allkeys-lru` для кэша, `noeviction` для данных); большие ключи (big keys) и горячие ключи — главные проблемы. `MEMORY USAGE key`, `--bigkeys`.

**Пайплайнинг** — отправить много команд без ожидания ответа на каждую (StackExchange.Redis делает мультиплексирование автоматически); **Lua/Functions** — атомарная логика на сервере.

**Шаблоны**: rate limiter на sorted set или `INCR` с `EXPIRE`; распределённая очередь на Streams с consumer groups и `XPENDING`/`XCLAIM` для зависших сообщений; leaderboard на ZSET; сессии; дедупликация (`SET NX EX`).

**Надёжность**: репликация асинхронная — при failover возможна потеря последних записей; Redis — не основное хранилище для критичных данных без понимания этого.

**StackExchange.Redis**: один `ConnectionMultiplexer` на приложение (singleton).

# @data-scaling

## Глубже: шардирование на практике
**Выбор ключа**: для SaaS — `tenant_id` (все данные клиента на одном шарде, запросы локальны); для соцсетей — `user_id`. Крупные арендаторы («киты») требуют выделенных шардов.

**Маршрутизация**: таблица-справочник «ключ → шард» (гибко, можно переносить отдельных клиентов) против вычисления хэша (просто, но решардинг тяжелее).

**Глобальные уникальные id**: Snowflake-подобные (время + id шарда + счётчик), UUID v7.

**Кросс-шардовые операции**: отчёты — через отдельное аналитическое хранилище (CDC → ClickHouse), а не fan-out запросы; транзакции между шардами — саги.

**Решардинг**: двойная запись + фоновая миграция + сверка + переключение чтения; или логические шарды, переносимые целиком.

**Готовые решения**: Citus (расширение Postgres), Vitess (MySQL), YugabyteDB/CockroachDB — распределённый SQL с автоматическим шардированием и консенсусом.

**Прежде чем шардировать**: вертикальный рост, реплики для чтения, партиционирование, кэш, вынос тяжёлых данных (файлы, логи) — шардирование сложно и необратимо.

# @data-search

## Глубже: поиск в продакшене
**Релевантность**: BM25 + поля с весами (заголовок важнее текста), фразовые совпадения, свежесть, популярность — через `function_score`. Настраивается на наборе запросов с ожидаемыми результатами (метрики NDCG, MRR).

**Анализаторы для русского**: морфология (стемминг snowball или лемматизация через плагины), синонимы, исправление опечаток (fuzzy, n-граммы), транслитерация.

**Автодополнение**: edge n-gram анализатор или `completion`-поле.

**Гибридный поиск**: BM25 + векторный kNN, объединение через Reciprocal Rank Fusion (встроено в Elasticsearch/OpenSearch).

**Индексация**: bulk API, алиасы индексов для переиндексации без простоя (строим новый индекс, переключаем alias), refresh interval (чем реже — тем быстрее индексация, но дольше до видимости).

**PostgreSQL как поиск**: `tsvector` + GIN + `ts_rank` — достаточно для многих продуктов без отдельного кластера; `pg_trgm` — нечёткий поиск.

**ClickHouse**: MergeTree, первичный ключ = порядок сортировки, материализованные представления для агрегатов, пакетная вставка.
