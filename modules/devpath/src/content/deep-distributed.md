# @distributed-basics

## Глубже: как рассуждать об отказах
**Детекторы отказов**: узел считается упавшим по таймауту heartbeat. Слишком короткий — ложные срабатывания при GC-паузах и сетевых задержках (узел «воскресает», возникают два лидера); слишком длинный — долгий простой. Адаптивные детекторы (phi accrual в Akka/Cassandra) оценивают вероятность отказа по истории задержек.

**Серые отказы** (gray failure): узел отвечает на health check, но обрабатывает реальные запросы с ошибками или медленно. Health check должен проверять реальную работу, а метрики — видеть деградацию с точки зрения клиентов.

**Метастабильные отказы**: система, пережившая всплеск, не возвращается в норму сама — ретраи и очереди поддерживают перегрузку. Лечение — ограничение ретраев, load shedding, backpressure, «сброс» очередей.

**Упражнение «что если»** для каждой зависимости: упала, тормозит в 10 раз, отвечает мусором, отвечает дважды, сеть разделилась. Для каждого случая должно быть известное поведение.

# @distributed-time

## Глубже: TrueTime, HLC и снимки
**Google Spanner TrueTime** возвращает не время, а интервал `[earliest, latest]`, гарантированно содержащий настоящее время (атомные часы и GPS, погрешность ~ единицы мс). Транзакция ждёт окончания неопределённости перед коммитом (**commit wait**) — и глобально упорядоченные метки дают внешнюю согласованность.

**HLC** (hybrid logical clock) = (физическое время, логический счётчик): близко к реальному времени, сохраняет причинность без спецоборудования. CockroachDB использует HLC и ограничение на расхождение часов (max offset) — узел с сильно ушедшими часами выключается.

**Снимки в распределённой БД**: метка времени задаёт согласованный срез данных по всем узлам — основа snapshot isolation в распределённых СУБД.

**Практика в сервисах**: время события — от источника (в UTC), порядок — по версии/логической метке, а не по часам сервера; для измерения длительностей — монотонные часы; дрейф часов мониторят (chrony, NTP).

Q: Как Spanner обеспечивает внешнюю согласованность с помощью TrueTime?
A: Каждой транзакции назначается метка времени, и перед подтверждением коммита она ждёт, пока интервал неопределённости TrueTime не пройдёт метку (commit wait). Тогда любая транзакция, начавшаяся позже по реальному времени, получит большую метку — порядок меток соответствует реальному порядку.

# @distributed-cap

## Глубже: согласованность на практике
**Jepsen** — проверки реальных БД на соответствие заявленной согласованности; многие системы нарушали обещания при разделениях сети. Читайте отчёты перед выбором хранилища.

**Настраиваемая согласованность**: в Cassandra/Cosmos DB уровень выбирается на запрос. Cosmos DB предлагает пять уровней: strong, bounded staleness, session, consistent prefix, eventual — **session** (read-your-writes в рамках сессии) — хороший выбор по умолчанию.

**Согласованность с точки зрения пользователя** важнее формальной: пользователь должен видеть свои изменения (read-your-writes) и не видеть «откат» данных (monotonic reads); остальные могут подождать.

**Техники**: sticky-сессии к реплике, чтение с лидера после записи, передача клиенту «токена позиции» (LSN/версии) и ожидание, пока реплика её догонит.

**Линеаризуемость дорога**: требует координации (кворум или лидер) на каждую операцию. Нужна для блокировок, выбора лидера, уникальности (два пользователя с одним логином), счётов.

Q: Какие сессионные гарантии согласованности важны для пользователя?
A: Read-your-writes (видеть свои изменения), monotonic reads (не видеть данные старее уже увиденных), monotonic writes (записи применяются в порядке отправки), writes-follow-reads (запись учитывает прочитанное). Они дешевле линеаризуемости и закрывают большую часть ожиданий пользователя.

# @distributed-replication

## Глубже: как это устроено в реальных системах
**PostgreSQL streaming replication**: реплики получают WAL; `synchronous_commit` и `synchronous_standby_names` задают, ждёт ли коммит подтверждения реплик (remote_write, on, remote_apply). **Patroni** + etcd — автоматический failover с выбором лидера через консенсус.

**Kafka**: у партиции лидер и ISR (in-sync replicas); `acks=all` + `min.insync.replicas=2` — запись подтверждена, когда её получили все синхронные реплики (минимум 2). Unclean leader election выключают, чтобы не терять данные.

**Multi-leader между ДЦ**: конфликты решают LWW, CRDT или бизнес-правила; часто выбирают «лидер на запись для каждого пользователя в его домашнем регионе».

**Leaderless (Dynamo-стиль)**: sloppy quorum и hinted handoff повышают доступность ценой согласованности.

**Проверка отставания**: метрика replication lag — алерт; приложение может выбирать реплику по допустимому лагу.

# @distributed-partitioning

## Глубже: партиционирование в реальных системах
**Kafka**: партиция — единица параллелизма и порядка; количество партиций трудно уменьшить, а при увеличении меняется соответствие ключ → партиция (порядок по ключу временно нарушается). Закладывайте запас заранее.

**Cassandra/ScyllaDB**: токен-кольцо с vnodes; ScyllaDB — shard-per-core внутри узла. **DynamoDB**: адаптивная ёмкость и разбиение горячих партиций.

**Вторичные индексы при шардировании**: локальные (на каждом шарде — scatter/gather при чтении) или глобальные (отдельно шардированный индекс — асинхронное обновление).

**Горячие ключи**: key salting (`celebrity#0..9`), локальный кэш, отдельная очередь для «китов», request coalescing.

**Rendezvous hashing** (HRW) — альтернатива consistent hashing: для ключа выбирается узел с максимальным hash(key, node), просто и равномерно.

**Jump consistent hash** (Google) — быстрый алгоритм без хранения кольца, но только для нумерованных бакетов.

# @distributed-consensus

## Глубже: Raft в деталях
**Безопасность лога**: лидер никогда не перезаписывает свой лог; фолловер с расходящимся логом откатывается до точки совпадения (проверка по индексу и term предыдущей записи). Лидер коммитит записи только своего term (и неявно — все предыдущие).

**Изменение состава кластера**: joint consensus или добавление/удаление по одному узлу; новый узел сначала догоняет как «learner», не участвуя в голосовании.

**Чтения**: линеаризуемое чтение требует подтверждения, что лидер всё ещё лидер: **ReadIndex** (кворум heartbeat) или **leases** (опора на ограниченный дрейф часов). Чтение с фолловера без этого — устаревшее.

**Снапшоты лога** — компактизация: состояние машины + индекс, старые записи удаляются.

**Pre-vote** — узел, оторванный от сети, не увеличивает term бесконечно и не сбивает лидера при возвращении.

**Где не нужен свой консенсус**: используйте etcd/ZooKeeper/Consul; реализовывать Raft самому — только в учебных целях (отличное упражнение: MIT 6.824).

## Глубже: идемпотентность end-to-end
**Где нужна**: HTTP-API (ключ идемпотентности), потребители сообщений (inbox), фоновые задания, вебхуки, интеграции с платёжками (передавать ключ провайдеру).

**Реализация ключа в API**:
1. `INSERT INTO idempotency_keys (key, request_hash, status='processing')` — уникальный индекс;
2. конфликт и статус processing → 409 (запрос ещё выполняется); конфликт с другим `request_hash` → 422 (ключ переиспользован для другого запроса);
3. выполнить операцию **в той же транзакции** (если локальна) и сохранить ответ;
4. повтор → вернуть сохранённый ответ; срок хранения ключей — сутки-неделя.

**Внешние побочные эффекты** (письмо, платёж) внутри транзакции не откатить — выносите в outbox, где и работает идемпотентность отправки.

**Идемпотентность без хранения**: операции «установить значение», условные обновления по версии (`WHERE version = @v`), upsert по естественному ключу.

**Дедупликация в брокерах**: Kafka idempotent producer (дубли от ретраев продюсера), Azure Service Bus duplicate detection по MessageId в окне.

# @distributed-transactions

## Глубже: саги без боли
**Изоляция саги**: промежуточные состояния видны — нужны контрмеры: **семантическая блокировка** (статус «в обработке» на заказе), коммутативные обновления, пессимистичный порядок шагов (сначала то, что проще компенсировать), повторное чтение значения перед решением.

**Типы шагов**: компенсируемые (можно отменить), **pivot** (точка невозврата — после неё сага идёт только вперёд) и повторяемые (гарантированно выполнятся с ретраями). Проектируйте порядок так, чтобы pivot был как можно позже.

**Компенсация ≠ откат**: письмо уже отправлено — компенсация — письмо с извинением; деньги списаны — возврат (с комиссией?). Бизнес должен определить компенсации.

**Durable execution** (Temporal, Azure Durable Functions, Dapr Workflow): сага — это обычный код с try/catch, а платформа хранит прогресс и переживает сбои — гораздо проще конечных автоматов вручную.

**2PC всё ещё жив** внутри одной СУБД-кластера (распределённые SQL-базы делают его поверх консенсуса) и в XA — но не между микросервисами.

# @distributed-messaging

## Глубже: Kafka и RabbitMQ в эксплуатации
**Kafka-потребители**: `enable.auto.commit=false` и коммит offset после обработки; ребалансировка группы при добавлении/падении потребителя останавливает чтение — **cooperative sticky** assignor уменьшает паузы; обработка должна успевать за `max.poll.interval.ms`.

**Ошибки обработки**: ретраи в памяти → retry-топики с задержкой → DLQ; «ядовитое» сообщение не должно блокировать партицию навсегда.

**Схемы**: Schema Registry (Avro/Protobuf/JSON Schema) с проверкой совместимости при публикации.

**Kafka как хранилище**: compacted topics хранят последнее значение по ключу — таблица изменений; retention по времени/размеру.

**RabbitMQ**: prefetch (QoS) ограничивает число неподтверждённых сообщений на потребителя; quorum queues для надёжности (Raft), streams для лог-подобного чтения; publisher confirms — продюсер знает, что брокер принял сообщение.

**MassTransit** в .NET: абстракция над брокерами, ретраи и redelivery, outbox/inbox, саги-автоматы, тестовый harness.

# @distributed-streaming

## Глубже: состояние и гарантии в потоковой обработке
**Состояние оператора** (счётчики окон, join-таблицы) хранится локально (RocksDB во Flink, state store в Kafka Streams) и реплицируется в changelog-топик или чекпоинты — после сбоя восстанавливается.

**Exactly-once в Kafka Streams/Flink**: транзакции Kafka связывают чтение входа, запись выхода и коммит offset атомарно; внешние системы — через идемпотентные или транзакционные sink'и.

**Stream–table duality**: поток изменений можно свернуть в таблицу, таблицу — развернуть в поток изменений (CDC). KTable в Kafka Streams — материализованное представление.

**Join'ы**: stream–stream (в окне времени), stream–table (обогащение справочником), table–table.

**Опоздавшие события**: allowed lateness и боковой вывод (side output) для слишком поздних.

**Когда не нужен стриминг**: если достаточно минутных задержек, микро-батчи или периодические SQL-агрегации проще в эксплуатации.

# @distributed-resilience

## Глубже: управление перегрузкой
**Адаптивный параллелизм**: вместо фиксированного лимита — алгоритмы, подстраивающие допустимое число одновременных запросов по латентности (TCP-подобный AIMD, Netflix concurrency-limits, Vegas). Сервис сам находит свою пропускную способность.

**Приоритезация и load shedding**: при перегрузке отказывать сначала фоновым и некритичным запросам; очередь LIFO при перегрузке (свежие запросы ещё кому-то нужны, старые — нет); отбрасывать запросы, у которых истёк дедлайн клиента.

**Retry budget**: ретраи не больше 10–20% от основного трафика на клиенте; сервер может отдавать «не повторять» (`Retry-After`, специальный заголовок).

**Изоляция клиентов** (bulkhead по арендаторам): «шумный сосед» не должен съесть ресурсы всех — квоты на арендатора, отдельные пулы.

**Cell-based architecture**: система делится на независимые ячейки со своими данными и сервисами; отказ ячейки затрагивает только её клиентов (AWS, Slack).

**Game days и chaos engineering**: регулярные учения с контролируемыми отказами (Chaos Mesh, Azure Chaos Studio, Litmus).

# @distributed-orleans

## Глубже: Orleans в продакшене
**Размещение grain'ов**: по умолчанию случайное; стратегии — prefer local, hash-based, activation count; stateless workers для масштабируемых без состояния операций.

**Однопоточность и reentrancy**: grain обрабатывает один запрос за раз; `await` вызова другого grain'а, который вызывает первый, — дедлок без `[Reentrant]` или `[AlwaysInterleave]` на методах. Проектируйте без циклических вызовов.

**Состояние**: `IPersistentState<T>` с провайдерами (ADO.NET, Azure Table/Blob, Redis); запись явная (`WriteStateAsync`) — решайте, когда сохранять. Транзакции между grain'ами (ACID) есть, но дороги.

**Потоки (streams)**: pub/sub между grain'ами поверх брокеров (Event Hubs, очереди).

**Кластер**: membership через таблицу в БД/облаке, graceful shutdown переносит активации; версионирование интерфейсов grain'ов для rolling upgrade.

**Когда нет**: аналитика по всем сущностям, простой CRUD, строгие межсущностные транзакции.
