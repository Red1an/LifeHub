# @dotnet-host

## Глубже: жизненный цикл хоста
Старт: `Build()` создаёт контейнер → `IHostedLifecycleService.StartingAsync` → `IHostedService.StartAsync` по порядку регистрации → Kestrel начинает слушать → `ApplicationStarted`. По умолчанию `StartAsync` каждого сервиса выполняется **последовательно**, и медленный старт одного задерживает всё приложение (`HostOptions.ServicesStartConcurrently` меняет это).

Остановка по SIGTERM/Ctrl+C: `ApplicationStopping` → Kestrel перестаёт принимать соединения и ждёт текущие запросы → `StopAsync` сервисов в обратном порядке → `ApplicationStopped`. Всё это укладывается в `ShutdownTimeout` (30 с по умолчанию); в Kubernetes `terminationGracePeriodSeconds` должен быть больше.

Конфигурация перезагружается при изменении файлов (`reloadOnChange`) — `IOptionsMonitor` получает новое значение; валидация (`ValidateOnStart`, `IValidateOptions<T>`) защищает от битых настроек. Для горячих путей логирования — `[LoggerMessage]`: генерирует код без упаковки и проверяет уровень до форматирования.

# @dotnet-di

## Глубже: как устроен контейнер
Встроенный контейнер строит **дерево вызовов** для каждого сервиса при первом разрешении и кэширует его (с .NET 6 — компиляция в IL/выражения). Scoped-экземпляры хранятся в `IServiceScope`; `IDisposable`-сервисы, созданные контейнером, освобождаются вместе со scope — **не диспозьте их сами**. Transient `IDisposable` из корневого провайдера живут до конца приложения — утечка.

Порядок регистраций: при нескольких реализациях `GetService<T>` вернёт **последнюю**, а `IEnumerable<T>` — все. `TryAdd*` не перезаписывает существующее — так библиотеки дают переопределять свои сервисы.

`ValidateOnBuild` проверяет, что все зависимости разрешимы, при старте. Для сложных сценариев (декораторы, перехватчики, сканирование сборок) — Scrutor или сторонние контейнеры (Autofac) через `UseServiceProviderFactory`.

Анти-паттерны: внедрение `IServiceProvider` в бизнес-классы, «божественные» конструкторы с 10+ зависимостями (признак нарушения SRP), async-инициализация в конструкторе (конструкторы должны быть быстрыми и без I/O).

# @dotnet-middleware

## Глубже: маршрутизация и endpoint metadata
С ASP.NET Core 3 маршрутизация разделена: `UseRouting` **выбирает эндпоинт**, а `UseEndpoints`/`Map*` его **выполняет**. Между ними middleware видит выбранный эндпоинт и его **метаданные** (`context.GetEndpoint()?.Metadata`) — так авторизация, CORS, rate limiting и output cache узнают атрибуты и настройки конкретного маршрута.

Свой middleware с метаданными: добавьте атрибут/объект в метаданные эндпоинта (`.WithMetadata(new AuditAttribute())`) и проверяйте его в middleware — сквозная логика, управляемая декларативно.

**Short-circuit** (.NET 8): `app.MapGet("/health", ...).ShortCircuit()` — выполнить эндпоинт сразу после маршрутизации, пропустив остальной конвейер.

**Ошибки**: `IExceptionHandler` (.NET 8) — цепочка обработчиков исключений, можно отдельно обрабатывать `ValidationException` → 400, `NotFoundException` → 404, остальное → 500 ProblemDetails. `UseStatusCodePages` — тела для пустых 4xx.

Middleware должен быть **быстрым и неблокирующим**: он выполняется на каждый запрос.

# @dotnet-api

## Глубже: контракты и эволюция API
**OpenAPI как контракт**: генерируйте клиентов из спецификации (NSwag, Kiota), проверяйте ломающие изменения диффом спецификаций в CI (oasdiff). **Схема ошибок** — единая: ProblemDetails с `type` (URI вида ошибки), `errors` для валидации, `traceId` для поддержки.

**Идемпотентность POST**: заголовок `Idempotency-Key`, хранение ключа и ответа, 409 при параллельном повторе. **Условные запросы**: `ETag` + `If-Match` для оптимистичной конкуренции на уровне HTTP — `412 Precondition Failed`, если ресурс изменился.

**Долгие операции**: `202 Accepted` + `Location` на ресурс статуса операции; клиент опрашивает или получает вебхук.

**Большие ответы**: стриминг `IAsyncEnumerable<T>` (System.Text.Json пишет массив по мере получения), поля по запросу (`?fields=`), сжатие.

**Версионирование**: изменения, требующие новой версии, редки, если с самого начала: не возвращать сущности, не удалять поля, толерантный клиент. Deprecation-заголовки (`Deprecation`, `Sunset`) заранее предупреждают клиентов.

# @dotnet-mediatr

## Глубже: альтернативы и транзакционные границы
**Транзакция на команду**: pipeline behavior открывает транзакцию, вызывает обработчик, коммитит и публикует доменные события **после** коммита (или через outbox). Запросы транзакции не требуют.

**Уведомления** (`INotification`) обрабатываются всеми подписчиками последовательно в том же процессе и той же транзакции — это не шина сообщений; падение одного обработчика валит всю операцию. Для надёжности — outbox и брокер.

**Альтернативы без рефлексии**: Mediator (martinothamar) — source generator, быстрее и совместим с AOT; Wolverine — медиатор + шина + outbox; или просто интерфейс `ICommandHandler<T>` и декораторы через Scrutor — 30 строк и полный контроль.

**Vertical slices**: одна фича = запрос + обработчик + валидатор + эндпоинт в одном файле или папке. Дублирование между срезами допустимо — это цена независимости.

Не прячьте за медиатором вызовы между обработчиками (`Send` внутри `Handle`) — это скрытая связанность; выносите общее в доменные сервисы.

# @dotnet-auth

## Глубже: токены и BFF
**Где хранить токены в SPA**: localStorage уязвим к XSS; в памяти — теряется при перезагрузке. Современная рекомендация (OAuth 2.0 for Browser-Based Apps) — **BFF (Backend for Frontend)**: SPA общается со своим бэкендом через HttpOnly-куку, а бэкенд хранит токены и проксирует вызовы API (Duende BFF, YARP).

**Проверка JWT в ASP.NET Core**: ключи подписи берутся из JWKS (`/.well-known/openid-configuration`) и кэшируются; ротация ключей провайдером проходит автоматически. Проверяются `ValidIssuer`, `ValidAudience`, `ClockSkew` (по умолчанию 5 минут — часто уменьшают).

**Scopes vs roles**: scope — что разрешено **клиентскому приложению** от имени пользователя (`orders.read`); роль — кто **пользователь**. API проверяет оба.

**Token exchange / on-behalf-of**: сервис A вызывает сервис B от имени пользователя, обменяв токен на новый с audience B — не пробрасывайте токен для A дальше.

**Claims transformation** (`IClaimsTransformation`) — обогатить принципал своими правами из БД; кэшируйте, она вызывается на каждый запрос.

Q: Почему для SPA рекомендуют BFF вместо хранения токенов в браузере?

# @dotnet-grpc

## Глубже: gRPC в продакшене
**Балансировка**: gRPC держит долгоживущее HTTP/2-соединение, и L4-балансировщик отправит все запросы клиента на один сервер. Нужна **L7-балансировка** (Envoy, Linkerd, YARP) или клиентская балансировка (`GrpcChannel` с `LoadBalancingConfig` и DNS-резолвером).

**Дедлайны** распространяются: клиент задаёт `deadline`, сервер получает `context.CancellationToken`, который срабатывает при истечении, — передавайте его во все вызовы.

**Эволюция контракта**: номера полей в `.proto` нельзя менять и переиспользовать (`reserved 3;`), новые поля — только добавлять, всё опционально по умолчанию. **Статусы**: используйте `RpcException` с кодами (`NotFound`, `InvalidArgument`, `Unavailable`), rich error model — детали в `google.rpc.Status`.

**Стриминг**: server/client/bidirectional streams — для подписок и потоковой загрузки; помните о backpressure и отмене. **gRPC-Web** или **JSON transcoding** (`AddJsonTranscoding`) дают доступ из браузера и REST-клиентов к тем же сервисам.

**SignalR в масштабе**: Azure SignalR Service или Redis backplane; сообщения группам; клиентские результаты (.NET 7) для вызова клиента с ответом.

# @dotnet-background

## Глубже: надёжная фоновая обработка
**Проблемы простого BackgroundService**: задания теряются при рестарте, нет повторов, при нескольких экземплярах задача выполняется на каждом (дубли).

Решения:
- **Распределённая блокировка / лидер**: только один экземпляр выполняет периодическую задачу (блокировка в БД `pg_try_advisory_lock`, Redis, лизинг в Azure Blob).
- **Очередь заданий в БД**: таблица с `status`, `locked_until`; воркеры берут задание `SELECT ... FOR UPDATE SKIP LOCKED` — классический надёжный паттерн на PostgreSQL.
- **Hangfire / Quartz** с кластерным режимом.
- **Брокер** (RabbitMQ, SQS) для событийной обработки с ретраями и DLQ.

**Идемпотентность заданий** обязательна: воркер может упасть после выполнения, но до отметки «готово».

**Channels внутри процесса**: ограниченный канал + фиксированное число потребителей = управляемый параллелизм; при остановке — `writer.Complete()` и дождаться дренажа очереди в `StopAsync`.

**Наблюдаемость**: метрики длины очереди, времени выполнения, ошибок; трассировка каждого задания как отдельного спана.

# @dotnet-resilience

## Глубже: настройка стратегий под реальность
**Таймауты по бюджету**: если общий SLA запроса 2 с, а цепочка — три вызова, то каждому таймаут меньше; передавайте оставшийся бюджет вниз (дедлайн), а не фиксированные 30 с.

**Circuit breaker**: настраивается по доле ошибок в окне (`FailureRatio = 0.5` за 30 с при минимуме 20 запросов), время открытого состояния, пробные запросы. Отдельный breaker на каждую зависимость (и даже на каждый хост).

**Hedging** — для чтения с высоким хвостом латентности: если ответа нет за p95, послать параллельный запрос к другой реплике и взять первый. Цена — дополнительная нагрузка.

**Rate limiter на клиенте** — не превышать квоты внешнего API; уважать `Retry-After` из 429/503.

**Chaos engineering в .NET**: Polly Chaos (Simmy) — внедрение задержек и ошибок по доле запросов в тестовой среде, чтобы проверить, что стратегии действительно работают.

**Телеметрия**: Polly и Microsoft.Extensions.Resilience публикуют метрики (срабатывания ретраев, открытия breaker) — выводите их на дашборд.

# @dotnet-caching

## Глубже: согласованность кэша
**Гонка «прочитал старое — записал в кэш»**: запрос A читает из БД старое значение, запрос B обновляет БД и удаляет ключ, затем A кладёт старое значение в кэш — устаревшие данные до конца TTL. Смягчение: короткий TTL, версия в ключе, задержанное повторное удаление (delete — пауза — delete), инвалидация по событиям CDC.

**Двухуровневый кэш** (HybridCache): L1 в памяти каждого экземпляра, L2 в Redis. Инвалидация L1 на других экземплярах требует рассылки (Redis pub/sub) — иначе они видят старое до истечения L1-TTL. Держите L1-TTL коротким.

**Что кэшировать**: результаты дорогих вычислений и запросов с высокой долей чтения; **не** кэшировать данные с жёсткими требованиями согласованности (баланс перед списанием).

**Ключи**: версионированные (`v2:product:42`), с учётом арендатора и языка; избегайте огромных значений (сериализация и сеть), сжимайте.

**Output cache vs response cache**: response caching управляет HTTP-заголовками для прокси и браузеров; output cache хранит ответ на сервере с тегами и программной инвалидацией (`IOutputCacheStore.EvictByTagAsync`).

# @dotnet-observability

## Глубже: наблюдаемость без взрыва стоимости
**Сэмплирование трейсов**: сохранять 100% дорого. **Head sampling** — решение в начале запроса (например, 10%); **tail sampling** в OpenTelemetry Collector — сохранить все трейсы с ошибками и медленные, остальные — выборочно.

**Кардинальность метрик**: метки только с ограниченным набором значений (маршрут-шаблон, код ответа), никогда — id пользователя или URL с параметрами.

**Корреляция логов**: OpenTelemetry-логгер добавляет `TraceId`/`SpanId` в каждую запись; в Loki/Seq по trace id видно все логи запроса во всех сервисах.

**Семантические соглашения** OTel: стандартные имена атрибутов (`http.request.method`, `db.system`) — дашборды и алерты работают для всех сервисов одинаково.

**Exemplars**: метрика латентности хранит ссылку на пример трейса — из всплеска на графике сразу к конкретному медленному запросу.

**Профилирование в проде**: непрерывные профайлеры (Pyroscope и аналоги) показывают горячие методы без воспроизведения.

## Глубже: Aspire за пределами F5
**Тесты**: `Aspire.Hosting.Testing` поднимает весь AppHost в интеграционном тесте — реальные контейнеры БД и брокера, сервисы, связи — и даёт HttpClient к нужному сервису. Это самый полный интеграционный тест распределённого приложения.

**Свои ресурсы**: `builder.AddContainer("mailpit", "axllent/mailpit")`, `AddExecutable` для не-.NET процессов, `AddNpmApp`/`AddPythonApp` для других стеков; параметры и секреты через `AddParameter`.

**Service defaults**: общий проект с `AddServiceDefaults()` — OpenTelemetry, health checks, resilience, service discovery — одинаково во всех сервисах.

**Деплой**: `aspire publish` / `azd` строят артефакты (Docker Compose, Kubernetes, облачные ресурсы) из описания AppHost; в проде Aspire Dashboard можно запускать отдельно как OTLP-приёмник.

**Ограничения**: AppHost — инструмент разработки и описания; он не оркестрирует прод, как Kubernetes, и не заменяет IaC для сложной инфраструктуры.

# @dotnet-performance

## Глубже: нагрузочное тестирование правильно
**Цель**: не «выдержит ли 1000 RPS», а **кривая**: латентность p50/p95/p99 при росте нагрузки и точка насыщения. Модели нагрузки: **открытая** (запросы приходят с заданной частотой, как в реальности) против **закрытой** (N виртуальных пользователей ждут ответа — занижает проблемы при деградации, coordinated omission).

**Инструменты**: k6 (сценарии на JS, open model через `constant-arrival-rate`), NBomber (на C#), Bombardier/wrk для простого HTTP. Тестируйте на окружении, похожем на прод, с прогретым приложением и реалистичными данными.

**Во время теста** снимайте `dotnet-counters` (CPU, GC, пул потоков, соединения), метрики БД, трейсы медленных запросов.

**Типичные находки**: пул соединений к БД исчерпан (`Max Pool Size`), синхронные блокировки, N+1, отсутствие индексов, аллокации в сериализации, логирование на каждый запрос с интерполяцией, лимиты Kestrel/прокси.

**Kestrel**: `MaxConcurrentConnections`, `Limits.MinRequestBodyDataRate`; за прокси — keep-alive к upstream.

# @dotnet-deploy

## Глубже: выкатка без простоя
**Rolling update в Kubernetes без 5xx** — это цепочка условий:
1. readiness-проба: новый под получает трафик только когда готов;
2. при остановке старого пода Kubernetes одновременно шлёт SIGTERM и начинает убирать его из балансировки — есть окно, когда трафик ещё идёт; поэтому **preStop-пауза** (5–10 с) перед остановкой;
3. приложение дорабатывает текущие запросы в пределах ShutdownTimeout;
4. `maxUnavailable: 0`, `maxSurge: 1` — всегда есть достаточно готовых подов.

**Миграции БД** при rolling update: expand/contract, миграции отдельной Job до выкатки, обратная совместимость кода с предыдущей схемой.

**Откат**: образы с неизменяемыми тегами (git sha), `kubectl rollout undo` или revert в GitOps; миграции, которые нельзя откатить, делайте особенно аккуратно.

**Конфигурация**: одна сборка для всех окружений, различия — в переменных окружения и секретах. **Feature flags** (Microsoft.FeatureManagement) отделяют выкатку от включения.

**Публикация**: ReadyToRun для быстрого старта, trimmed/AOT — для маленьких образов, chiseled-образы Ubuntu без shell.
