# @onec-platform

## Платформа и конфигурация
**1С:Предприятие** — платформа (среда исполнения, СУБД-абстракция, интерфейс) + **конфигурация** (прикладное решение: Бухгалтерия, ERP, УТ). Разработчик описывает **объекты метаданных**, а платформа сама создаёт таблицы в СУБД, формы и механизмы.

Основные объекты:
- **Справочники** — списки (Номенклатура, Контрагенты), иерархия, реквизиты, табличные части.
- **Документы** — факты хозяйственной деятельности (Поступление, Реализация), имеют дату, номер, **проведение**.
- **Перечисления** — фиксированные наборы значений.
- **Регистры**: сведений, накопления, бухгалтерии, расчёта — где хранятся учётные итоги.
- **Отчёты, обработки, общие модули, роли, подсистемы, HTTP-сервисы**.

## Архитектура
- **Файловый режим** — база в файле, для небольших баз.
- **Клиент-серверный** — кластер серверов 1С + СУБД (MS SQL Server, PostgreSQL). Код исполняется на клиенте (тонкий клиент, веб-клиент) и на сервере.

## Инструменты
**Конфигуратор** — классическая среда. **1C:EDT** (Enterprise Development Tools) — современная IDE на Eclipse с git, рефакторингами, проверками — выбор для командной разработки. Хранилище конфигурации — старый способ совместной работы.

Для C#-разработчика: 1С — это DSL для учётных систем с очень высоким уровнем абстракции; многое, что в .NET пишется руками (ORM, UI, права), здесь даёт платформа.

# @onec-language

## Встроенный язык
Русскоязычный синтаксис (есть английские аналоги), динамическая типизация.
```bsl
Функция СуммаСтрок(Таблица) Экспорт
    Итог = 0;
    Для Каждого Строка Из Таблица Цикл
        Итог = Итог + Строка.Сумма;
    КонецЦикла;
    Возврат Итог;
КонецФункции
```
Коллекции: **Массив**, **Структура** (ключ-значение с фиксированными ключами-строками), **Соответствие** (словарь), **ТаблицаЗначений** (таблица в памяти с колонками, индексами, группировкой), **СписокЗначений**.

## Клиент и сервер
Код исполняется в разных контекстах, указанных директивами:
- `&НаКлиенте` — на компьютере пользователя (нет доступа к базе);
- `&НаСервере` — на сервере, **с контекстом формы** (данные формы передаются туда и обратно — дорого);
- `&НаСервереБезКонтекста` — на сервере без передачи формы (дёшево, предпочтительно);
- `&НаКлиентеНаСервереБезКонтекста`.

Каждый вызов сервера с клиента — сетевой круг. Правило: **минимум серверных вызовов**, собирать данные за один вызов.

## Модули
- **Общие модули** с флагами: Сервер, Клиент, Вызов сервера, Привилегированный, Глобальный. Повторное использование значений — кэширование результатов функций.
- **Модули объектов и менеджеров** — логика конкретного справочника/документа.
- **Обработчики событий**: `ПередЗаписью`, `ОбработкаПроведения`, `ОбработкаЗаполнения`, `ПриЗаписи`.

Q: Почему в 1С важно минимизировать серверные вызовы с клиента?
A: Каждый вызов — сетевой круг между клиентом и сервером, а контекстный вызов ещё и передаёт данные формы. Много мелких вызовов делают интерфейс медленным, особенно через интернет; данные нужно получать одним вызовом без контекста.

# @onec-queries

## Язык запросов
Похож на SQL, но работает с объектами метаданных и поддерживает разыменование ссылок через точку:
```bsl
Запрос = Новый Запрос;
Запрос.Текст =
"ВЫБРАТЬ
|    Реализация.Контрагент.Наименование КАК Клиент,
|    СУММА(Реализация.СуммаДокумента) КАК Сумма
|ИЗ
|    Документ.РеализацияТоваровУслуг КАК Реализация
|ГДЕ
|    Реализация.Дата МЕЖДУ &Начало И &Конец
|    И Реализация.Проведен
|СГРУППИРОВАТЬ ПО
|    Реализация.Контрагент.Наименование";
Запрос.УстановитьПараметр("Начало", НачалоМесяца(ТекущаяДата()));
Запрос.УстановитьПараметр("Конец", КонецМесяца(ТекущаяДата()));
Выборка = Запрос.Выполнить().Выбрать();
```
Параметры — через `&Имя` и `УстановитьПараметр` (защита от ошибок и инъекций). Разыменование `Контрагент.Наименование` неявно делает соединение — удобно, но при злоупотреблении запросы тяжелеют.

## Виртуальные таблицы регистров
Готовые таблицы с итогами: `РегистрНакопления.ТоварыНаСкладах.Остатки(&Дата, Склад = &Склад)`, `.Обороты`, `.ОстаткиИОбороты`, `СрезПоследних` у регистров сведений. **Условия пишут в параметрах виртуальной таблицы**, а не в ГДЕ — тогда платформа отбирает данные до расчёта итогов.

## Временные таблицы и пакеты
**Пакетный запрос** — несколько запросов через `;`, **временные таблицы** (`ПОМЕСТИТЬ ВТ_Товары`) передают результат следующему, можно индексировать.

## Главный антипаттерн
**Запрос в цикле**: для каждой строки документа — отдельный запрос за ценой. 1000 строк = 1000 обращений к СУБД. Правильно — один запрос по всем товарам сразу (через параметр-массив или временную таблицу) и работа с результатом в памяти.

Q: Почему условия отбора лучше писать в параметрах виртуальной таблицы регистра?
A: Платформа применяет их до расчёта остатков и оборотов, обрабатывая только нужные записи и итоги. Условие в ГДЕ фильтрует уже рассчитанный результат по всем данным — медленнее и может дать неверные итоги.

# @onec-registers

## Проведение
Документ сам по себе — первичка. При **проведении** (`ОбработкаПроведения`) он формирует **движения** по регистрам — именно они дают учётные итоги. Отмена проведения удаляет движения. Движения — это записи, подчинённые регистратору (документу).

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)
    Движения.ТоварыНаСкладах.Записывать = Истина;
    Для Каждого Строка Из Товары Цикл
        Движение = Движения.ТоварыНаСкладах.ДобавитьРасход();
        Движение.Период = Дата;
        Движение.Склад = Склад;
        Движение.Номенклатура = Строка.Номенклатура;
        Движение.Количество = Строка.Количество;
    КонецЦикла;
КонецПроцедуры
```

## Виды регистров
- **Накопления** (остатки или обороты): приход/расход — склад, деньги, взаиморасчёты.
- **Сведений**: значения по измерениям, могут быть **периодическими** (цены, курсы — срез последних на дату).
- **Бухгалтерии**: проводки по плану счетов.
- **Расчёта**: начисления с периодами действия (зарплата).

## Контроль остатков и блокировки
Чтобы не отгрузить больше, чем есть: записать движения, затем **проверить остатки** запросом и отказать при отрицательных. В параллельной работе нужны **управляемые блокировки** (`БлокировкаДанных`) на нужные измерения регистров, иначе два документа одновременно спишут один товар. Новая методика — сначала движения, потом контроль по регистру в той же транзакции.

# @onec-bsp

## Библиотека стандартных подсистем
**БСП** — набор готовых подсистем от 1С, встроенный во все типовые конфигурации: пользователи и права, присоединённые файлы, печать, дополнительные отчёты и обработки, обмен данными, электронная почта, версионирование, обновление ИБ и многое другое. Правило: прежде чем писать своё — проверить, нет ли этого в БСП, и использовать её программный интерфейс (модули с суффиксом `...Переопределяемый`, `...Сервер`).

## Доработка типовых
Изменять типовую конфигурацию напрямую — значит усложнить каждое обновление от 1С (сравнение-объединение). Современный способ — **расширения конфигурации**:
- добавить свои объекты и реквизиты;
- перехватить методы типовых модулей аннотациями `&Перед`, `&После`, `&Вместо`, `&ИзменениеИКонтроль`;
- расширение подключается к базе, типовая остаётся на поддержке, обновления ставятся проще.

## Обновление
Доработанные конфигурации обновляют через сравнение-объединение с новой версией поставщика; расширения проверяют на совместимость. Минимум изменений в типовых объектах — меньше боли. Документировать доработки.

# @onec-forms

## Управляемые формы
Форма описывается декларативно и работает в тонком клиенте, веб-клиенте и мобильном. Разделение:
- **Реквизиты формы** — данные (на сервере и передаются на клиент);
- **Элементы формы** — визуальное представление, связанное с реквизитами;
- **Команды** — действия (кнопки, меню).

Обработчики событий формы: `ПриСозданииНаСервере` (подготовка данных, один раз на сервере), `ПриОткрытии` (на клиенте), `ПередЗаписью`, события элементов (`ПриИзменении`).

## Клиент-серверное взаимодействие
Каждое действие, требующее данных из базы, — серверный вызов. Пример неправильного: при изменении каждого поля вызывать контекстный серверный метод. Правильно: пересчитывать на клиенте что можно, а на сервер ходить без контекста, передавая только нужные параметры.

## Отчёты на СКД
**Система компоновки данных** — механизм отчётов: схема (запрос, поля, ресурсы, параметры) + настройки (группировки, отборы, оформление), которые пользователь может менять сам. Большинство отчётов типовых конфигураций сделаны на СКД. Плюс макеты печатных форм (табличные документы).

A: Реквизиты — данные формы (значения, которые обрабатываются на сервере и клиенте). Элементы — визуальные компоненты (поля, таблицы, кнопки), отображающие реквизиты и вызывающие команды.

# @onec-integration

## Способы интеграции
- **HTTP-сервисы 1С** — свой REST API: шаблоны URL, методы, обработчики на встроенном языке. Самый гибкий способ отдать данные наружу.
- **OData** — стандартный REST-интерфейс ко всем объектам конфигурации (после публикации состава), без программирования. Удобно для чтения и простых операций, но медленнее и раскрывает внутреннюю модель.
- **Веб-сервисы (SOAP)** — для старых интеграций.
- **Обмен через файлы и очереди** — выгрузка JSON/XML, интеграция через RabbitMQ/Kafka (коннекторы, внешние компоненты, промежуточный сервис).
- Из 1С наружу — объект `HTTPСоединение`/`HTTPЗапрос`, JSON-сериализация (`ЗаписатьJSON`, `ПрочитатьJSON`).

```bsl
Функция ОстаткиGET(Запрос)
    Ответ = Новый HTTPСервисОтвет(200);
    Ответ.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");
    Ответ.УстановитьТелоИзСтроки(ПолучитьОстаткиJSON(Запрос.ПараметрыURL["склад"]));
    Возврат Ответ;
КонецФункции
```

## 1С и .NET
Типичная архитектура: .NET-сервис (сайт, мобильное API, интеграции с маркетплейсами) ↔ 1С как учётная система.
- .NET забирает справочники и остатки из HTTP-сервиса 1С, кэширует и отдаёт быстро;
- заказы из .NET попадают в 1С через HTTP POST или очередь, **идемпотентно** по внешнему номеру;
- 1С публикует изменения (регистр сведений «очередь изменений» + фоновое задание отправки) — аналог outbox.

1С часто медленнее и менее доступна, чем .NET-сервисы: закладывайте кэш, ретраи, асинхронность и не делайте синхронных цепочек «запрос сайта → запрос в 1С».

A: HTTP-сервисы (свой REST), OData (стандартный REST к объектам), SOAP веб-сервисы, обмен файлами (JSON/XML), очереди сообщений через компоненты или промежуточные сервисы, исходящие HTTP-запросы из 1С, COM/внешние компоненты.

# @onec-performance

## Откуда тормоза
- Запросы в цикле, неоптимальные запросы (условия не в параметрах виртуальных таблиц, разыменования через несколько точек).
- **Блокировки**: транзакции ждут друг друга, таймауты, взаимоблокировки.
- Лишние серверные вызовы с клиента, контекстные вызовы.
- Большие объёмы в таблицах регистров без актуальных итогов.

## Управляемые блокировки
В управляемом режиме платформа блокирует данные на уровне 1С, а не таблиц СУБД. Разработчик явно блокирует нужные данные перед чтением для изменения (`БлокировкаДанных`, элемент блокировки с полями измерений). Принципы: блокировать как можно меньше и как можно позже, короткие транзакции, одинаковый порядок.

## Инструменты
- **Замер производительности** в конфигураторе — какие строки кода сколько выполняются.
- **Технологический журнал** — события сервера: долгие запросы (DBMSSQL/DBPOSTGRS), ожидания блокировок (TLOCK, TTIMEOUT, TDEADLOCK), исключения.
- **ЦУП** (центр управления производительностью) и **APDEX** — оценка удовлетворённости пользователей временем ключевых операций.
- Со стороны СУБД — планы запросов, индексы (индексирование реквизитов и измерений в конфигураторе).

Q: Какие принципы работы с управляемыми блокировками в 1С?
A: Блокировать только нужные данные (по конкретным измерениям), как можно позже и на минимальное время, держать транзакции короткими, соблюдать единый порядок блокировок, не выполнять внутри транзакций интерактив и долгие внешние вызовы.
