# @sec-mindset

## Три свойства, которые мы защищаем
**Триада CIA**:
- **Конфиденциальность** — данные видит только тот, кому можно (утечка базы клиентов — нарушение).
- **Целостность** — данные не изменены незаметно (подменили сумму перевода — нарушение).
- **Доступность** — система работает, когда нужна (DDoS, шифровальщик — нарушение).
Любая уязвимость бьёт по одному или нескольким из них. Полезно добавить **подотчётность**: кто и когда что сделал (журналы аудита).

## Принципы защиты
- **Наименьшие привилегии** — у сервиса, пользователя, токена ровно те права, что нужны. Взломали — ущерб ограничен.
- **Эшелонированная защита** (defense in depth) — несколько независимых слоёв: WAF, валидация, параметризованные запросы, права БД. Пробили один — остановят другие.
- **Запрет по умолчанию** — всё, что явно не разрешено, запрещено (эндпоинт без атрибута авторизации — закрыт).
- **Минимальная поверхность атаки** — меньше открытых портов, эндпоинтов, зависимостей, функций — меньше мест для атаки.
- **Не доверять входу** — всё, что пришло извне (запрос, файл, заголовок, сообщение из очереди, ответ чужого API), может быть враждебным.
- **Безопасность по умолчанию** — безопасный вариант должен быть самым простым.

## Моделирование угроз
Лучшее время думать о безопасности — **до написания кода**. Простой процесс на час:
1. **Нарисовать** систему: компоненты, хранилища, потоки данных, **границы доверия** (интернет → API, API → БД, сервис → внешний провайдер).
2. **Найти угрозы** по STRIDE для каждого элемента:
   - **S**poofing — выдать себя за другого;
   - **T**ampering — подменить данные;
   - **R**epudiation — отказаться от совершённого действия;
   - **I**nformation disclosure — утечка;
   - **D**enial of service — отказ в обслуживании;
   - **E**levation of privilege — повышение прав.
3. **Оценить** риск: вероятность × ущерб.
4. **Решить**: устранить, снизить, принять, передать — и записать в задачи.
Четыре вопроса Адама Шостака: что мы строим? что может пойти не так? что мы с этим сделаем? хорошо ли мы справились?

# @sec-injection

## Общий корень
Инъекция возникает, когда **данные пользователя смешиваются с кодом** интерпретатора: SQL, командной оболочки, пути файла, шаблона, запроса LDAP. Интерпретатор не отличает «данные» от «команды» — и выполняет то, что подсунул атакующий.

Универсальное лекарство: **передавать данные отдельно от кода** — параметры запроса, массивы аргументов процесса, API вместо сборки строк. Валидация входа — дополнительный слой, но не замена.

## SQL и NoSQL
```csharp
// Уязвимо: строка собирается из ввода
db.Database.ExecuteSqlRaw($"UPDATE users SET name = '{name}' WHERE id = {id}");
// Безопасно: FormattableString → параметры
db.Database.ExecuteSql($"UPDATE users SET name = {name} WHERE id = {id}");
```
Ловушки даже с ORM: `FromSqlRaw`/`ExecuteSqlRaw` с интерполяцией, динамический `ORDER BY` по имени колонки из запроса (параметром колонку не передать — только белый список), `LIKE` без экранирования `%`. В MongoDB — операторы в JSON-вводе (`{"$ne": null}` вместо пароля).

## Команды и пути
```csharp
// Уязвимо: оболочка интерпретирует ; && |
Process.Start("bash", $"-c \"convert {fileName} out.png\"");
// Лучше: без оболочки, аргументы списком
var psi = new ProcessStartInfo("convert");
psi.ArgumentList.Add(fileName); psi.ArgumentList.Add("out.png");
```
**Path traversal**: `../../etc/passwd` в имени файла. Защита: не использовать имя от пользователя как путь; если нужно — `Path.GetFullPath` и проверка, что результат внутри разрешённой папки; генерировать свои имена (GUID).

## Десериализация и XML
- **Небезопасная десериализация**: `BinaryFormatter` (удалён в .NET 9), `Newtonsoft.Json` с `TypeNameHandling.All/Auto` на недоверенных данных — атакующий указывает тип, и при создании объекта выполняется его код. Используйте System.Text.Json с явными типами, без полиморфизма по имени типа из входа.
- **XXE**: XML с внешними сущностями читает файлы сервера. В современном .NET `XmlReader` по умолчанию безопасен (DtdProcessing.Prohibit), но старые настройки `XmlDocument` с `XmlResolver` опасны.
- **Template injection**: пользовательский ввод как шаблон Razor/Scriban/Handlebars — выполнение кода.

Q: Что общего у всех видов инъекций и как с ними бороться?
A: Недоверенные данные попадают в интерпретатор как часть кода (SQL, shell, путь, шаблон, XML). Защита — разделять данные и код: параметризованные запросы, списки аргументов без оболочки, белые списки, безопасные API; валидация — дополнительный слой.

A: Он позволяет входным данным указывать .NET-тип создаваемого объекта. Атакующий подставляет тип-«гаджет», конструктор или сеттеры которого выполняют опасные действия, — удалённое выполнение кода при десериализации.

# @sec-xss

## Что такое XSS
Cross-Site Scripting — атакующий заставляет **ваш сайт** выполнить **его скрипт** в браузере жертвы. Скрипт работает с правами сайта: читает данные страницы, делает запросы от имени пользователя, крадёт токены из localStorage.
- **Stored** — вредный код сохранён (комментарий, имя профиля) и показан другим.
- **Reflected** — код в параметре ссылки и сразу отражён в ответе.
- **DOM-based** — уязвим клиентский JavaScript (`innerHTML = location.hash`).

## Защита
1. **Кодирование вывода по контексту**: Razor и React экранируют по умолчанию. Опасны `@Html.Raw`, `MarkupString` в Blazor, `dangerouslySetInnerHTML`, `innerHTML`, `v-html`.
2. Если нужен пользовательский HTML (редактор) — **санитайзер** с белым списком тегов (HtmlSanitizer для .NET).
3. **Content-Security-Policy** — второй эшелон: браузер выполняет скрипты только из разрешённых источников.
```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-r4nd0m'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'
```
Без `'unsafe-inline'`: встроенные скрипты — только с nonce или хэшем.

## Заголовки и куки
- `Strict-Transport-Security` — только HTTPS.
- `X-Content-Type-Options: nosniff` — браузер не угадывает тип.
- `frame-ancestors` в CSP (или `X-Frame-Options: DENY`) — защита от **clickjacking** (ваш сайт в невидимом фрейме).
- `Referrer-Policy`, `Permissions-Policy`.
- Куки сессии: **HttpOnly** (недоступны JavaScript — XSS не украдёт), **Secure** (только HTTPS), **SameSite=Lax/Strict** (защита от CSRF), префикс `__Host-`.

## CSRF и CORS
**CSRF** — чужой сайт отправляет запрос к вашему, а браузер прикладывает куки жертвы. Защита: antiforgery-токены (`[ValidateAntiForgeryToken]`, в формах Razor автоматически), SameSite-куки, проверка Origin. API с токеном в заголовке `Authorization` CSRF не подвержены.

**Ошибки CORS**: `Access-Control-Allow-Origin` = значение из заголовка Origin без проверки + `AllowCredentials` — любой сайт читает ответы от имени пользователя. Разрешайте только конкретные origin.

Q: Какие меры защищают от XSS?
A: Контекстное кодирование вывода (шаблонизаторы по умолчанию), отказ от Raw/innerHTML с пользовательскими данными, санитайзер для разрешённого HTML, Content-Security-Policy без unsafe-inline, HttpOnly-куки для сессий, отсутствие токенов в localStorage.

Q: Чем CSRF отличается от XSS?
A: XSS — выполнение чужого скрипта на вашем сайте. CSRF — чужой сайт заставляет браузер жертвы отправить запрос к вашему сайту с её куками; скрипт на ваш сайт не внедряется, ответ атакующий не видит.

# @sec-authn

## Пароли
- Хранить только медленный хэш с солью: **Argon2id**, bcrypt, PBKDF2 (ASP.NET Core Identity `PasswordHasher` — PBKDF2 с сотнями тысяч итераций).
- Политика по NIST: длина важнее сложности (минимум 8, лучше 12+), разрешать длинные фразы, **проверять по базе утёкших паролей** (Have I Been Pwned, k-anonymity API), не заставлять менять без причины.
- Одинаковый ответ и время на «нет такого пользователя» и «неверный пароль» — не раскрывать существование аккаунтов.

## Атаки на вход
- **Перебор** одного аккаунта → блокировка/задержки после N попыток.
- **Credential stuffing** — пары логин/пароль из чужих утечек массово по многим аккаунтам → rate limiting по IP и устройству, CAPTCHA, обнаружение аномалий, MFA.
- **Фишинг** → MFA, устойчивая к фишингу (passkeys).

## Многофакторная аутентификация
- **SMS-коды** — лучше, чем ничего, но уязвимы к подмене SIM.
- **TOTP** (Google Authenticator) — коды из приложения; можно выманить фишингом.
- **Push-подтверждения** — осторожно с «усталостью от пушей» (атакующий шлёт десятки запросов).
- **WebAuthn / passkeys** — ключ привязан к домену сайта криптографически, фишинговый сайт его не получит. Лучший вариант сегодня.

## Сессии и токены
- После входа — **новый** идентификатор сессии (защита от фиксации сессии).
- Разумное время жизни, неактивность → выход, **серверный отзыв** (выход на всех устройствах, смена пароля → отзыв токенов).
- Refresh-токены: хранить безопасно, **ротация** при каждом использовании и обнаружение повторного использования (признак кражи).
- **Восстановление доступа** — частая слабость: одноразовые, короткоживущие, криптостойкие ссылки; не раскрывать, есть ли email в системе; уведомлять о смене пароля.

Q: Как правильно реализовать восстановление пароля?
A: Одинаковый ответ независимо от существования email; одноразовый криптостойкий токен с коротким сроком (хранить хэш); ссылка на HTTPS; после смены — отозвать все сессии и токены, уведомить пользователя; ограничить частоту запросов.

# @sec-authz

## Модели доступа
- **RBAC** — права через роли (Администратор, Менеджер). Просто, но роли размножаются.
- **ABAC** — решение по атрибутам: пользователя (отдел), ресурса (владелец, статус), контекста (время, IP). «Менеджер может править заказы своего региона в статусе Черновик».
- **ReBAC** — по связям в графе (владелец папки → доступ к файлам внутри), как Google Zanzibar; реализации: OpenFGA, SpiceDB.

## Проверка на уровне объекта
Самая частая уязвимость в API — **IDOR / BOLA**: права проверены на «может ли читать заказы», но не на «может ли читать **этот** заказ».
```csharp
public sealed class OrderOwnerHandler : AuthorizationHandler<OwnerRequirement, Order>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx, OwnerRequirement req, Order order)
    {
        if (order.CustomerId.ToString() == ctx.User.FindFirstValue("sub")) ctx.Succeed(req);
        return Task.CompletedTask;
    }
}
// в эндпоинте
var result = await auth.AuthorizeAsync(User, order, "OrderOwner");
if (!result.Succeeded) return Results.NotFound();   // не раскрываем существование
```
Ещё надёжнее — **фильтровать запрос по владельцу** сразу (`Where(o => o.CustomerId == userId)`), тогда чужое физически не загрузится.

## Мультиарендность
В SaaS данные разных клиентов в одной БД — утечка между арендаторами = катастрофа. Меры: `TenantId` во всех таблицах, **global query filter** в EF Core, Row-Level Security в PostgreSQL как второй слой, тесты «пользователь арендатора A не видит данных B».

## Запрет по умолчанию
```csharp
builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build());
```
Теперь всё закрыто, а публичное открывается явно `AllowAnonymous()`. Проверки — **на сервере**: скрытая кнопка в UI не защищает. Для админских функций — отдельные политики, аудит действий, по возможности отдельный интерфейс.

Q: Как защититься от IDOR в API?
A: Проверять права на каждый конкретный объект: фильтровать запросы по владельцу/арендатору, использовать ресурсную авторизацию (AuthorizationHandler с ресурсом), возвращать 404 на чужое, покрывать тестами доступ к чужим объектам; непредсказуемые id — лишь дополнительный слой.

## Шифрование
- **При передаче**: TLS везде, включая внутреннюю сеть между сервисами и до БД (`SSL Mode=Require` в строке подключения), HSTS.
- **При хранении**: шифрование дисков/БД (TDE, облачное шифрование) защищает от кражи носителя. Для особо чувствительных полей (паспорт, номер карты) — **шифрование на уровне приложения** с ключами в KMS, чтобы доступ к БД не давал открытых данных.
- Номера карт вообще не хранить — токенизация у платёжного провайдера (PCI DSS).

## Персональные данные
**Минимизация**: не собирайте то, что не нужно. Каждое поле ПДн — ответственность и риск.
- **Маскирование**: `+7 ••• ••• 12 34` в интерфейсе и логах.
- **Псевдонимизация** в аналитике: вместо email — хэш с секретной солью.
- **Сроки хранения** и удаление по запросу (право на забвение), включая бэкапы и копии в поиске/кэше.
- **Разграничение доступа** сотрудников и аудит просмотров.

## Законы (на уровне разработчика)
- **152-ФЗ** (Россия): согласие на обработку, локализация баз граждан РФ на территории РФ, модель угроз и меры защиты, уведомление Роскомнадзора об утечках.
- **GDPR** (ЕС): законное основание, права субъекта (доступ, удаление, переносимость), privacy by design, уведомление об утечке за 72 часа.
Юридические детали — к юристам, но архитектура должна позволять выполнить требования: найти все данные пользователя, выгрузить, удалить.

# @sec-files

## Загрузка файлов
Файл от пользователя — один из самых опасных входов.
- **Не доверять расширению и Content-Type** — проверять сигнатуру (magic bytes) и допускать только белый список типов.
- **Ограничить размер** (`[RequestSizeLimit]`, лимиты Kestrel) и количество.
- **Своё имя файла** (GUID); исходное имя хранить отдельно и экранировать при выводе.
- Хранить **вне веб-корня** — лучше в объектном хранилище, отдавать через контроллер или подписанные ссылки с `Content-Disposition: attachment`.
- Изображения — перекодировать (убирает вредную нагрузку и метаданные EXIF с геопозицией).
- Антивирусная проверка для документов.
- SVG и HTML — это код: либо запрет, либо отдача с другого домена и строгим CSP.

## Архивы
- **Zip Slip**: имена в архиве вида `../../app/web.config` → распаковка перезаписывает файлы. Проверять полный путь каждого элемента.
- **Zip-бомбы**: 40 КБ архив → 4 ГБ. Лимит на общий распакованный размер и число файлов.

## SSRF
Server-Side Request Forgery: приложение по адресу от пользователя делает запрос (загрузка аватара по URL, вебхуки, предпросмотр ссылок). Атакующий указывает `http://169.254.169.254/` (метаданные облака с токенами), `http://localhost:6379`, внутренние сервисы.
Защита:
- белый список доменов, где возможно;
- резолвить DNS и запрещать приватные, loopback и link-local адреса (**после** резолва и на каждом редиректе — иначе DNS rebinding);
- отдельный egress-прокси для исходящих запросов;
- IMDSv2 в AWS, сетевые политики.

## Open redirect
`/login?returnUrl=https://evil.com` — после входа пользователя перекидывает на фишинговый сайт. Разрешать только локальные адреса: `Url.IsLocalUrl(returnUrl)` / `LocalRedirect`.

# @sec-supply

## Атака через зависимости
Ваше приложение — это 10% вашего кода и 90% чужого. Векторы:
- **известные уязвимости** (CVE) в пакетах;
- **typosquatting** — пакет с похожим именем (`Newtonsoft.Jsom`);
- **захват аккаунта мейнтейнера** и вредная версия популярного пакета;
- **dependency confusion** — публичный пакет с именем вашего внутреннего;
- **slopsquatting** — ИИ «выдумал» несуществующий пакет, а атакующий его зарегистрировал;
- компрометация сборочной инфраструктуры.

## Что делать в .NET
- `dotnet list package --vulnerable --include-transitive` и аудит NuGet при restore (включён по умолчанию, `NuGetAudit`), Dependabot/Renovate для обновлений.
- **Lock-файлы**: `RestorePackagesWithLockFile` + `--locked-mode` в CI — сборка не подтянет неожиданные версии.
- **Package Source Mapping** — внутренние пакеты только из внутреннего фида, публичные — из nuget.org (защита от dependency confusion).
- **Central Package Management** (`Directory.Packages.props`) — версии в одном месте.
- Проверять новую зависимость: популярность, мейнтейнеры, активность, лицензия, действительно ли нужна.

## SBOM и реакция
**SBOM** (CycloneDX, `dotnet CycloneDX` / `sbom-tool`) — список всех компонентов каждой сборки. Когда выходит критическая CVE (как Log4Shell), SBOM за минуты отвечает: «где у нас эта библиотека?». Дальше — обновить, пересобрать, выкатить; для этого нужен быстрый конвейер.

Подпись артефактов (cosign для образов, подписанные NuGet-пакеты) и проверка при деплое замыкают цепочку.

# @sec-logging

## Что логировать для безопасности
- аутентификация: успешные и неуспешные входы, MFA, смена пароля, выход;
- авторизация: отказы в доступе (всплеск 403 — признак перебора);
- административные действия, изменение прав, настроек, экспорт данных;
- ошибки валидации в подозрительных количествах;
- срабатывания rate limiting, WAF.
Каждое событие: **кто** (пользователь, IP, устройство), **что**, **когда**, **над чем**, **результат**, trace id.

## Чего не логировать
Пароли, токены, ключи, полные номера карт и документов, тела запросов с персональными данными. **Log injection**: пользовательский ввод с переводами строк подделывает записи — структурное логирование (поля, а не склеивание строк) решает проблему.

## Аудит
Журнал аудита — отдельно от отладочных логов: **неизменяемый** (append-only, отдельное хранилище, у приложения нет прав на удаление), с долгим сроком хранения. Нужен для расследований и регуляторов.

## Обнаружение и реагирование
- Алерты: множественные неудачные входы, вход из новой страны, массовая выгрузка данных, 403/404-сканирование, новые админы.
- SIEM собирает события со всех систем и коррелирует их.
- **План реагирования** на инцидент: кто дежурит, как изолировать (отозвать токены, заблокировать учётки, выключить функцию), сохранить улики, уведомить (пользователей, регулятора — по закону), восстановить, разобрать без поиска виноватых.

# @sec-aspnet

## Транспорт и заголовки
```csharp
if (!app.Environment.IsDevelopment()) { app.UseExceptionHandler(); app.UseHsts(); }
app.UseHttpsRedirection();
app.Use(async (ctx, next) =>
{
    var h = ctx.Response.Headers;

    h["Content-Security-Policy"] = "default-src 'self'; frame-ancestors 'none'; object-src 'none'";

```
- HTTPS везде, HSTS в проде.
- CORS — только конкретные origin, не `AllowAnyOrigin` вместе с credentials.
- Убрать заголовок `Server` (`options.AddServerHeader = false` в Kestrel).

## Доступ
- **FallbackPolicy** требует аутентификации для всего, публичное — `AllowAnonymous`.
- Ресурсная авторизация для объектов, политики вместо проверок ролей строками по коду.
- Antiforgery для форм на куках; куки: HttpOnly, Secure, SameSite.
- JWT: проверка issuer, audience, lifetime, ключа; короткий срок жизни.

## Ограничения
- Rate limiting (строже на вход и регистрацию).
- Лимиты Kestrel: размер тела (`MaxRequestBodySize`), заголовков, таймауты, число соединений.
- Лимиты размера страниц и глубины JSON (`JsonSerializerOptions.MaxDepth`).
- Таймауты и `CancellationToken` на внешних вызовах.

## Ошибки, данные, зависимости
- ProblemDetails без стек-трейсов в проде, `DeveloperExceptionPage` только локально.
- Data Protection с общим хранилищем ключей.
- Секреты — из хранилища, не в `appsettings`.
- Валидация всех входов (FluentValidation/DataAnnotations), DTO вместо сущностей (защита от mass assignment).
- Аудит пакетов, актуальная версия .NET (патчи безопасности выходят ежемесячно).
- Контейнер: non-root, минимальный образ, read-only файловая система.

# @sec-pentest

## Что такое пентест
Тестирование на проникновение — легальная имитация атаки, чтобы найти уязвимости раньше злоумышленника. **Только с письменного разрешения владельца** и в согласованных рамках — иначе это преступление (в РФ — ст. 272 УК). Практикуйтесь на своих стендах и специальных площадках.

## Этапы
1. **Разведка**: какие домены, эндпоинты, технологии, версии; карта приложения (все страницы и API, параметры, роли).
2. **Поиск уязвимостей**: автоматические сканеры + ручная проверка логики.
3. **Эксплуатация**: подтвердить, что уязвимость реальна и каков ущерб.
4. **Отчёт**: описание, шаги воспроизведения, риск (CVSS), рекомендации.

## Инструменты
- **Burp Suite** (Community бесплатна) — прокси между браузером и сайтом: смотреть и изменять запросы, повторять их (Repeater), перебирать параметры (Intruder).
- **OWASP ZAP** — бесплатный сканер и прокси, удобно встраивается в CI (baseline scan).
- `curl`, DevTools браузера, `ffuf` для поиска скрытых путей, `sqlmap` для проверки SQL-инъекций на своих стендах.

## Что находят чаще всего
Ошибки контроля доступа (IDOR, доступ к админке), небезопасная конфигурация (открытые Swagger, отладочные эндпоинты, `.git` на сервере), XSS, слабые сессии, утечки информации в ошибках, SSRF, устаревшие компоненты, **ошибки бизнес-логики** (отрицательное количество товара, применение купона дважды, гонки при списании бонусов) — их сканеры не находят.

## Где тренироваться
**PortSwigger Web Security Academy** — лучшие бесплатные лабораторные по каждой уязвимости. Также OWASP Juice Shop (уязвимое приложение для практики), HackTheBox, TryHackMe, CTF-соревнования. Bug bounty — легальный поиск уязвимостей за вознаграждение по правилам программы.

Q: Какие этапы у тестирования на проникновение?
A: Согласование рамок и разрешение, разведка и построение карты приложения, поиск уязвимостей (сканеры и ручная проверка), подтверждение и эксплуатация в рамках, оценка риска и отчёт с рекомендациями, повторная проверка после исправлений.
