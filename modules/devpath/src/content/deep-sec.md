# @sec-mindset

## Глубже: моделирование угроз как процесс
**Когда**: при проектировании новой функции, изменении границ доверия (новая интеграция, публичный API), после инцидента. Лучше 30 минут на каждую заметную фичу, чем один огромный документ раз в год.

**Техники кроме STRIDE**: **attack trees** (цель атакующего → способы → подспособы), **LINDDUN** (угрозы приватности), **PASTA** (риск-ориентированный процесс), **kill chain** (этапы атаки: разведка → доступ → закрепление → действия).

**Оценка риска**: DREAD устарел; практичнее CVSS для уязвимостей и простая матрица вероятность × ущерб для угроз.

**Инструменты**: Microsoft Threat Modeling Tool, OWASP Threat Dragon, просто Miro/draw.io + таблица.

**Security requirements**: из модели угроз — конкретные требования в бэклог («все эндпоинты /admin требуют роль и MFA», «загрузка файлов ≤ 10 МБ, только PNG/JPEG»). **OWASP ASVS** — готовый каталог требований трёх уровней для проверки приложения.

**Assume breach**: проектируйте так, будто периметр уже пробит — сегментация, минимальные права, аудит, шифрование внутри.

# @sec-injection

## Глубже: неочевидные инъекции
**Second-order SQL injection**: безопасно сохранённые данные потом используются в динамическом SQL в другом месте (отчёт, хранимая процедура).

**Инъекция в имена**: динамические имена таблиц/колонок только через белый список; `QUOTENAME` в SQL Server как дополнительная мера.

**LINQ Dynamic / Expression parsing** из пользовательской строки (`System.Linq.Dynamic.Core`) — фактически выполнение кода; ограничивайте разрешённые операторы.

**Log injection / CRLF injection**: переводы строк в заголовках ответа или логах (подделка записей, HTTP response splitting) — Kestrel отклоняет CRLF в заголовках, структурные логи безопасны.

**CSV/Formula injection**: значение `=HYPERLINK(...)` в экспорте Excel выполнится у пользователя — экранировать ведущие `= + - @`.

**Header injection в почте**, **ReDoS** (катастрофический бэктрекинг регулярки), **XPath**, **ORM-специфичные** ловушки (сырые фрагменты в `OrderBy` строкой).

**Десериализация**: System.Text.Json безопасен по умолчанию; полиморфизм — только через `[JsonDerivedType]` с явным списком; Newtonsoft `TypeNameHandling` — только `None` для недоверенного входа.

# @sec-xss

## Глубже: CSP и современный фронтенд
**Строгая CSP** (strict CSP): `script-src 'nonce-{random}' 'strict-dynamic'; object-src 'none'; base-uri 'none'` — скрипты только с одноразовым nonce, загружаемые ими — разрешены. Nonce генерируется на каждый ответ (middleware + Razor tag helper).

**Report-only режим**: `Content-Security-Policy-Report-Only` + `report-to` — сначала собрать нарушения, потом включить.

**Trusted Types** — браузер запрещает опасные DOM-sink'и (`innerHTML`) без санитизированных объектов.

**DOM XSS в SPA**: React/Angular экранируют по умолчанию; опасны `dangerouslySetInnerHTML`, `bypassSecurityTrust*`, `href="javascript:..."` из пользовательских данных, `eval`, сторонние markdown-рендереры без санитайзера (DOMPurify).

**Изоляция пользовательского контента**: отдавать загруженные файлы и HTML с отдельного домена (usercontent), sandbox для iframe.

**Clickjacking**: `frame-ancestors 'none'`. **Cookie**: `__Host-` префикс (Secure, путь /, без Domain) — не перезаписываются поддоменами.

# @sec-authn

## Глубже: современная аутентификация
**Passkeys** (WebAuthn/FIDO2): пара ключей на устройстве, приватный ключ не покидает его, подпись привязана к домену — фишинг бесполезен; синхронизируются через iCloud/Google/менеджеры паролей. В .NET — библиотеки Fido2NetLib; ASP.NET Core Identity добавляет поддержку passkeys (.NET 10).

**Пароли по NIST SP 800-63B**: длина от 8 (лучше 15 для без-MFA), без обязательной периодической смены и «сложностных» правил, проверка по базам утечек, разрешать вставку из менеджера паролей.

**Защита от перебора**: прогрессивные задержки и блокировки по аккаунту и IP, CAPTCHA после неудач, уведомления о входе с нового устройства, риск-ориентированная аутентификация (новая страна → MFA).

**Сессии**: серверные сессии дают мгновенный отзыв; JWT — короткий срок + refresh с ротацией и детекцией повторного использования.

**Внешние провайдеры**: делегируйте аутентификацию проверенному IdP (Entra ID, Keycloak, Auth0) — меньше кода, больше функций (MFA, аудит, SSO).

**Account recovery** — самое слабое место: коды восстановления, повторная верификация, задержки при смене email/телефона.

# @sec-authz

## Глубже: авторизация в масштабе
**Внешние движки политик**: OPA (Rego), Cedar (AWS), OpenFGA/SpiceDB (ReBAC по модели Zanzibar) — политики отделены от кода, проверяются централизованно, аудитируются.

**Zanzibar-модель**: отношения `document:42#viewer@user:7`, наследование через связи (`folder` → `document`), проверка «может ли user:7 view document:42» — масштабируется на миллиарды связей (Google Drive, GitHub).

**Фильтрация списков**: проверять каждый объект по одному — медленно; нужны запросы «какие объекты доступны» (list objects) или фильтр в SQL.

**Row-Level Security** в PostgreSQL/SQL Server: политика в БД (`USING (tenant_id = current_setting('app.tenant')::uuid)`) — второй слой защиты мультиарендности.

**Принцип**: авторизация на **каждом** уровне доступа к данным (API, фоновые задачи, экспорт, поиск); поисковый индекс и кэш тоже должны учитывать права.

**Административные функции**: отдельные роли, MFA, just-in-time доступ (временное повышение прав), журнал всех действий, «четыре глаза» для опасных операций.

# @net-api-security

## Глубже: API под атакой
**OWASP API Top 10** на практике:
- **BOLA** — проверка владельца объекта;
- **Broken Authentication** — слабые токены, отсутствие rate limit на логин;
- **Broken Object Property Level Authorization** — mass assignment и отдача лишних полей (DTO на вход и выход);
- **Unrestricted Resource Consumption** — лимиты размера, пагинации, частоты, стоимости операций;
- **BFLA** — доступ к административным функциям по неочевидным URL;
- **Unrestricted Access to Sensitive Business Flows** — боты, скупающие товары: лимиты по бизнес-действиям;
- **SSRF**, **misconfiguration**, **improper inventory** (забытые старые версии API), **unsafe consumption** чужих API.

**Инвентаризация**: все API и версии в каталоге (OpenAPI), удаление старых, gateway как единая точка политик.

**Защита сервис-сервис**: mTLS + короткие токены с audience; не доверять заголовкам вроде `X-User-Id` от клиентов — только от своего gateway по защищённому каналу.

# @sec-data

## Глубже: шифрование и данные в .NET
**Envelope encryption**: данные шифруются ключом данных (DEK), DEK шифруется мастер-ключом (KEK) в KMS/HSM. Ротация KEK не требует перешифровки всех данных.

**Прикладное шифрование полей**: `AesGcm` с DEK на арендатора/запись, хранение nonce и тега; **Always Encrypted** в SQL Server — шифрование на клиенте, сервер БД не видит открытых данных; детерминированное шифрование позволяет поиск по равенству, но раскрывает одинаковые значения.

**Поиск по зашифрованному**: blind index — HMAC от нормализованного значения в отдельной колонке.

**Data Protection API**: purpose strings для изоляции (`CreateProtector("Orders.Tokens.v1")`), time-limited protector для одноразовых ссылок.

**Маскирование и минимизация**: DTO без лишних полей, маскирование в логах (Serilog destructuring policies, `[LogMasked]`), разные уровни доступа к ПДн для сотрудников.

**Удаление**: soft delete не удаляет ПДн — для «права на забвение» нужна анонимизация/crypto-shredding и удаление из резервных копий по сроку.

**Классификация данных**: публичные, внутренние, конфиденциальные, ПДн, особые категории — разные требования к хранению и доступу.

# @net-crypto

## Глубже: криптография без ошибок
**Выбор алгоритмов** (2025+): симметрично — AES-256-GCM или ChaCha20-Poly1305; хэш — SHA-256/SHA-512 (SHA-1 и MD5 — нет); пароли — Argon2id; подписи — Ed25519 или ECDSA P-256, RSA ≥ 3072 с PSS; обмен ключами — X25519. **Постквантовая криптография**: ML-KEM (Kyber) и ML-DSA уже в TLS браузеров (гибридные схемы); в .NET 10 появились API ML-KEM/ML-DSA.

**Частые ошибки**: повтор nonce в GCM, ECB, самодельные схемы «зашифровать и подписать», сравнение MAC обычным `==` (утечка по времени — `CryptographicOperations.FixedTimeEquals`), `Random` для ключей, хранение ключа рядом с данными, собственный протокол вместо TLS.

**Ключи**: генерация `RandomNumberGenerator`, хранение в KMS/HSM, `CryptographicOperations.ZeroMemory` для очистки из памяти, ротация, разделение по назначению.

**JWT-криптография**: `alg: none`, путаница RS256/HS256 (публичный ключ как HMAC-секрет) — фиксируйте ожидаемый алгоритм.

**Высокоуровневые API**: Data Protection, libsodium (NSec) — меньше решений, меньше ошибок.

## Глубже: обработка файлов безопасно
**Обработчики форматов — поверхность атаки**: библиотеки изображений, PDF, Office, архивов имеют уязвимости (ImageTragick). Обрабатывайте в изолированном воркере/контейнере с лимитами ресурсов и без сети; держите библиотеки обновлёнными.

**Документы**: XXE в DOCX/XLSX (это ZIP с XML), макросы — конвертировать или запрещать.

**SSRF глубже**: проверка после DNS-резолва с фиксацией адреса для соединения (иначе DNS rebinding), запрет редиректов или проверка каждого, блок IPv6-эквивалентов и форм записи (`0x7f000001`, `127.1`), egress-прокси с белым списком; для метаданных облака — IMDSv2 (токен), сетевые политики.

**Загрузка напрямую в хранилище**: pre-signed URL с ограничением типа и размера, затем асинхронная проверка (антивирус, тип) и только потом публикация.

# @sec-supply

## Глубже: реакция на уязвимость в зависимости
**Сценарий «вышла критическая CVE»**:
1. SBOM/инвентаризация — где используется (включая транзитивные и образы);
2. оценка — достижим ли уязвимый код, есть ли эксплойт (KEV-каталог, EPSS);
3. временные меры — WAF-правило, отключение функции;
4. обновление или патч, пересборка, выкатка через быстрый конвейер;
5. проверка и разбор.

**Транзитивные зависимости**: `dotnet list package --include-transitive`, явное закрепление безопасной версии транзитивного пакета (Central Package Management с `CentralPackageTransitivePinningEnabled`).

**Проверка новых пакетов**: OpenSSF Scorecard, возраст и активность, число мейнтейнеров, подписи, отсутствие install-скриптов (для npm), реальная необходимость.

**Внутренний фид**: прокси-кэш пакетов (Azure Artifacts, Nexus, Artifactory) — контроль и воспроизводимость, защита от удаления пакетов из публичного реестра.

**Компрометация мейнтейнера** (как xz): поведенческий анализ, задержка обновлений на несколько дней для новых версий (Renovate `minimumReleaseAge`).

# @sec-logging

## Глубже: обнаружение и реагирование
**Что делать с логами безопасности**: собирать централизованно (SIEM: Microsoft Sentinel, Elastic Security, Wazuh), нормализовать, коррелировать события разных систем, строить детекции.

**Примеры детекций**: 50 неудачных входов за минуту на один аккаунт или с одного IP; вход с двух стран за час; массовая выгрузка данных; создание администратора; доступ к чужим объектам (всплеск 403/404 на /api/orders/{id}); отключение аудита.

**Аудит-журнал в .NET**: отдельный поток событий (кто, что, когда, над чем, откуда, результат), запись в append-only хранилище (отдельная БД с правами только на INSERT, WORM-хранилище, внешний сервис), цифровая цепочка хэшей для обнаружения подделки.

**Реагирование**: playbooks (что делать при компрометации учётки, утечке ключа, вредоносном пакете), учения, контакты, требования законов по уведомлению (152-ФЗ — уведомление РКН об утечке в течение суток), сохранение улик.

**Метрики**: время обнаружения (MTTD) и реагирования (MTTR).

## Глубже: проверка защищённости на практике
**Автоматизируйте чек-лист**:

**Kestrel hardening**: `MaxRequestBodySize`, `MaxRequestHeadersTotalSize`, `RequestHeadersTimeout`, `MinRequestBodyDataRate` (защита от slowloris), `AddServerHeader = false`.

**Антифорджери и SPA**: для cookie-аутентификации SPA — antiforgery-токен в заголовке (`X-XSRF-TOKEN`) + SameSite.

**Безопасные умолчания Minimal API**: `RequireAuthorization()` на группах, `DisableAntiforgery()` только осознанно, `AllowAnonymous()` — редко и явно.

**Обновления .NET**: патчи безопасности выходят во второй вторник месяца — автоматическое обновление базовых образов.

# @sec-pentest

## Глубже: учимся атаковать правильно
**Методологии**: OWASP Web Security Testing Guide (WSTG) — полный перечень проверок по категориям; PTES — этапы пентеста.

**Burp Suite на практике**: Proxy (перехват), Repeater (ручные эксперименты с запросом), Intruder (перебор параметров), Comparer, расширения (Autorize — автоматическая проверка авторизации: повторяет запросы от имени другого пользователя).

**Что проверять в своём API в первую очередь**: смена id в каждом запросе (IDOR), доступ к админ-эндпоинтам обычным пользователем, массовое присвоение полей, лимиты, гонки (одновременные запросы на списание бонусов — Burp «send group in parallel»), ошибки с деталями, JWT (alg, срок, подпись).

**Race conditions** — недооценённый класс: «использовать купон один раз» ломается 20 параллельными запросами. Защита — атомарные операции в БД, уникальные ограничения, блокировки.

**Практика**: PortSwigger Web Security Academy (бесплатно, с лабораториями по каждой теме), OWASP Juice Shop локально, HackTheBox/TryHackMe; сертификации — OSCP, BSCP (Burp Suite Certified Practitioner).
