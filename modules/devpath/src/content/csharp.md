# @csharp-types

## Два мира типов
В C# все типы делятся на **значимые** (`struct`, `enum`, примитивы вроде `int`, `double`, `bool`) и **ссылочные** (`class`, `interface`, `delegate`, `string`, массивы).

Главное отличие — **семантика присваивания**, а не место хранения:
- переменная значимого типа **содержит сами данные**; присваивание копирует их целиком;
- переменная ссылочного типа содержит **ссылку** на объект в управляемой куче; присваивание копирует ссылку, и обе переменные смотрят на один объект.

```csharp
struct Point { public int X; }
class Box { public int X; }

var p1 = new Point { X = 1 }; var p2 = p1; p2.X = 42;   // p1.X == 1
var b1 = new Box { X = 1 };   var b2 = b1; b2.X = 42;   // b1.X == 42
```

## «Struct живёт на стеке» — миф
Где лежат данные — деталь реализации. Локальная `int` обычно в стеке или регистре, но **поле `int` внутри класса лежит в куче** вместе с объектом, элемент `int[]` — тоже в куче, а локальная переменная, захваченная лямбдой или живущая в async-методе, переезжает в сгенерированный класс, то есть в кучу.

Правильная формулировка на собеседовании: *значимые типы копируются по значению и хранятся «inline» там, где объявлены; ссылочные — всегда в куче, а переменная хранит ссылку*.

## Boxing и unboxing
**Упаковка (boxing)** — превращение значения в объект кучи: CLR выделяет память, копирует значение, возвращает ссылку. Распаковка — обратное копирование с проверкой типа.

Где boxing прячется:
- `object o = 42;` и коллекции `ArrayList`, `Hashtable`;
- вызов метода интерфейса на struct через переменную типа интерфейса: `IComparable c = 5;`;
- `params object[]`, старые `string.Format`, `Console.WriteLine("{0}", x)`;
- `Equals(object)` у struct без переопределения — ещё и медленное сравнение через рефлексию.

Лечение: generic-методы (`void M<T>(T x) where T : IComparable<T>`), `IEquatable<T>`, интерполяция строк (она использует обработчики без упаковки).

## Современные struct
- `readonly struct` — все поля неизменяемы, компилятор не делает защитных копий при вызовах через `in`/`readonly`-поля.
- `ref struct` (например, `Span<T>`) — **никогда не попадёт в кучу**: нельзя боксить, хранить в полях класса, захватывать в лямбды.
- `record struct` — значимый тип с генерацией `Equals`, `GetHashCode`, `ToString`.

Совет: делайте struct маленькими (до ~16–24 байт) и неизменяемыми. Большая изменяемая структура — источник багов «я поменял копию, а не оригинал».

## Равенство
- `==` для классов по умолчанию сравнивает **ссылки** (кроме `string`, у которого перегружен оператор).
- `Equals` можно переопределить для сравнения по значению; тогда **обязательно** переопределяют `GetHashCode`: равные объекты обязаны иметь равный хэш, иначе `Dictionary` и `HashSet` сломаются.
- `record` делает value-equality автоматически.

Q: Чем значимые типы отличаются от ссылочных — сформулируй как на собеседовании.
A: Значимые копируются по значению и хранятся inline там, где объявлены (в стеке, в поле объекта, в элементе массива). Ссылочные всегда живут в куче, переменная хранит ссылку, присваивание копирует ссылку. Место хранения — деталь реализации, важна семантика копирования.

# @csharp-oop

## Три кита и их цена
**Инкапсуляция** — прячем состояние и даём операции над ним. **Наследование** — переиспользуем реализацию. **Полиморфизм** — вызываем метод, не зная конкретного типа.

В C# полиморфизм подтипов работает через `virtual`/`override`: вызов идёт через таблицу виртуальных методов (vtable) — это небольшая косвенность, которую JIT часто убирает (девиртуализация), если класс `sealed` или тип известен точно.

## override, new, sealed, abstract
```csharp
class Animal { public virtual string Say() => "..."; public string Name() => "animal"; }
class Dog : Animal { public override string Say() => "Гав"; public new string Name() => "dog"; }

Animal a = new Dog();
a.Say();   // "Гав"   — override: решает тип ОБЪЕКТА
a.Name();  // "animal" — new: решает тип ПЕРЕМЕННОЙ
```
- `abstract` — метод без реализации, класс нельзя создать.
- `sealed` на классе запрещает наследование (и помогает JIT), на методе — дальнейший override.
- Совет из практики: делайте классы `sealed` по умолчанию, открывайте для наследования осознанно.

## Интерфейсы сегодня
Интерфейс — контракт без состояния. Современный C# позволяет:
- **default interface methods** — реализацию по умолчанию (для эволюции API без поломки реализаций);
- **static abstract members** — статические члены в контракте (основа generic math: `T.Zero`, `T operator +`).

Абстрактный класс нужен, когда есть общее **состояние** или защищённая логика; интерфейс — когда нужен только контракт и множественная реализация.

## Композиция вместо наследования
Глубокие иерархии хрупкие: изменение базового класса ломает наследников (проблема «хрупкого базового класса»). Композиция — объект **содержит** другие объекты и делегирует им работу:

```csharp
public sealed class CachedRepository(IRepository inner, IMemoryCache cache) : IRepository
{
    public Task<User?> Get(int id) =>
        cache.GetOrCreateAsync(id, _ => inner.Get(id));
}
```
Это паттерн «Декоратор» — поведение добавляется без наследования.

## Records, init, required
- `record` — ссылочный тип с равенством по значению, `ToString`, деконструкцией и `with`: `var p2 = p1 with { Age = 30 };`.
- `init` — свойство задаётся только при создании.
- `required` — компилятор заставит задать свойство в инициализаторе.

Q: Чем отличаются override и new?
A: override заменяет виртуальный метод — вызывается реализация по фактическому типу объекта. new скрывает метод базового класса — вызываемая версия зависит от статического типа переменной.

# @csharp-exceptions

## Как работают исключения
Исключение — объект, производный от `Exception`. При `throw` CLR ищет подходящий `catch` вверх по стеку вызовов, разматывая стек и выполняя блоки `finally`. Это **дорого**: сбор стек-трейса и размотка стоят микросекунды, поэтому исключения — для исключительных ситуаций, а не для обычного потока управления.

```csharp
try { Process(); }
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.NotFound) { /* фильтр */ }
catch (IOException) { throw; }       // пробросить, сохранив стек
finally { Cleanup(); }
```

## throw vs throw ex
- `throw;` — пробрасывает текущее исключение **с исходным стек-трейсом**.
- `throw ex;` — **обрезает** стек-трейс до текущего места. Почти всегда ошибка.
- Нужно обернуть — `throw new DomainException("…", ex);` (inner exception сохраняет причину).

**Фильтры `when`** выполняются до размотки стека — удобно для логирования без поимки: `catch (Exception ex) when (Log(ex)) { }` где `Log` возвращает `false`.

## Свои исключения и Result
Своё исключение имеет смысл, если вызывающий код будет его **различать** (`OrderNotFoundException`). Иначе хватит стандартных: `ArgumentException`, `InvalidOperationException`, `NotSupportedException`.

Альтернатива для ожидаемых ошибок бизнес-логики — **Result-паттерн**: метод возвращает `Result<T>` (успех или ошибка), и компилятор заставляет обработать оба варианта. Правило: ожидаемое (валидация, «не найдено») → Result; неожиданное (сеть упала, баг) → исключение.

## Исключения и асинхронность
- Исключение в `async Task` сохраняется в задаче и выбрасывается при `await`.
- `Task.WhenAll` при `await` бросает **первое** исключение; все остальные — в `task.Exception.InnerExceptions` (`AggregateException`).
- `async void` — исключение уходит в контекст синхронизации и может уронить процесс.
- Глобальная обработка в ASP.NET Core — `UseExceptionHandler` / `IExceptionHandler` → ответ в формате ProblemDetails.

Q: Когда исключение, а когда Result-паттерн?
A: Исключения — для неожиданных сбоев (инфраструктура, баги, нарушение контракта). Result — для ожидаемых бизнес-исходов (валидация, «не найдено», «недостаточно средств»), которые вызывающий обязан обработать. Исключения дорогие и неявные в сигнатуре.

Q: Что такое фильтр исключений и чем он лучше if внутри catch?
A: catch (...) when (условие) — условие проверяется до размотки стека, поэтому неподходящее исключение не ловится и стек сохраняется; удобно для логирования и выборочной обработки.

# @csharp-generics

## Зачем обобщения
Generics дают типобезопасный код без копипасты и без упаковки: `List<int>` хранит `int` напрямую, а не `object`.

**Ограничения** (`where`) говорят компилятору, что можно делать с `T`:
```csharp
T Max<T>(T a, T b) where T : IComparable<T> => a.CompareTo(b) >= 0 ? a : b;
```
Основные: `class`, `struct`, `notnull`, `unmanaged`, `new()`, базовый класс, интерфейс.

## Как это устроено в CLR
В отличие от Java (стирание типов), в .NET generics **реальные** (reified): тип `T` известен в рантайме, `typeof(T)` работает.
- Для каждого **значимого** типа JIT генерирует отдельный специализированный код (`List<int>` и `List<double>` — разные машинные коды) → максимальная скорость.
- Для всех **ссылочных** типов используется одна общая реализация (указатели одного размера).

Следствие: статическое поле в `Cache<T>` — **своё для каждого T**. Это используют для дешёвых per-type кэшей.

## Ковариантность и контравариантность
Работает только для **интерфейсов и делегатов** и только для ссылочных типов:
- `out T` (ковариантность) — `T` только возвращается: `IEnumerable<string>` можно присвоить в `IEnumerable<object>`.
- `in T` (контравариантность) — `T` только принимается: `Action<object>` можно присвоить в `Action<string>`.

`List<T>` инвариантен: если бы `List<string>` был `List<object>`, в него можно было бы положить `int`.

## Generic math
С C# 11 интерфейсы могут содержать `static abstract` члены. Это позволило написать обобщённую арифметику:
```csharp
T Sum<T>(IEnumerable<T> xs) where T : INumber<T>
{
    var s = T.Zero;
    foreach (var x in xs) s += x;
    return s;
}
```

Q: Что значат in и out у параметров типа?
A: out — ковариантность: T только в выходных позициях, можно подставить более производный тип (IEnumerable<string> → IEnumerable<object>). in — контравариантность: T только во входных позициях (Action<object> → Action<string>). Только интерфейсы/делегаты и ссылочные типы.

Q: Чем generics в .NET отличаются от Java?
A: В .NET они реифицированы: информация о T есть в рантайме, для value types генерируется специализированный код без упаковки. В Java — стирание типов, все T становятся Object.

# @csharp-delegates

## Делегаты
Делегат — типобезопасная ссылка на метод (объект с `Target` и указателем на метод). Встроенные: `Action<...>` (без результата), `Func<..., TResult>`, `Predicate<T>`.

Делегаты **мультикаст**: `a += b` создаёт новый делегат со списком вызова. При вызове выполняются все, возвращается результат последнего.

## События
`event` — это делегат, который снаружи можно только `+=` и `-=`, а вызвать — только владельцу.

**Утечка памяти через события** — классика: издатель (долгоживущий) держит делегат → делегат держит подписчика (`Target`) → подписчик не собирается GC, пока не отпишется.
```csharp
service.Changed += OnChanged;   // подписка в конструкторе окна
// ... окно закрыли, но не отписались → окно живёт вечно
```
Решения: отписка в `Dispose`, слабые события, `IObservable` с `IDisposable`-подпиской.

## Замыкания
Лямбда, использующая внешнюю переменную, **захватывает переменную, а не значение**. Компилятор создаёт класс-замыкание (display class), куда переносит переменную — это аллокация.

```csharp
var actions = new List<Action>();
for (int i = 0; i < 3; i++) actions.Add(() => Console.Write(i));
actions.ForEach(a => a());   // 333 — одна переменная i на весь цикл
```
В `foreach` с C# 5 переменная новая на каждой итерации — там выведется 012.

`static` лямбды запрещают захват — компилятор гарантирует отсутствие аллокации замыкания.

## Делегат или Expression?
`Func<User, bool>` — скомпилированный код. `Expression<Func<User, bool>>` — **дерево выражения**: данные о коде, которые можно анализировать и транслировать (EF Core превращает их в SQL). Отсюда разница между `IEnumerable.Where` и `IQueryable.Where`.

Q: Что компилятор делает с захваченной переменной в лямбде?
A: Переносит её в поле сгенерированного класса-замыкания (display class). Лямбда становится методом этого класса. Переменная живёт в куче, пока жив делегат; это аллокация и возможная причина неожиданного поведения.

Q: Чем Expression<Func<T,bool>> отличается от Func<T,bool>?
A: Func — исполняемый код. Expression — дерево выражения, описание кода как данных; его можно разобрать и перевести, например в SQL (IQueryable в EF Core), или скомпилировать в делегат.

# @csharp-linq

## Итераторы и yield
`yield return` превращает метод в **машину состояний**, реализующую `IEnumerable<T>`. Код выполняется порциями — по одной на каждый `MoveNext()`.

```csharp
IEnumerable<int> Numbers() {
    Console.WriteLine("старт");
    yield return 1;
    yield return 2;
}
var q = Numbers();        // ничего не выведено!
foreach (var n in q) { }  // «старт» — только сейчас
```

## Отложенное выполнение
Большинство операторов LINQ (`Where`, `Select`, `OrderBy`) **ленивые**: они строят конвейер, а выполнение происходит при перечислении (`foreach`, `ToList`, `Count`, `First`).

Ловушки:
- **многократное перечисление** — каждый `foreach` выполняет запрос заново (для EF — новый SQL-запрос, для генератора — повторная работа). Решение — материализовать через `ToList()`/`ToArray()`;
- **изменение источника** между объявлением запроса и перечислением меняет результат;
- исключения вылетают при перечислении, а не на строке с `Where`.

## IEnumerable vs IQueryable
- `IEnumerable<T>.Where(Func<T,bool>)` — фильтрация **в памяти** приложения.
- `IQueryable<T>.Where(Expression<...>)` — выражение передаётся провайдеру (EF Core) и превращается в SQL.

Классическая ошибка: `db.Users.AsEnumerable().Where(u => u.Age > 18)` — выгружает всю таблицу и фильтрует в памяти.

## Цена LINQ
LINQ выделяет итераторы и делегаты. В горячем коде (миллионы вызовов) простой `for` может быть в разы быстрее. В .NET 7–9 LINQ сильно оптимизирован (векторизованные `Sum`/`Min`/`Max`, специализации для массивов), но правило «измеряй BenchmarkDotNet» остаётся.

Полезные операторы: `SelectMany` (развернуть вложенные коллекции), `GroupBy`, `ToLookup`, `Chunk`, `DistinctBy`, `MaxBy`, `Zip`, `Aggregate`.

Q: Что такое отложенное выполнение и какие у него ловушки?
A: Операторы LINQ строят конвейер, а данные обрабатываются при перечислении. Ловушки: многократное перечисление (повторная работа/запросы), изменение источника до перечисления, исключения в месте перечисления.

Q: Как компилятор реализует yield return?
A: Генерирует класс — машину состояний, реализующую IEnumerable/IEnumerator. Локальные переменные становятся полями, MoveNext выполняет код до следующего yield и запоминает состояние.

# @csharp-collections

## List и Dictionary изнутри
- `List<T>` — обёртка над массивом. Добавление — амортизированно O(1): при заполнении создаётся массив вдвое больше и данные копируются. Вставка/удаление в середину — O(n). Если размер известен — задавайте `capacity`.
- `Dictionary<TKey,TValue>` — хэш-таблица с корзинами (buckets) и массивом записей. Поиск в среднем O(1), но деградирует при плохом `GetHashCode` (много коллизий). Ключ нельзя менять после вставки, если это влияет на хэш.
- `HashSet<T>` — то же, но без значений.

## Что выбрать
| Задача | Коллекция |
|---|---|
| по индексу, порядок вставки | `List<T>` |
| поиск по ключу | `Dictionary` |
| уникальность, пересечения | `HashSet<T>` |
| FIFO / LIFO | `Queue<T>` / `Stack<T>` |
| приоритет | `PriorityQueue<TElement,TPriority>` |
| отсортировано по ключу | `SortedDictionary` (дерево, O(log n)) |

## Immutable и Frozen
- `ImmutableList`, `ImmutableDictionary` — неизменяемые, изменение возвращает новую коллекцию с разделением структуры. Удобны для многопоточности, но медленнее.
- `FrozenDictionary`/`FrozenSet` (.NET 8) — строятся один раз дорого, зато **читаются быстрее** обычных. Идеальны для справочников и конфигурации.

## Потокобезопасные
Обычные коллекции не потокобезопасны при записи. Для конкурентного доступа — `ConcurrentDictionary` (`GetOrAdd`, `AddOrUpdate`; фабрика может вызваться несколько раз!), `ConcurrentQueue`, `Channel<T>` для producer/consumer.

Q: Почему плохой GetHashCode убивает производительность Dictionary?
A: Ключи с одинаковым хэшем попадают в одну корзину, поиск превращается в линейный проход по цепочке — O(n) вместо O(1).

Q: Когда ImmutableDictionary, а когда FrozenDictionary?
A: Immutable — когда данные меняются, но нужна неизменяемость снимков (многопоточность, история состояний). Frozen — когда данные построены один раз и только читаются: он быстрее на чтение, но создаётся дорого.

# @csharp-strings

## Неизменяемость
`string` в .NET — неизменяемый ссылочный тип с UTF-16 внутри. Любое «изменение» создаёт новую строку. Поэтому конкатенация в цикле — O(n²) по памяти:
```csharp
var s = "";
foreach (var x in items) s += x;         // плохо: новая строка на каждой итерации
var sb = new StringBuilder();
foreach (var x in items) sb.Append(x);   // хорошо
```
Литералы **интернируются** — одинаковые литералы указывают на один объект.

## Сравнение строк
По умолчанию `string.Equals` и `==` сравнивают **порядково** (ordinal, по кодам символов). А вот `StartsWith(string)`, `IndexOf(string)`, `CompareTo`, `ToUpper()` без параметров учитывают **текущую культуру** — это медленнее и даёт сюрпризы (знаменитая турецкая «i»).

Правило: для идентификаторов, ключей, протоколов — `StringComparison.Ordinal` / `OrdinalIgnoreCase`; для текста, который видит пользователь, — культура.

## Кодировки
- Внутри .NET строка — UTF-16 (`char` = 2 байта; эмодзи — это 2 `char`, суррогатная пара).
- В файлах и сети почти всегда UTF-8. `Encoding.UTF8.GetBytes` / `GetString`.
- `s.Length` — число `char`, а не видимых символов. Для «букв» — `StringInfo` / `Rune`.

## Современные инструменты
- интерполяция `$"{a} {b}"` компилируется в `DefaultInterpolatedStringHandler` — без лишних аллокаций и упаковки;
- `string.Create`, `ReadOnlySpan<char>` для разбора без подстрок;
- `[GeneratedRegex]` — регулярка компилируется на этапе сборки; всегда задавайте таймаут для пользовательского ввода (защита от ReDoS).

# @csharp-memory

## Как устроена управляемая куча
.NET использует **сборщик мусора с поколениями**. Идея: большинство объектов умирают молодыми.
- **Gen0** — новые объекты; собирается часто и быстро.
- **Gen1** — буфер между молодыми и старыми.
- **Gen2** — долгоживущие объекты; полная сборка дорогая.
- **LOH** (Large Object Heap) — объекты ≥ 85 000 байт; собирается с Gen2, по умолчанию не компактируется (фрагментация).
- **POH** (Pinned Object Heap) — для закреплённых объектов.

Выделение памяти в .NET очень дешёвое (сдвиг указателя). Дорого не выделять, а **собирать** и продвигать объекты в старшие поколения.

## Как работает сборка
1. Приостановка потоков (для большей части работы).
2. **Маркировка**: от корней (локальные переменные, статические поля, хэндлы) обходятся достижимые объекты.
3. **Очистка/сжатие**: мёртвое удаляется, живое сдвигается, ссылки обновляются.

Режимы: **Workstation** (клиентские приложения) и **Server** (отдельная куча и поток GC на ядро, выше пропускная способность — по умолчанию в ASP.NET Core). **Background GC** выполняет Gen2 параллельно с работой приложения. С .NET 8 есть **DATAS** — адаптивный размер куч для контейнеров.

## Dispose и финализаторы
GC освобождает только память. Файлы, сокеты, соединения с БД — **неуправляемые ресурсы**, их освобождают детерминированно через `IDisposable`:
```csharp
await using var conn = new NpgsqlConnection(cs);
using var stream = File.OpenRead(path);
```
Финализатор (`~Class()`) — страховка на случай, если Dispose забыли. Объект с финализатором переживает лишнюю сборку (попадает в очередь финализации) — поэтому в `Dispose` вызывают `GC.SuppressFinalize(this)`. Сегодня финализаторы почти не пишут — используют `SafeHandle`.

## Утечки в управляемом коде
Утечка в .NET — это объект, который **остаётся достижимым**:
- статические коллекции-кэши без ограничений;
- подписки на события без отписки;
- замыкания, захватившие большой объект;
- `Timer`, который держит ссылку на колбэк.

Диагностика: `dotnet-counters monitor` (размер куч, частота GC), `dotnet-gcdump` / `dotnet-dump` + анализ в Visual Studio или PerfView.

# @csharp-span

## Span<T> и Memory<T>
`Span<T>` — «окно» на непрерывный участок памяти: массив, часть массива, стек (`stackalloc`), неуправляемую память. Срез — O(1) и **без копирования и аллокаций**.
```csharp
ReadOnlySpan<char> line = "2026-09-28;42;ok";
int sep = line.IndexOf(';');
var date = DateOnly.Parse(line[..sep]);      // без Substring
```
`Span<T>` — `ref struct`, поэтому живёт только на стеке: нельзя хранить в полях класса, использовать через await, захватывать в лямбды. Для этого есть `Memory<T>` — обычная структура, из которой можно получить `Span`.

## Пулы
- `ArrayPool<T>.Shared.Rent(n)` — взять массив из пула (может быть **больше** n!), `Return` — вернуть. Снижает нагрузку на GC при частых временных буферах.
- `stackalloc` — буфер на стеке, только для маленьких размеров (сотни байт — единицы КБ), иначе StackOverflow.

```csharp
byte[] buf = ArrayPool<byte>.Shared.Rent(4096);
```

Kestrel, System.Text.Json, парсеры протоколов — всё на Span и пулах. Для потоковой обработки сетевых данных — `System.IO.Pipelines` (буферы из пула, backpressure).

Важно: не делайте этого «везде». Начинайте с читаемого кода, измеряйте, оптимизируйте горячие места.

# @csharp-async

## Зачем асинхронность
Асинхронность — не про параллелизм, а про то, чтобы **не занимать поток во время ожидания** (сеть, диск, БД). Пока запрос к БД идёт 50 мс, поток пула обслуживает другие запросы. Это даёт масштабируемость сервера.

```csharp
public async Task<User?> GetUserAsync(int id, CancellationToken ct)
{
    var user = await _db.Users.FindAsync([id], ct);   // поток свободен во время запроса
    return user;
}
```

## Что делает компилятор
`async`-метод превращается в **машину состояний** (struct, реализующий `IAsyncStateMachine`):
1. Код выполняется синхронно до первого `await` незавершённой задачи.
2. На `await` метод регистрирует продолжение и **возвращает незавершённую Task** вызывающему.
3. Когда операция завершается, продолжение выполняется (на пуле потоков или в захваченном контексте), и метод идёт до следующего await.

Если задача уже завершена (например, данные из кэша), `await` продолжает синхронно — без переключений.

## Контекст синхронизации и deadlock
В UI-приложениях и старом ASP.NET есть `SynchronizationContext`: продолжение после `await` возвращается в «тот же» поток. Отсюда классический **deadlock**:
```csharp
var data = GetDataAsync().Result;   // UI-поток блокируется и ждёт задачу,
                                    // а задача ждёт UI-поток для продолжения
```
В ASP.NET Core контекста нет, но `.Result`/`.Wait()` всё равно зло: блокируют поток пула → **thread pool starvation** под нагрузкой.

`ConfigureAwait(false)` — «продолжай на любом потоке». Нужен в **библиотеках**; в коде приложений ASP.NET Core ни на что не влияет.

## Task vs ValueTask
`ValueTask<T>` — структура, позволяющая вернуть результат без аллокации Task, когда метод часто завершается синхронно (кэш, буфер). Ограничения: нельзя await-ить дважды, нельзя await-ить параллельно, нельзя `.Result` до завершения. По умолчанию — `Task`.

## Правила хорошего async
- async до конца («async all the way»), никаких `.Result`.
- Никаких `async void` (кроме обработчиков событий).
- Принимайте и прокидывайте `CancellationToken`.
- Параллельные независимые операции — `Task.WhenAll`, а не последовательные await.
- `IAsyncEnumerable<T>` + `await foreach` — для потоковой выдачи данных.

# @csharp-threading

## Потоки и пул
Создавать `new Thread` почти никогда не нужно. Работу отдают **пулу потоков** через `Task.Run` (CPU-работа) или асинхронные API (I/O). Пул сам регулирует количество потоков (алгоритм hill climbing), но добавляет их **медленно** — поэтому блокировки потоков (`.Result`, `Thread.Sleep`) так вредны.

Для долгой блокирующей работы — `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)` (отдельный поток).

## Примитивы синхронизации
| Примитив | Когда |
|---|---|
| `lock` (Monitor) | короткая критическая секция, синхронный код |
| `SemaphoreSlim` | ограничить параллелизм, **async-совместимый** (`WaitAsync`) |
| `ReaderWriterLockSlim` | много читателей, редкие писатели |
| `Interlocked` | атомарные операции над числами/ссылками без блокировок |
| `System.Threading.Lock` (.NET 9) | новый тип для lock, быстрее |

Внутри `lock` нельзя `await` — компилятор запретит. Для асинхронного кода — `SemaphoreSlim(1,1)`.

## Модель памяти и гонки
Без синхронизации компилятор и процессор могут переставлять чтения/записи, а ядра — видеть устаревшие значения из кэша. `count++` — это три операции (прочитать, увеличить, записать); два потока могут потерять инкремент.

```csharp
Interlocked.Increment(ref _count);   // атомарно
```
`volatile` гарантирует видимость и запрещает некоторые перестановки, но **не делает** составные операции атомарными.

## Дедлоки
Deadlock возникает, когда потоки ждут друг друга по кругу. Условия Коффмана: взаимное исключение, удержание и ожидание, нет вытеснения, циклическое ожидание. Лечение — всегда брать блокировки **в одном порядке**, держать их коротко, использовать таймауты.

## Параллельная обработка
- `Parallel.ForEach` / `Parallel.ForEachAsync` (с `MaxDegreeOfParallelism`) — обработка коллекции.
- PLINQ — `.AsParallel()` для CPU-bound запросов.
- `Channel<T>` — асинхронная очередь producer/consumer с ограничением размера (backpressure).

A: Monitor привязан к потоку-владельцу, а продолжение после await может выполниться на другом потоке, и отпустить блокировку будет некому. Используют SemaphoreSlim(1,1) с WaitAsync и Release в finally.

# @csharp-reflection

## Рефлексия
Рефлексия позволяет в рантайме читать метаданные типов и вызывать члены: `typeof(T).GetProperties()`, `Activator.CreateInstance`, `MethodInfo.Invoke`. На ней работают сериализаторы, DI-контейнеры, ORM, фреймворки тестирования.

Цена: вызов через `Invoke` в десятки раз медленнее прямого; поиск членов тоже дорог. Поэтому результаты рефлексии **кэшируют**, а горячие вызовы компилируют в делегаты (`Expression.Compile`, `CreateDelegate`) — или вообще уходят от рефлексии к генерации кода.

## Атрибуты
Атрибут — метаданные на типе/члене: `[Required]`, `[JsonPropertyName("id")]`, `[Authorize]`. Сами по себе ничего не делают — их читает какой-то код (фреймворк или ваш) через рефлексию или генератор.

## Source Generators
**Генераторы исходного кода** запускаются во время компиляции (Roslyn), анализируют ваш код и **дописывают новый C#**. Преимущества: нет рефлексии в рантайме, быстрый старт, совместимость с AOT, ошибки видны при сборке.

Примеры в .NET: `System.Text.Json` (`JsonSerializerContext`), `[LoggerMessage]`, `[GeneratedRegex]`, конфигурационный биндинг, Minimal API (Request Delegate Generator). Сторонние: Mapperly, Refit.

Пишите **incremental** генераторы (`IIncrementalGenerator`) — они не тормозят IDE.

## Native AOT и trimming
Native AOT компилирует приложение в нативный код заранее: быстрый старт, меньше памяти, нет JIT. Цена — ограничения:
- нельзя генерировать код в рантайме (`Reflection.Emit`);
- тримминг удаляет неиспользуемый код, и рефлексия по строковым именам может не найти удалённое;
- нужны аннотации `[DynamicallyAccessedMembers]` и source generators вместо рефлексии.

# @csharp-modern

## Pattern matching
```csharp
string Describe(object o) => o switch
{
    int n when n < 0          => "отрицательное",
    int or long               => "целое",
    string { Length: 0 }      => "пустая строка",
    Point(0, 0)               => "начало координат",   // позиционный
    int[] [1, .., var last]   => $"массив, последний {last}", // list pattern
    null                      => "null",
    _                         => "что-то"
};
```
Виды: type, property (`{ Length: > 5 }`), relational (`> 0 and < 10`), logical (`and`, `or`, `not`), positional, list patterns.

## Короче и безопаснее
- **primary constructors** для классов: `class Service(ILogger<Service> log, IRepo repo) { ... }` — параметры доступны во всём классе (но это не поля readonly!);
- **collection expressions**: `int[] a = [1, 2, 3]; List<int> b = [..a, 4];`;
- **raw string literals**: `"""{ "json": "без экранирования" }"""`;
- **required** члены, `init`, file-scoped namespace, global using;
- **nullable reference types** — `string?` и предупреждения компилятора о возможном null.

## C# 13–14
- `params` для любых коллекций (`params ReadOnlySpan<T>`) — без аллокации массива;
- новый тип `System.Threading.Lock`;
- ключевое слово `field` в свойствах — доступ к автоматическому полю: `public string Name { get; set => field = value.Trim(); }`;
- **extension members** — расширяющие свойства и статические члены в блоках `extension`.

# @csharp-runtime

## Путь кода
C# → компилятор Roslyn → **IL** (промежуточный язык) в сборке → при запуске **JIT** компилирует IL в машинный код для конкретного процессора → выполнение.

Посмотреть, во что превращается ваш код, можно на **sharplab.io**: C# → IL → ассемблер.

## Tiered compilation и PGO
- **Tier 0** — быстрая компиляция без оптимизаций (быстрый старт).
- Горячие методы (вызваны 30+ раз / циклы — через OSR) перекомпилируются в **Tier 1** с полными оптимизациями.
- **Dynamic PGO** (по умолчанию с .NET 8) — между тирами собирается профиль: какие типы реально приходят в виртуальные вызовы, какие ветки горячие. Tier 1 оптимизирует под реальную нагрузку (например, guarded devirtualization).

## Оптимизации JIT
- **inlining** — тело маленького метода вставляется в место вызова;
- **devirtualization** — виртуальный вызов заменяется прямым (sealed, известный тип, PGO);
- **bounds check elimination** — убирает проверки границ массива, если доказано, что индекс в пределах (`for (int i = 0; i < arr.Length; i++)`);
- векторизация, loop cloning, escape analysis (.NET 9–10: объекты, не покидающие метод, — на стеке).

## ReadyToRun и Native AOT
- **ReadyToRun** — сборка содержит заранее скомпилированный код + IL; JIT может перекомпилировать горячее. Быстрее старт.
- **Native AOT** — всё компилируется заранее в один нативный файл, JIT нет. Быстрейший старт и малая память, но ограничения на рефлексию и динамический код.

> Шаблон `i < arr.Length` JIT распознаёт и доказывает, что индекс в пределах.

Q: Что даёт Dynamic PGO?
A: JIT собирает профиль выполнения на Tier 0 (реальные типы в виртуальных вызовах, частота веток) и использует его при оптимизации Tier 1: guarded devirtualization, инлайнинг горячих путей, раскладка кода. Типичный прирост — 10–20% без изменения кода.

# @csharp-benchmark

## Почему Stopwatch врёт
Замер «запустил цикл — посмотрел Stopwatch» даёт мусор: первые вызовы идут через Tier 0 JIT, мешают GC, частота процессора плавает, результат может быть выкинут оптимизатором как неиспользуемый.

**BenchmarkDotNet** решает это: прогрев, много итераций, статистика, изоляция процессов, сравнение с baseline.

```csharp
[MemoryDiagnoser]
public class StringBench
{
    [Params(10, 1000)] public int N;

    [Benchmark(Baseline = true)]
    public string Concat() { var s = ""; for (int i = 0; i < N; i++) s += i; return s; }

    [Benchmark]
    public string Builder() { var sb = new StringBuilder(); for (int i = 0; i < N; i++) sb.Append(i); return sb.ToString(); }
}
// BenchmarkRunner.Run<StringBench>();  — только в Release!
```

## Как читать результат
- **Mean** — среднее время; смотрите и **Error/StdDev** — разброс.
- **Ratio** — относительно baseline.
- **Allocated** (с `[MemoryDiagnoser]`) — байт на операцию; часто важнее времени, т.к. аллокации = будущая работа GC.
- Gen0/Gen1 — сколько сборок на 1000 операций.

## Профилирование сервиса
Бенчмарк — для микро-вопросов. Для реального сервиса:
- `dotnet-counters monitor -p <pid>` — CPU, GC, пул потоков, исключения, запросы в секунду;
- `dotnet-trace collect` + PerfView / Speedscope / Visual Studio — где тратится CPU;
- профилировщики памяти (dotMemory, VS) — кто аллоцирует.

Правило: **сначала измерь**, найди горячее место (обычно 5% кода дают 95% времени), оптимизируй, измерь снова.

Q: Почему нельзя мерить производительность Stopwatch в цикле?
