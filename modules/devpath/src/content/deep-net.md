# @net-tcpip

## Глубже: TCP под нагрузкой
**Управление перегрузкой**: slow start (окно удваивается), congestion avoidance, реакция на потери. **CUBIC** (по умолчанию в Linux) и **BBR** (Google, моделирует пропускную способность и RTT — лучше на каналах с потерями).

**Задержка = RTT × число круговых поездок**: TCP-рукопожатие (1 RTT) + TLS 1.3 (1 RTT) + запрос (1 RTT). Переиспользование соединений и HTTP/2 убирают первые два для последующих запросов.

**Nagle и delayed ACK** вместе дают задержки ~40 мс на маленьких сообщениях — `TCP_NODELAY` (Kestrel и HttpClient ставят сами).

**Порты и соединения**: эфемерные порты (~28 тыс. по умолчанию в Linux) — предел исходящих соединений к одному адресу; TIME_WAIT держит порт 60 с.

**Backlog**: очередь установленных соединений, ещё не принятых приложением; переполнение → SYN отбрасываются, клиенты видят таймауты.

**MTU и фрагментация**: 1500 байт в Ethernet; в туннелях (VPN, overlay) меньше — «чёрные дыры» PMTU.

Q: Почему переиспользование соединений так сильно влияет на латентность?
A: Новое соединение требует TCP-рукопожатия и TLS-рукопожатия (минимум 2 RTT) и начинается с маленького окна перегрузки (slow start). Переиспользуемое соединение уже «разогрето»: запрос идёт сразу с большим окном.

# @net-http

## Глубже: HTTP для бэкенд-инженера
**Кэширование глубже**: `Cache-Control: public, max-age=60, stale-while-revalidate=300` — отдавать устаревшее, пока обновляется в фоне; `Vary` — по каким заголовкам различаются варианты; `private` — только браузер, не CDN.

**Условные запросы**: `ETag` + `If-None-Match` (304), `If-Match` для оптимистичной конкуренции (412).

**HTTP/2 в .NET**: мультиплексирование в `HttpClient` (`EnableMultipleHttp2Connections` при большом числе параллельных запросов), gRPC требует HTTP/2. **HTTP/3** в Kestrel — QUIC через msquic.

**Безопасность заголовков**: HSTS, CSP, `X-Content-Type-Options`, cookies с `SameSite`, `Secure`, `__Host-` префикс.

**CORS глубже**: preflight кэшируется (`Access-Control-Max-Age`); `AllowCredentials` несовместим с `*`; ошибки CORS видит только браузер — сервер получает запрос.

**Полезные коды**: 202 (принято к обработке), 207, 409, 412, 422, 425, 429 с `Retry-After`, 503 с `Retry-After`.

Q: Как работает условное кэширование с ETag?
A: Сервер возвращает ETag (отпечаток версии ресурса). Клиент при повторном запросе отправляет If-None-Match с этим значением; если ресурс не изменился, сервер отвечает 304 Not Modified без тела, иначе — 200 с новым содержимым и ETag.

# @net-dns-tls

## Глубже: DNS и TLS в эксплуатации
**DNS**: кэширование на всех уровнях (браузер, ОС, резолвер) — снижайте TTL заранее перед миграцией. `CNAME` нельзя на корне домена (используйте ALIAS/ANAME у провайдера). **DNS в .NET**: `HttpClient` через `SocketsHttpHandler.PooledConnectionLifetime` пересоздаёт соединения, чтобы видеть смену адресов.

**DNSSEC** — подпись записей от подмены; **DoH/DoT** — шифрование DNS-запросов.

**TLS**: 1.3 — меньше шифров, 1-RTT, forward secrecy обязательна; 0-RTT — быстрее, но уязвим к повтору (только для идемпотентных запросов).

**Сертификаты**: SAN (все имена), wildcard, короткие сроки (Let's Encrypt 90 дней, индустрия идёт к ~47 дням) → автоматизация обязательна (ACME, cert-manager). **Certificate Transparency** — публичные логи всех выданных сертификатов; мониторьте выдачу на свои домены.

**mTLS в .NET**: `ClientCertificateMode.RequireCertificate` в Kestrel, проверка цепочки и отпечатка; в mesh — автоматически.

**Отладка**: `openssl s_client -connect host:443 -servername host`, `dig +trace`, SSL Labs для проверки конфигурации.

# @net-loadbalancing

## Глубже: балансировка в больших системах
**Алгоритмы**: **power of two choices** — выбрать двух случайных и отправить менее загруженному: почти оптимально и без глобального знания; **least outstanding requests**; **consistent hashing** для кэш-локальности (с bounded loads, чтобы не перегружать горячие узлы).

**Балансировка на клиенте** (gRPC, service mesh): клиент сам знает список экземпляров — нет лишнего хопа, но нужен service discovery.

**Health checks**: активные (прокси проверяет) и пассивные (outlier detection — исключать экземпляры с ошибками), медленный старт новых экземпляров (slow start), отключение (draining) перед остановкой.

**Глобально**: anycast, GeoDNS, глобальные балансировщики (Azure Front Door, Cloudflare), failover между регионами.

**CDN глубже**: cache key, purge по тегам, origin shield (промежуточный кэш), кэширование API-ответов на edge, edge functions.

**DDoS**: объёмные атаки гасит провайдер/CDN, атаки на приложение (L7) — WAF, rate limiting, challenge.

Q: Какие механизмы делают балансировку устойчивой к проблемным экземплярам?
A: Активные health checks, пассивное обнаружение выбросов (ошибки, латентность), таймауты и ретраи на другой экземпляр для идемпотентных запросов, slow start для новых экземпляров, draining перед остановкой, алгоритмы с учётом нагрузки (least requests, power of two choices).
