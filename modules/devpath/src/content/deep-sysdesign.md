# @sysdesign-method

## Глубже: как выглядит сильный ответ
**Уровни ожиданий**: middle — рабочая схема с базовыми компонентами; senior — обоснованные компромиссы, узкие места и отказы, оценки; staff — несколько вариантов с анализом, эволюция системы, организационные и операционные аспекты (наблюдаемость, деплой, стоимость).

**Углубление** — выбирайте 1–2 темы, интересные для задачи: модель данных и выбор хранилища, согласованность, горячие ключи, кэширование, очереди, масштабирование записи, отказ ДЦ.

**Типичные ошибки**: сразу рисовать микросервисы; не спросить о масштабе; называть технологии без причин («возьмём Kafka»); игнорировать чтение/запись и распределение нагрузки; не говорить об отказах; монолог без вовлечения интервьюера.

**Словарь компромиссов**: согласованность vs доступность, латентность vs пропускная способность, стоимость vs надёжность, простота vs гибкость, нормализация vs скорость чтения, push vs pull.

**Тренировка**: вслух с таймером 45 минут, запись себя, разбор эталонных решений после собственной попытки.

# @sysdesign-shortener

## Глубже: сокращатель ссылок в масштабе
**Генерация id без координации**: диапазоны счётчика, выдаваемые каждому экземпляру (сервис-выдатчик диапазонов в БД/ZooKeeper), + base62; или Snowflake (время + id узла + счётчик) → base62. Чтобы коды не были предсказуемы — перемешивание (обратимая перестановка, Feistel).

**Хранилище**: запись 40/с, чтение 4000/с, миллиарды записей — key-value (DynamoDB/Cassandra) или шардированный PostgreSQL по коду; первичный ключ = код.

**Кэш**: распределение популярности по закону Ципфа — небольшой кэш закрывает большую долю запросов; кэширование на CDN с 301 для ссылок без статистики.

**Аналитика**: событие клика в Kafka → агрегация (Flink/ClickHouse) → отчёты; не блокировать редирект записью статистики.

**Безопасность и злоупотребления**: проверка на фишинг (Safe Browsing), лимиты на создание, запрет открытого редиректа на внутренние ресурсы, удаление по жалобам.

**Кастомные алиасы**: проверка уникальности, запрещённые слова, резервирование.

# @sysdesign-ratelimiter

## Глубже: распределённый rate limiter
**Точность vs стоимость**: централизованный счётчик в Redis точен, но добавляет сетевой вызов; локальные счётчики в каждом экземпляре (лимит / N экземпляров) дёшевы, но неточны при неравномерной балансировке; гибрид — локальный кэш токенов с периодической синхронизацией.

**Атомарность в Redis**: Lua-скрипт для token bucket (прочитать токены и время, пополнить, списать, записать) — одна операция; sliding window на sorted set (`ZADD`, `ZREMRANGEBYSCORE`, `ZCARD`).

**Многоуровневые лимиты**: на пользователя, на IP, на API-ключ, глобально на сервис, на дорогие операции отдельно; «стоимость» запроса вместо счёта запросов (тяжёлый поиск = 10 единиц).

**Поведение при отказе**: fail open с локальным лимитом; не превращать rate limiter в единую точку отказа.

**Клиентская сторона**: заголовки `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, `Retry-After`; клиенты уважают их и используют backoff.

**В .NET**: встроенный `System.Threading.RateLimiting` локально; распределённые — Redis-реализации (например, RedisRateLimiting).

---recall
Q: Как спроектировать rate limiter для распределённого API?
A: Выбрать алгоритм (token bucket или sliding window), хранить счётчики в Redis с атомарными Lua-операциями или использовать гибрид с локальными счётчиками, лимиты на нескольких уровнях (пользователь, IP, ключ, глобально) и по стоимости операций, возвращать 429 и заголовки лимитов, при отказе хранилища — fail open с локальной защитой.

# @sysdesign-chat

## Глубже: мессенджер в деталях
**Идентификаторы сообщений**: монотонные в пределах чата (Snowflake или счётчик на чат) — порядок и синхронизация «дай всё после id X».

**Доставка**: клиент → gateway (WebSocket) → сервис сообщений (сохранение, присвоение id) → fan-out: онлайн-получателям через их gateway (реестр сессий), офлайн — push. Подтверждения: сервер получил (1 галочка), доставлено на устройство (2), прочитано.

**Мультиустройства**: у пользователя несколько сессий; синхронизация по курсору на устройство; E2E-шифрование с несколькими устройствами (Signal protocol, sender keys для групп) усложняет всё.

**Хранение**: Cassandra/ScyllaDB (Discord), партиции по (chat_id, bucket по времени) — ограничить размер партиции; медиа — объектное хранилище + CDN.

**Масштаб gateway**: миллионы соединений, лёгкие процессы, мягкое переподключение при деплое (рассылка «переподключись» порциями), sticky не нужен при реестре сессий.

**Большие группы/каналы**: pull вместо fan-out, ленивая доставка, счётчики непрочитанного считаются отдельно.

# @sysdesign-feed

## Глубже: ранжированная лента
**Двухэтапное ранжирование**: генерация кандидатов (посты подписок, популярное, рекомендации — сотни/тысячи) → ранжирование моделью (вероятность взаимодействия) → переранжирование (разнообразие, свежесть, правила, реклама).

**Хранение ленты**: в Redis список id (последние N сотен), гидрация данными постов и авторов батчами из кэшей; пагинация курсором по (score, id).

**Гибрид fan-out**: авторы с < X подписчиков — push; знаменитости — pull при чтении; неактивным не строим ленту заранее, строим при входе.

**Удаление и приватность**: удалённый пост исчезает из лент — лениво фильтровать при гидрации; изменение приватности аккаунта — пересборка.

**Счётчики** (лайки, просмотры): приблизительные и агрегированные асинхронно; точные — только где нужно.

**Метрики**: время до первого экрана ленты, свежесть, вовлечённость; A/B-тесты алгоритмов.

# @sysdesign-notifications

## Глубже: уведомления без спама и потерь
**Модель данных**: шаблоны (с версиями и локализацией), предпочтения пользователя по типам и каналам, журнал отправок (статус, провайдер, попытки), ключ дедупликации.

**Конвейер**: событие → обогащение (данные пользователя) → проверка правил (предпочтения, тихие часы, частотные лимиты, объединение похожих — «5 новых комментариев» вместо пяти пушей) → рендер → очередь канала по приоритету → отправка → колбэки статусов.

**Надёжность**: outbox из сервисов-источников, at-least-once с дедупликацией по ключу, ретраи с backoff, circuit breaker на провайдера, резервный провайдер SMS/email.

**Масштаб рассылок**: сегментация, растягивание во времени, ограничения провайдеров (email — репутация домена, SPF/DKIM/DMARC, прогрев IP), учёт часовых поясов.

**Метрики**: доставлено, открыто, кликнуто, отписки; жалобы на спам как сигнал.

## Глубже: бронирование под пиком
**Стратегии конкуренции**:
- оптимистичная (условный UPDATE / версия) — при низкой конкуренции;
- пессимистичная (`SELECT ... FOR UPDATE SKIP LOCKED` для выдачи любого свободного места);
- резервирование в Redis (`SET seat NX EX 600`) + подтверждение в БД — быстро, но две системы.

**Виртуальная очередь**: пользователи получают токен места в очереди (Redis sorted set по времени прихода), пропускаются порциями в «зону покупки» с ограниченной ёмкостью; токен подписан и имеет срок.

**Инвентарь**: кэш доступности (может быть чуть устаревшим) для просмотра; точная проверка — только при резервировании.

**Оплата**: резерв → платёж с ключом идемпотентности → подтверждение; истёк резерв при успешной оплате — автоматический возврат или повторная попытка удержать место.

**Защита от ботов**: лимиты на аккаунт/карту, CAPTCHA/проверки в очереди, обнаружение аномалий.

**Отказы**: БД бронирований — источник правды, всё остальное (кэш, очередь) можно восстановить.

# @sysdesign-payments

## Глубже: платёжная платформа
**Компоненты**: платёжный сервис (оркестрация), **ledger** (двойная запись, неизменяемые проводки), кошельки/балансы (производные от ledger), интеграции с PSP/эквайерами, сверка, антифрод, отчётность.

**Состояния платежа** как конечный автомат с явными переходами и хранимой историей; вебхуки провайдера — идемпотентно, с проверкой подписи, с возможностью пропуска и дублирования.

**Деньги**: хранить в минимальных единицах (копейки) как целые, валюта всегда рядом; округление по правилам; курсы валют с меткой времени.

**Согласованность**: локальная транзакция для проводок; с внешним миром — сага и сверка; «unknown» статус — нормальная часть жизни.

**Сверка**: ежедневные файлы от провайдера против своих записей: совпало / есть у нас, нет у них / есть у них, нет у нас / суммы различаются — очередь разбора.

**Требования**: PCI DSS (не хранить данные карт — токенизация у провайдера), аудит, разграничение доступа, 54-ФЗ (чеки) в России.

# @sysdesign-storage

## Глубже: хранилище файлов
**Блоки и дедупликация**: content-defined chunking (границы по содержимому, rolling hash) — вставка в начало файла не сдвигает все блоки; дедупликация между пользователями экономит место, но может раскрывать факт наличия файла (атаки подтверждения) — часто дедуплицируют только в пределах аккаунта.

**Метаданные**: иерархия папок, версии, права, список блоков файла — в транзакционной БД (шардирование по workspace); операции «переместить папку» — изменение метаданных, а не данных.

**Синхронизация**: журнал изменений (change log) с курсором на устройство; long polling/WebSocket для уведомлений; конфликт — копия файла; удалённое — в корзину с TTL.

**Хранилище блоков**: объектное хранилище с erasure coding для экономии (вместо тройной репликации), холодные уровни для старых версий.

**Загрузка**: возобновляемая (tus-протокол, multipart upload S3), pre-signed URL, проверка хэша блока.

**Совместная работа**: для документов — OT/CRDT (Google Docs, Figma), а не блочная синхронизация.

A: Сервер ведёт журнал изменений метаданных с монотонным курсором; устройства получают уведомления (long polling/WebSocket) и запрашивают изменения после своего курсора; загружают только отсутствующие блоки по хэшам; конфликты одновременных изменений сохраняются как отдельные копии; удаления идут в корзину.

# @sysdesign-search

## Глубже: поиск и подсказки в масштабе
**Typeahead**: логи запросов → агрегация (MapReduce/Spark, окно по времени, затухание старых) → построение trie с топ-K в узлах → раскатка на реплики сервиса подсказок; горячие префиксы — кэш в браузере/CDN (префикс — ключ). Персонализация — подмешивание истории пользователя на клиенте или отдельным слоем. Фильтр неприемлемых подсказок.

**Шардирование trie**: по первой букве/диапазону префиксов — с учётом неравномерности (на «с» и «п» больше запросов).

**Поисковый движок**: индексатор (из потока изменений) → шарды инвертированного индекса с репликами → брокер запросов (scatter-gather, объединение топов) → ранжирование в два этапа (BM25 → learning-to-rank) → кэш результатов популярных запросов.

**Свежесть**: near-real-time индексация (секунды), отдельный «свежий» индекс для новых документов.

**Качество**: исправление опечаток, синонимы, морфология, логирование кликов для обучения ранжирования, метрики NDCG, A/B.
