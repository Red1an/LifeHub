# @aidev-landscape

## Глубже: как выбирать и комбинировать инструменты
**Критерии**: качество модели на ваших задачах, умение агента работать с большим репозиторием (поиск, контекст), интеграция с IDE/терминалом/CI, режимы разрешений и безопасность, приватность кода (корпоративные тарифы, где обрабатываются данные), стоимость (подписка vs токены), расширяемость (MCP, хуки, команды).

**Типичная связка сильного инженера**: автодополнение в IDE для потока мелких правок + агент в терминале/IDE для задач на несколько файлов + фоновые агенты для независимых задач из бэклога + ИИ-ревью PR как второй взгляд.

**Модели меняются быстро**: держите собственный маленький набор «эталонных задач» из своего проекта и прогоняйте на новых моделях/инструментах — так решение о переходе будет основано на фактах, а не на хайпе.

**Метрики пользы**: время цикла задачи, доля принятых без переделки изменений, дефекты после релиза — а не «сколько строк сгенерировано».

# @aidev-tasking

## Глубже: шаблоны постановки задач
**Шаблон «фича»**: контекст (модуль, зачем) → поведение (сценарии «дано/когда/тогда») → ограничения (не трогать, использовать) → образцы (файлы-примеры) → проверка (тесты, команды) → формат отчёта.

**Шаблон «баг»**: шаги воспроизведения, ожидаемое и фактическое поведение, логи/стек целиком, что уже проверено; просьба сначала **воспроизвести тестом**, потом чинить причину, а не симптом.

**Шаблон «исследование»**: «не меняй код; найди, как устроено X; ответ — схема и список файлов с ролями».

**Итерации**: «сначала план» → согласование → выполнение по шагам с коммитами → самопроверка агента («перечитай diff, проверь крайние случаи») → ваше ревью.

**Анти-паттерны**: огромная задача одним сообщением; «сделай хорошо»; задача без способа проверки; исправление через «не работает, попробуй ещё» без деталей; переписывание одной и той же сессии часами (контекст засоряется — начните заново с уточнённой постановкой).

# @aidev-context

## Глубже: память и контекст проекта
**Иерархия файлов правил**: глобальные (личные предпочтения), уровня репозитория (команды, архитектура), уровня модулей (особенности модуля). Корневой файл — короткий, детали — по ссылкам на документы, которые агент читает при необходимости.

**Что писать** — то, что агент не выведет из кода: как запускать и тестировать, неочевидные соглашения, запреты, подводные камни, где лежит документация. **Что не писать** — очевидное из кода, длинные описания всех классов (устаревают), секреты.

**Живая документация**: после сессии, где агент долго разбирался, попросите его дописать вывод в файл правил — следующая сессия начнётся умнее.

**Управление окном**: compact/очистка между задачами; план и прогресс большой задачи — в файле (`PLAN.md`, чек-лист), чтобы пережить сжатие контекста и новые сессии; субагенты для «шумной» работы (поиск по тысячам файлов).

**Контекст извне**: MCP-серверы документации для актуальных версий библиотек, ссылки на issue и дизайн, скриншоты UI.

# @aidev-agentic

## Глубже: параллельная и автоматизированная работа
**Параллельные агенты**: отдельные git worktree на каждую задачу, независимые области кода, одна задача — одна ветка — один PR; вы переключаетесь между ними как тимлид между разработчиками. Предел — ваша способность ревьюить.

**Headless и CI**: агент в конвейере — автоматический разбор упавших тестов с предложением исправления, генерация описаний PR, ревью, обновление зависимостей с исправлением сломанного кода, массовые миграции по шаблону. Ограничьте инструменты и права, работайте в изолированном окружении.

**Хуки и детерминизм**: то, что должно выполняться всегда (форматирование, сборка, запрет правок в определённых файлах), — не просьба в промпте, а хук.

**Режимы автономности**: от «подтверждать всё» до «автоматически в песочнице»; повышайте автономность по мере доверия и качества проверок в проекте.

**Роль человека**: декомпозиция, приоритеты, архитектурные решения, ревью, ответственность за продакшен.

# @aidev-verify

## Глубже: инженерия обратной связи
**Скорость цикла** — главный множитель продуктивности агента: быстрые юнит-тесты, возможность запустить часть тестов (`--filter`), инкрементальная сборка, понятные сообщения об ошибках. Если прогон тестов занимает 20 минут, агент будет работать вслепую.

**Проверяемые спецификации**: тесты, схемы (OpenAPI, JSON Schema), типы, контракты — всё, что машина может проверить без человека.

**Защита тестов**: CODEOWNERS или хук, запрещающий агенту менять тесты в определённой задаче; отдельный ревью diff тестов; мутационное тестирование показывает, что тесты не ослабли.

**UI**: Playwright-тесты, скриншоты и визуальные сравнения, проверка консоли браузера; агенту с браузерным инструментом можно поручить самопроверку интерфейса.

**Property-based тесты** (FsCheck, CsCheck) — проверка свойств на тысячах случайных входов: хорошо ловят крайние случаи в сгенерированном коде.

**Ревью как проверка**: второй агент-ревьюер со свежим контекстом, затем человек.

# @aidev-spec

## Глубже: спецификация, понятная машине и людям
**Хорошая спецификация**: пользовательские сценарии с критериями приёмки, нефункциональные требования (производительность, безопасность), явные «не делаем», открытые вопросы. ИИ помогает её **уточнять**: «задай 10 вопросов, которые разработчик задал бы по этой спецификации».

**План**: архитектурные решения со ссылками на ADR, модель данных, контракты API, риски, стратегия тестирования, порядок работ.

**Задачи**: маленькие, независимые где возможно, каждая с критерием готовности и тестами; помечены зависимости и то, что можно делать параллельно.

**Реализация**: агент получает спецификацию, план и одну задачу; после каждой — проверка и отметка в `tasks.md`.

**Жизнь документов**: при изменении требований — сначала спецификация, потом код; расхождение кода и спецификации — баг одного из них.

**Инструменты**: GitHub Spec Kit (`/specify`, `/plan`, `/tasks`, `/implement`), Kiro (requirements → design → tasks), BMAD-подобные методики с ролями агентов.

---recall
Q: Из каких артефактов состоит spec-driven процесс и как они связаны?
A: Спецификация (что и зачем: сценарии, критерии приёмки, нефункциональные требования, границы) → технический план (архитектура, данные, контракты, риски, стратегия тестов) → список задач (маленькие, проверяемые, с зависимостями) → реализация по задачам с проверкой; изменения требований проходят через спецификацию.

## Глубже: ревью ИИ-кода как навык
**Читать как код новичка с большим словарём**: код выглядит уверенно и чисто, поэтому ошибки маскируются. Проверяйте не стиль, а смысл: правильная ли модель предметной области, обработаны ли ошибки, нет ли тихих подмен поведения.

# @aidev-mcp

## Глубже: свой MCP-сервер
**Архитектура MCP**: клиент (приложение с моделью) ↔ сервер (ваш процесс) по stdio (локально) или Streamable HTTP (удалённо). Сервер объявляет **tools** (действия), **resources** (данные для контекста), **prompts** (шаблоны).

**C# SDK**: пакет `ModelContextProtocol`, хостинг через `AddMcpServer().WithStdioServerTransport().WithToolsFromAssembly()`; для HTTP — ASP.NET Core с `WithHttpTransport()`; инструменты — методы с атрибутами и описаниями, параметры из DI.

**Проектирование инструментов**: узкие безопасные операции вместо «выполни SQL», понятные описания и ошибки, пагинация больших результатов, ответ в компактном формате (модель платит токенами за каждый символ).

**Безопасность**: аутентификация для удалённых серверов (OAuth), минимальные права, подтверждение опасных действий на стороне клиента, валидация параметров, аудит; осторожно со сторонними серверами — они выполняются с вашими правами.

**Хуки и навыки** дополняют MCP: хуки — детерминированные действия на событиях агента; навыки — пакеты инструкций/скриптов, подгружаемые по ситуации.

# @aidev-security

## Глубже: модель угроз для ИИ-разработки
**«Смертельная триада»** (Саймон Уиллисон): доступ к приватным данным + воздействие недоверенного контента + возможность отправлять данные наружу. При наличии всех трёх prompt injection может привести к утечке. Уберите хотя бы одну составляющую для рискованных сценариев.

**Векторы инъекций**: README и код сторонних зависимостей, issues и комментарии PR от внешних людей, веб-страницы, результаты MCP-инструментов, файлы в репозитории.

**Защитные меры**:
- песочницы и контейнеры для автономной работы, без доступа к продакшену;
- разрешённые списки команд и доменов, запрет на отправку данных наружу;
- секреты вне рабочей папки, запрет чтения `.env`/ключей в настройках агента;
- ревью всего, что агент меняет в CI-конфигурации, скриптах сборки и зависимостях;
- проверка каждого нового пакета (slopsquatting);
- корпоративные условия обработки кода.

**В приложениях с LLM**: OWASP LLM Top 10 — prompt injection, раскрытие чувствительных данных, excessive agency (слишком много прав), небезопасная обработка вывода.

# @aidev-legacy

## Глубже: миграции с помощью агентов
**Стратегия большой миграции** (например, .NET Framework 4.8 → .NET 8/9):
1. инвентаризация: зависимости, несовместимые API (System.Web, WCF, AppDomain, Remoting), сторонние пакеты — агент составляет отчёт;
2. характеризационные и интеграционные тесты для критичных сценариев;
3. перевод проектов в SDK-стиль, multi-targeting (`net48;net8.0`) для постепенного перехода библиотек;
4. .NET Upgrade Assistant для механики, агент — для ручных правок по проектам, по одному PR на проект;
5. замены: WCF → gRPC/CoreWCF, System.Web → ASP.NET Core (strangler fig через YARP: новый сайт проксирует непереведённые маршруты старому).

**Понимание кода**: агент строит карту модулей и потоков данных, находит мёртвый код, пишет документацию «как это работает» для каждого модуля; вы проверяете выборочно.

**Шаблонные изменения по всей кодовой базе**: агент + тесты + маленькие PR лучше, чем «одним махом»; для строго механических — Roslyn-анализаторы с code fix.

## Глубже: осознанное развитие с ИИ
**Исследования продуктивности** показывают противоречивые результаты: большой выигрыш на незнакомых и шаблонных задачах, иногда замедление у опытных разработчиков в знакомом коде (время уходит на промпты, ожидание и исправления). Вывод — измеряйте на себе и выбирайте, где ИИ помогает.
