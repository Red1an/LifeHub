# @data-sql

## JOIN и NULL
- `INNER JOIN` — только совпадающие строки.
- `LEFT JOIN` — все строки слева, справа `NULL`, если пары нет. Классика: «клиенты без заказов» = `LEFT JOIN orders o ... WHERE o.id IS NULL`.
- `FULL JOIN`, `CROSS JOIN` (декартово произведение).

**NULL — это «неизвестно»**, а не ноль: `NULL = NULL` даёт не `TRUE`, а `NULL`. Поэтому проверяют `IS NULL`, а `NOT IN (подзапрос с NULL)` возвращает пустоту — используйте `NOT EXISTS`. `COUNT(*)` считает строки, `COUNT(col)` — не-NULL значения.

## Агрегация и оконные функции
`GROUP BY` схлопывает строки; `HAVING` фильтрует группы (после агрегации), `WHERE` — строки (до).

**Оконные функции** считают по «окну» строк, **не схлопывая** их:
```sql
SELECT customer_id, created_at, total,
       SUM(total)  OVER (PARTITION BY customer_id ORDER BY created_at) AS running_total,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
FROM orders;
```
`ROW_NUMBER`, `RANK`, `DENSE_RANK`, `LAG`/`LEAD` (предыдущая/следующая строка), `NTILE`. Задача «последний заказ каждого клиента» — `rn = 1`.

## CTE
`WITH` делает запрос читаемым, разбивая его на именованные шаги. **Рекурсивный CTE** обходит иерархии: дерево категорий, оргструктуру, граф.
```sql
WITH RECURSIVE tree AS (
  SELECT id, parent_id, name, 1 AS depth FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.parent_id, c.name, t.depth + 1 FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;
```
Порядок **логического** выполнения запроса: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → оконные функции → ORDER BY → LIMIT. Поэтому псевдоним из SELECT нельзя использовать в WHERE.

---recall
Q: Чем WHERE отличается от HAVING?
A: WHERE фильтрует строки до группировки и не может использовать агрегаты. HAVING фильтрует группы после GROUP BY и работает с агрегатами (HAVING COUNT(*) > 5).

Q: Чем оконная функция отличается от GROUP BY?
A: GROUP BY схлопывает строки группы в одну. Оконная функция считает значение по окну (PARTITION BY/ORDER BY), но сохраняет все исходные строки — удобно для нарастающих итогов, рангов, сравнения с соседними строками.

# @data-indexes

## Как работает B-tree индекс
Индекс — отдельная структура, отсортированная по ключу, со ссылками на строки. **B-tree** — сбалансированное дерево: поиск за O(log n), подходит для `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, префиксного `LIKE 'abc%'`.

Цена индекса: место на диске и **замедление записи** — каждый INSERT/UPDATE обновляет все индексы таблицы.

## Составные индексы
Индекс `(a, b)` отсортирован сначала по `a`, внутри — по `b`. Он помогает запросам по `a` и по `a AND b`, но не по одному `b` (правило **левого префикса**). Порядок колонок: сначала условия равенства, потом диапазоны и сортировка.

**Covering index** содержит все нужные запросу колонки (в ключе или `INCLUDE`) — БД отвечает из индекса, не трогая таблицу (index-only scan).

Индекс **не используется**, если:
- на колонке функция: `WHERE lower(email) = ...` (нужен функциональный индекс);
- `LIKE '%abc'` с ведущим `%`;
- низкая селективность (выбирается большая доля таблицы — seq scan дешевле);
- несовпадение типов (неявное приведение).

## Читаем план
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42 AND created_at > now() - interval '30 days';
```
Смотрим: тип сканирования (`Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`), **оценку строк vs фактические** (большое расхождение → устаревшая статистика, `ANALYZE`), время, чтения буферов. Тип соединения: Nested Loop (мало строк), Hash Join, Merge Join.

## Другие индексы
- **Hash** — только равенство.
- **GIN** — массивы, JSONB, полнотекстовый поиск.
- **GiST/SP-GiST** — геоданные, диапазоны.
- **BRIN** — огромные таблицы с естественным порядком (логи по времени).
- **Частичный индекс**: `CREATE INDEX ... WHERE status = 'active'`.

---recall
Q: Что такое правило левого префикса для составного индекса?
A: Индекс (a, b, c) можно использовать для условий по a, по a и b, по a, b и c — то есть по левому префиксу колонок. Условие только по b или c не позволяет пройти по индексу эффективно.

Q: Что такое covering index и зачем он нужен?
A: Индекс, содержащий все колонки, нужные запросу (ключ + INCLUDE). БД отвечает прямо из индекса без обращения к таблице — index-only scan, меньше чтений.

# @data-transactions

## ACID
- **Atomicity** — всё или ничего.
- **Consistency** — транзакция переводит БД из одного корректного состояния в другое (ограничения соблюдены).
- **Isolation** — параллельные транзакции не мешают друг другу (в той или иной степени).
- **Durability** — подтверждённое не потеряется (журнал WAL).

## Аномалии и уровни изоляции
| Аномалия | Суть |
|---|---|
| Dirty read | читаю незакоммиченные изменения другой транзакции |
| Non-repeatable read | повторное чтение строки даёт другое значение |
| Phantom | повторный запрос по условию возвращает новые строки |
| Lost update | два read-modify-write, одно обновление теряется |
| Write skew | две транзакции читают общие данные и пишут в разные строки, нарушая инвариант |

Уровни: **Read Uncommitted → Read Committed** (по умолчанию в PostgreSQL и SQL Server) → **Repeatable Read** (в PostgreSQL — snapshot isolation) → **Serializable**. Чем выше — тем меньше аномалий и тем больше блокировок/ретраев.

## MVCC
В PostgreSQL (и в SQL Server со snapshot) изменения создают **новые версии строк**, а каждая транзакция видит свой снимок. Читатели не блокируют писателей. Цена — старые версии надо убирать (VACUUM).

## Как не терять обновления
```sql
-- пессимистично: заблокировать строку до конца транзакции
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- атомарно одной командой
UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100;
```
**Оптимистичная конкуренция**: в строке есть версия (`xmin` в Postgres, `rowversion` в SQL Server). `UPDATE ... WHERE id = 1 AND version = 7` — если 0 строк изменено, кто-то успел раньше → повтор или ошибка 409. В EF Core — `[Timestamp]`/`IsConcurrencyToken` и `DbUpdateConcurrencyException`.

**Дедлок** в БД — две транзакции ждут блокировки друг друга; СУБД убивает одну из них. Лечение: одинаковый порядок обновления строк, короткие транзакции, ретраи.

---recall
Q: Перечисли аномалии параллельных транзакций.
A: Dirty read, non-repeatable read, phantom read, lost update, write skew (и read skew). Уровни изоляции ограничивают допустимые аномалии; Serializable исключает их все.

Q: Как работает оптимистичная блокировка?
A: В строке хранится версия. Обновление выполняется с условием на старую версию и увеличивает её. Если строк обновлено 0 — данные изменил кто-то другой, операцию повторяют или возвращают конфликт. Блокировки не держатся, хорошо при редких конфликтах.

# @data-postgres

## MVCC и VACUUM
UPDATE в PostgreSQL = вставка новой версии строки + пометка старой мёртвой. Мёртвые версии (**bloat**) раздувают таблицы и индексы. Их убирает **VACUUM** (autovacuum работает сам). Проблемы начинаются, когда autovacuum не успевает на горячих таблицах или долгая транзакция держит старый снимок и не даёт чистить.

Следите: `pg_stat_user_tables` (n_dead_tup, last_autovacuum), длинные транзакции в `pg_stat_activity`, **transaction ID wraparound**.

## JSONB
`jsonb` — бинарный JSON с индексами:
```sql
CREATE INDEX ON events USING gin (payload jsonb_path_ops);
SELECT * FROM events WHERE payload @> '{"type": "order_paid"}';
```
Удобно для гибких атрибутов, но не заменяет нормальную схему: нет внешних ключей, статистика хуже, легко устроить свалку.

## Полезные расширения
- `pg_stat_statements` — топ самых дорогих запросов (первое, что включают при тормозах);
- `pg_trgm` — нечёткий поиск и индексы для `LIKE '%abc%'`;
- `PostGIS` — геоданные;
- `pgvector` — векторы для ИИ-поиска;
- `pg_partman` — управление партициями.

## Npgsql и .NET
Npgsql — драйвер для .NET, EF Core-провайдер поддерживает JSONB, массивы, enum, диапазоны. Используйте пул соединений (включён по умолчанию), а при сотнях экземпляров — **PgBouncer** в режиме transaction pooling (с осторожностью к prepared statements).

Q: Что такое bloat в PostgreSQL и откуда он берётся?
A: Место, занятое мёртвыми версиями строк после UPDATE/DELETE (следствие MVCC). Если VACUUM не успевает (горячие таблицы, долгие транзакции), таблицы и индексы раздуваются, запросы замедляются.

# @data-modeling

## Нормализация
Цель — чтобы каждый факт хранился **в одном месте** и не было аномалий обновления.
- **1НФ** — атомарные значения, нет повторяющихся групп.
- **2НФ** — неключевые атрибуты зависят от всего составного ключа.
- **3НФ** — нет транзитивных зависимостей (город клиента не хранится в заказе).
Практическое правило: нормализуйте до 3НФ, денормализуйте осознанно.

## Денормализация
Ради скорости чтения дублируют данные: счётчик комментариев в посте, имя клиента в заказе (исторический снимок — это даже правильно!), материализованные представления, read-модели в CQRS. Цена — нужно поддерживать согласованность (триггеры, события, пересчёт).

## Ключи
- **Суррогатные** (`bigint identity`, UUID) — стабильны, не несут смысла.
- **Естественные** (ИНН, email) — меняются чаще, чем кажется; делайте их уникальным индексом, но не первичным ключом.
- **UUID v4** случаен → фрагментация B-tree при вставках. **UUID v7** (упорядочен по времени, `Guid.CreateVersion7()` в .NET 9) — генерируется на клиенте и хорошо ложится в индекс.

## Частые паттерны
- **Soft delete** (`deleted_at`) — удобно, но все запросы должны фильтровать (global query filter в EF), уникальные индексы — частичные.
- **Аудит** — таблицы истории или temporal tables.
- **Деньги** — `numeric/decimal`, никогда `float`.
- **Время** — хранить в UTC (`timestamptz`), конвертировать при показе.

---recall
Q: Когда денормализация оправдана?
A: Когда чтение сильно преобладает и джойны/агрегации дороги: счётчики, read-модели, исторические снимки (цена в заказе на момент покупки), отчёты. При этом нужен механизм поддержания согласованности копий.

# @data-efcore

## Как работает EF Core
`DbContext` — unit of work + change tracker. Сущности, загруженные через контекст, **отслеживаются**: EF хранит снимок, а `SaveChanges` сравнивает и генерирует UPDATE только изменённых полей в одной транзакции.

`DbContext` — короткоживущий (scoped на запрос) и **не потокобезопасный**: нельзя выполнять два запроса параллельно на одном контексте.

## Проблема N+1
```csharp
var orders = await db.Orders.ToListAsync();
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);   // с lazy loading — отдельный запрос на каждый заказ
```
Решения:
- `Include(o => o.Customer)` — загрузить связанные данные сразу;
- **проекция** `Select(o => new { o.Id, o.Customer.Name })` — лучший вариант для чтения: грузим только нужные колонки;
- `AsSplitQuery()` — если Include нескольких коллекций раздувает результат (картезианский взрыв).

## Только чтение — AsNoTracking
Для запросов, результаты которых не будут изменяться: `AsNoTracking()` — без снимков, быстрее и меньше памяти. Можно сделать поведением по умолчанию: `UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)`.

## Миграции
`dotnet ef migrations add AddOrderStatus` → код миграции → `dotnet ef database update`. В проде лучше:
- генерировать **идемпотентный SQL-скрипт** (`dotnet ef migrations script --idempotent`) или **migration bundle** и применять отдельным шагом деплоя;
- не вызывать `Database.Migrate()` при старте в нескольких репликах одновременно;
- проверять сгенерированный SQL (переименование может стать DROP + ADD).

Q: Что такое проблема N+1 и как её решить в EF Core?
A: Один запрос за списком и по отдельному запросу за связанными данными для каждого элемента. Решения: Include (eager loading), проекции через Select, split queries для нескольких коллекций; отключить lazy loading.

# @data-efcore-adv

## Массовые операции
С EF Core 7 есть `ExecuteUpdate` и `ExecuteDelete` — один SQL без загрузки сущностей:
```csharp
await db.Sessions.Where(s => s.ExpiresAt < now).ExecuteDeleteAsync(ct);
await db.Products.Where(p => p.CategoryId == 5)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.Price, p => p.Price * 1.1m), ct);
```
Они обходят change tracker и перехватчики SaveChanges — учитывайте это (аудит, доменные события).

## Производительность
- **Compiled queries** (`EF.CompileAsyncQuery`) — убирают затраты на трансляцию LINQ для горячих запросов.
- **DbContext pooling** (`AddDbContextPool`) — переиспользование экземпляров контекста.
- Пакетирование команд SaveChanges включено по умолчанию.
- Смотрите сгенерированный SQL: `ToQueryString()`, логирование `LogTo`.

## Моделирование
- **Owned types** — value objects (Address внутри Order) в тех же колонках или JSON.
- **Value converters** — хранить strongly-typed Id, enum как строки.
- **JSON-колонки** (`ToJson()`) — вложенные объекты в jsonb с запросами по ним.
- **Global query filters** — soft delete, мультиарендность.
- **Interceptors** — аудит, soft delete, логирование команд.

## Dapper рядом с EF
Для сложных отчётных запросов и максимальной скорости чтения используют **Dapper** (или `SqlQuery<T>` в EF Core 8): пишете SQL руками, получаете DTO. Частый подход: запись — через EF и доменную модель, сложное чтение — SQL/Dapper.

# @data-nosql

## Виды NoSQL
- **Документные** (MongoDB, Couchbase) — JSON-документы, гибкая схема, вложенные данные читаются одним запросом.
- **Key-value** (Redis, DynamoDB) — максимально быстрый доступ по ключу.
- **Wide-column** (Cassandra, ScyllaDB) — огромные объёмы записи, данные раскладываются по ключу партиции.
- **Графовые** (Neo4j) — связи как first-class, обходы графа.
- **Поисковые** (Elasticsearch) и **колоночные аналитические** (ClickHouse) — отдельные классы.

## Моделирование от запросов
В реляционной модели сначала нормализуют данные, а запросы пишут потом. В NoSQL — наоборот: **схему проектируют под запросы**. В Cassandra одна таблица часто = один запрос; данные дублируются, джойнов нет.

MongoDB: встраивать (embed) связанные данные, если их читают вместе и они не растут бесконечно; ссылаться (reference), если растут или нужны отдельно.

## Когда что
Postgres с JSONB закрывает большинство случаев «нужна гибкая схема». NoSQL оправдан, когда:
- масштаб записи/объём выше возможностей одного сервера (Cassandra);
- нужен ultra-low latency доступ по ключу (Redis);
- модель — это действительно граф (Neo4j);
- документная модель естественна, и транзакции между документами редки.

Цена: слабее гарантии согласованности (часто eventual), нет джойнов, миграции данных — на приложении.

Q: Когда оправдан переход с PostgreSQL на NoSQL?
A: Когда требования выходят за возможности реляционной БД: масштаб записи/объём на много узлов, сверхнизкая латентность по ключу, графовые обходы, естественная документная модель. Во многих остальных случаях достаточно Postgres с JSONB.

# @data-redis

## Структуры данных
Redis — не просто «кэш строк»:
- **String** — значения, счётчики (`INCR` атомарен);
- **Hash** — объект с полями;
- **List** — очередь/стек;
- **Set** — уникальные элементы, пересечения;
- **Sorted Set** — элементы со score: рейтинги, таймлайны, rate limiting по окну;
- **Stream** — журнал событий с consumer groups;
- HyperLogLog (приблизительный count distinct), Bitmap, Geo.

Redis однопоточный в выполнении команд → каждая команда **атомарна**; для нескольких команд — `MULTI/EXEC` или Lua-скрипт.

## Персистентность
- **RDB** — периодические снимки: быстро восстанавливается, но теряются данные с последнего снимка.
- **AOF** — журнал всех команд (fsync раз в секунду): надёжнее, больше файл.
Можно комбинировать. Если Redis — только кэш, персистентность часто выключают.

## Pub/Sub и Streams
- **Pub/Sub** — сообщения не хранятся: подписчик офлайн — сообщение потеряно.
- **Streams** — хранятся, есть consumer groups и подтверждения (как облегчённая Kafka).

## Распределённые блокировки
`SET lock:order:42 <token> NX PX 30000` — захватить, если свободно, с TTL. Отпускать — только своим токеном (Lua-скрипт сравнить-и-удалить). Подводные камни: TTL истёк во время GC-паузы → два владельца. Для корректности нужны **fencing tokens**; алгоритм Redlock спорен. Для критичного — ZooKeeper/etcd или блокировки в БД.

## Масштабирование
**Sentinel** — автоматический failover для master-replica. **Redis Cluster** — шардирование на 16384 слота; команды с несколькими ключами работают только в одном слоте (hash tags `{user:1}`).

# @data-scaling

## Вертикально, потом горизонтально
Сначала: индексы, оптимизация запросов, кэш, более мощный сервер. Это покрывает удивительно многое. Потом — горизонтальные техники.

## Репликация
Одна запись на **primary**, копии на **репликах**. Реплики разгружают чтение и дают отказоустойчивость.
- **Асинхронная** — быстрая, но при падении primary можно потерять последние транзакции; реплики **отстают** (replication lag).
- **Синхронная** — надёжнее, запись медленнее.

Проблема **read-your-writes**: пользователь сохранил профиль и тут же читает с реплики, где изменений ещё нет. Решения: читать свои данные с primary какое-то время, ждать позицию репликации, sticky к primary после записи.

## Партиционирование и шардирование
- **Партиционирование** — одна таблица на части внутри одного сервера (по дате, по диапазону): быстрое удаление старых данных (`DROP PARTITION`), запросы читают только нужные части.
- **Шардирование** — данные на разных серверах по **ключу шарда** (user_id, tenant_id). Хороший ключ: равномерное распределение и запросы в пределах одного шарда. Плохой — горячие шарды и кросс-шардовые запросы.

Решардинг болезнен: заранее закладывают много логических шардов на меньшее число физических или используют consistent hashing. Готовые решения: Citus для Postgres, Vitess для MySQL.

## Пул соединений
Каждое соединение Postgres — процесс (~10 МБ). Сотни экземпляров сервиса × пул по 100 = тысячи соединений. **PgBouncer** (transaction pooling) мультиплексирует их в небольшое число реальных.

Q: Чем партиционирование отличается от шардирования?
A: Партиционирование делит таблицу на части в пределах одного сервера БД (удобство обслуживания, отсечение партиций). Шардирование распределяет данные по разным серверам по ключу шарда для масштабирования записи и объёма.

# @data-search

## Инвертированный индекс
Полнотекстовый поиск строит **инвертированный индекс**: слово → список документов, где оно встречается. Перед индексацией текст проходит **анализатор**: токенизация, нижний регистр, стоп-слова, **стемминг/лемматизация** (бегу → бег), синонимы. Поэтому «бегущий» находит «бег».

Ранжирование — BM25: учитывает частоту слова в документе и его редкость во всей коллекции.

## Elasticsearch / OpenSearch
Распределённый поисковый движок: индекс делится на **шарды** с репликами. Маппинг задаёт типы полей (`text` для полнотекста, `keyword` для точного совпадения и агрегаций). Умеет фасеты, агрегации, подсветку, автодополнение, векторный поиск.

Это **не основная БД**: данные синхронизируют из источника правды.

## Синхронизация: CDC
Как держать поиск актуальным:
- двойная запись из приложения — просто, но легко рассинхронизировать;
- outbox + потребитель;
- **CDC** (Change Data Capture): Debezium читает журнал БД (WAL) и публикует изменения в Kafka — надёжно и без изменений кода.

## OLTP vs OLAP
- **OLTP** (Postgres, SQL Server) — много коротких транзакций, строчное хранение.
- **OLAP** (ClickHouse, BigQuery) — аналитика по миллиардам строк: **колоночное хранение**, сжатие, векторизованное выполнение. Агрегация по колонке читает только её.

Q: Что такое CDC и зачем он нужен?
A: Change Data Capture — захват изменений из журнала транзакций БД (например, Debezium читает WAL) и публикация их как событий. Позволяет надёжно синхронизировать поисковые индексы, кэши, хранилища аналитики без двойной записи в коде.
