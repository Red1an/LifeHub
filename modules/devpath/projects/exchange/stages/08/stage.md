Бирже нужны **свечи** — цены открытия, максимума, минимума и закрытия по минутам, — без них нет графика в терминале. Завтра понадобятся
ещё уведомления о сделках, отчёты для налоговой, ML-детектор подозрительных сделок, выгрузка в хранилище для аналитиков.
Если каждую такую штуку вызывать прямо из `POST /orders`, заявка будет ждать их всех, а падение любой уронит торговлю.

Правильно иначе: сделка порождает **событие**, событие уходит в журнал (Kafka), а все, кому интересно, читают журнал сами, в своём темпе.
Сведение ничего не знает о потребителях. Звучит просто, пока не начинаешь думать о том, что бывает в жизни:

- база закоммитила сделку, а Kafka в эту секунду недоступна — событие потеряно?
- событие отправили, ответ потерялся, отправили ещё раз — потребитель учтёт сделку дважды?
- два экземпляра API читают один топик — оба посчитают одну сделку?
- в каком порядке потребитель увидит сделки одного инструмента?

---task
- Каждая сделка попадает в топик Kafka (`Kafka:TradesTopic`, строка подключения `ConnectionStrings:Kafka` — в тестах `localhost:19092`).
  Ключ сообщения — тикер, значение — JSON `{ tradeId, ticker, price, qty, buyOrderId, sellOrderId, at }`.
- Сделки одного инструмента лежат в топике в порядке исполнения.
- **Kafka недоступна — торговля не останавливается**: заявки исполняются, а события доходят до топика, когда брокер вернулся. Ни одно не теряется.
- Потребитель событий (группа `Kafka:CandlesGroup`) строит минутные свечи: `GET /candles/{ticker}` →
  `[{ start, open, high, low, close, volume }]` по возрастанию `start`.
- Потребитель **идемпотентный**: повтор того же события в топике не меняет свечу.
- Два экземпляра API в одной группе потребителей: каждая сделка учтена ровно один раз.

Инфраструктура этапа — Kafka (KRaft, один узел) в `infra/docker-compose.yml`. Тесты на этапе останавливают и поднимают брокер.

---design
Сделка в базе и событие в Kafka — две разные системы, общей транзакции у них нет. Как гарантировать «если есть сделка — будет и событие»?
Что ты выберешь: at-most-once, at-least-once или exactly-once — и где тогда нужна идемпотентность? Как сохранить порядок, если публикаторов два?

---primer Kafka за 10 минут
Kafka — **журнал**: сообщения дописываются в конец и хранятся заданное время, их можно перечитать. Топик делится на **партиции**;
порядок гарантируется только **внутри партиции**, а партицию выбирает ключ сообщения (одинаковый ключ — одна партиция).
Потребители объединяются в **группу**: партиции делятся между участниками группы, каждое сообщение обрабатывает один участник.
Где группа остановилась — **оффсет**, который потребитель коммитит сам.

```bash
dotnet add src/Exchange.Api package Confluent.Kafka
```

```csharp
using var producer = new ProducerBuilder<string, string>(new ProducerConfig
{
    BootstrapServers = "localhost:19092",
    EnableIdempotence = true,   // повторы внутри продюсера не создают дублей
    Acks = Acks.All,
}).Build();
await producer.ProduceAsync("orders", new Message<string, string> { Key = "user-42", Value = "{...}" });

using var consumer = new ConsumerBuilder<string, string>(new ConsumerConfig
{
    BootstrapServers = "localhost:19092",
    GroupId = "emails",
    AutoOffsetReset = AutoOffsetReset.Earliest,
    EnableAutoCommit = false,   // коммитим сами, после обработки
}).Build();
consumer.Subscribe("orders");
while (!ct.IsCancellationRequested)
{
    var r = consumer.Consume(ct);
    Handle(r.Message.Value);
    consumer.Commit(r);         // упали до этой строки — сообщение придёт снова
}
```

Фоновую работу в ASP.NET Core делают в `BackgroundService` (`builder.Services.AddHostedService<T>()`). Блокирующий `Consume` — в `Task.Run`.

3. Фоновый публикатор outbox: забирает неотправленные по порядку, отправляет, отмечает. Что будет с порядком, если публикаторов два?

5. `GET /candles/{ticker}`.

---hint
«Закоммитить в базу, потом отправить в Kafka» теряет событие, если процесс упал между шагами или Kafka недоступна. «Сначала в Kafka, потом
в базу» шлёт событие о сделке, которой может не оказаться. Единственная надёжная точка — сама база: событие — строка в той же транзакции,
а отправка — отдельный процесс, который повторяет, пока не получится.

---hint
Публикатор outbox отправляет **at-least-once**: отправил, но упал до отметки «отправлено» — после перезапуска отправит ещё раз. Значит,
дубликаты в топике возможны всегда, и защищаться от них должен потребитель: «уже видел этот tradeId» + изменение свечи в одной транзакции,
коммит оффсета — после. Два публикатора на двух серверах перемешают порядок: пусть активен один (`pg_try_advisory_xact_lock`).

---hint
Потребитель: `EnableAutoCommit = false`, `AutoOffsetReset = Earliest`, обработка → `consumer.Commit(r)`. Идемпотентность:
`INSERT INTO processed_trades (trade_id) VALUES (…) ON CONFLICT DO NOTHING` — 0 строк значит повтор. Свеча: начало минуты
`at.Ticks - at.Ticks % TimeSpan.TicksPerMinute`. Продюсер: `MessageTimeoutMs` в несколько секунд, чтобы недоступность брокера быстро
превращалась в ошибку и повтор, а не висела.

## Transactional outbox

Это стандартный ответ на вопрос «как надёжно опубликовать событие об изменении в базе» — его спрашивают почти на каждом собеседовании
про микросервисы. Двухфазный коммит между базой и брокером (XA) медленный и плохо поддерживается. Outbox превращает задачу в локальную
транзакцию плюс повторяемую отправку. Альтернатива — **CDC** (Change Data Capture, Debezium): читать журнал изменений базы и публиковать
его. Без опроса таблицы, но с ещё одной системой в эксплуатации.

## Семантика доставки

- **At-most-once** — отправил и забыл: быстро, но теряет.
- **At-least-once** — повторяет до подтверждения: не теряет, но дублирует. Почти всегда выбирают это.
- **Exactly-once** — на уровне Kafka есть транзакции продюсера и read-process-write внутри Kafka, но как только побочный эффект выходит
  наружу (база, письмо), «ровно один раз» достигается только как **at-least-once + идемпотентный обработчик**. Это и есть правильный ответ на собеседовании.

## Порядок и партиции

Kafka гарантирует порядок только внутри партиции. Ключ = тикер кладёт все сделки инструмента в одну партицию — порядок сохранён, а разные
инструменты обрабатываются параллельно. Цена: «горячий» ключ (все торгуют SBER) упирается в одну партицию и одного потребителя.
Число партиций — потолок параллелизма группы: потребителей больше, чем партиций, — лишние простаивают.

## Почему один публикатор

Два публикатора outbox на двух серверах берут разные пачки и отправляют одновременно — события одного тикера перемешиваются. Варианты:
один активный (leader election через advisory lock, как у нас), разделение outbox по ключам между экземплярами, или CDC. Порядок
и параллелизм всегда конфликтуют — выбираешь, что важнее.

## Kafka или RabbitMQ

RabbitMQ — очередь: сообщение отдали потребителю и удалили, сложная маршрутизация, приоритеты, задержки. Kafka — журнал: хранит,
можно перечитать с начала новым потребителем, огромная пропускная способность, порядок по партициям. Для событий «что произошло»
(event streaming, аналитика, несколько независимых потребителей) — Kafka; для задач «сделай это» (очередь работ) — часто RabbitMQ.

---recall
Q: Что такое transactional outbox и зачем он нужен?
A: Событие записывается в таблицу outbox в той же транзакции, что и изменение данных; отдельный процесс отправляет его в брокер с повторами. Так событие не теряется и не появляется без изменения.

Q: At-most-once, at-least-once, exactly-once — что выбирают на практике?
A: At-least-once (не теряем, допускаем дубли) + идемпотентный обработчик; exactly-once «из коробки» работает только внутри Kafka.

Q: Как Kafka гарантирует порядок и как этим пользоваться?
A: Только внутри партиции; ключ сообщения выбирает партицию — события одной сущности с одним ключом идут по порядку.

Q: Что такое consumer group?
A: Группа потребителей делит партиции топика между собой: каждое сообщение обрабатывает один участник группы, оффсеты хранятся на группу.

Q: Kafka или RabbitMQ?
A: Kafka — журнал с хранением, перечитыванием и порядком по партициям (потоки событий, много потребителей); RabbitMQ — очередь задач с гибкой маршрутизацией.
