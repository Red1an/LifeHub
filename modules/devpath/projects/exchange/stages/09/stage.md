Ночью в чат пишут: «биржа тормозит». Что тормозит? Сведение, база, Kafka, Redis, сеть? У каких пользователей, с какого времени?
Сейчас ответа нет: есть только `Console.WriteLine` и ощущения. В продакшене систему нужно **видеть**:

- **метрики** — сколько, как быстро, как часто ошибки (числа во времени, дёшево хранить, на них алерты);
- **трейсы** — путь одного запроса через все части системы: HTTP → сведение → outbox → Kafka → потребитель;
- **логи** — подробности конкретного события, по которым можно искать;
- **health checks** — чтобы балансировщик и оркестратор понимали, жив ли экземпляр и можно ли слать ему трафик;
- **алерты** — чтобы о проблеме узнавал дежурный, а не пользователи.

Делаем как в индустрии: приложение пишет телеметрию через **OpenTelemetry** по протоколу OTLP в коллектор, коллектор раздаёт метрики
в **Prometheus**, трейсы в **Jaeger**, а **Grafana** рисует дашборды из твоих файлов.

---task
**Телеметрия** — OpenTelemetry, экспорт по OTLP. Адрес и параметры — стандартные переменные окружения
(`OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_METRIC_EXPORT_INTERVAL` — тесты задают их сами).
В Prometheus должны появиться:

| Метрика | Что |
|---|---|
| `exchange_orders_total{side, ticker}` | принятые заявки |
| `exchange_trades_total{ticker}` | сделки |
| `exchange_match_duration_seconds` | гистограмма времени сведения (по ней считается p99) |
| `http_server_request_duration_seconds{http_route}` | HTTP-метрики сервера |

- **Трейс** запроса с заголовком `traceparent` проходит через outbox и Kafka: в сообщении Kafka есть заголовок `traceparent` того же трейса,
  а в Jaeger у трейса есть span HTTP-сервера и span **потребителя** (тот, что строит свечи).
- **Логи** структурные: о каждой заявке — запись со свойством `OrderId` (шаблон `"… {OrderId} …"`, а не `$"…{id}…"`).
- **Health checks:** `/health/live` — 200, пока процесс жив; `/health/ready` — 200, если доступны PostgreSQL и Redis, иначе 503.
- **Дашборд** Grafana — файл в репозитории `observability/dashboards/*.json`, с «Биржа» в названии и `uid`: заявки по `exchange_orders_total`
  и p99 сведения через `histogram_quantile`.
- **Алерты** — `observability/*.yml` (правила Prometheus): хотя бы одно по метрикам `exchange_*`.

Инфраструктура этапа (хаб поднимет сама): коллектор OTLP — `localhost:14318`, Prometheus — http://localhost:19090,
Grafana — http://localhost:13000, Jaeger — http://localhost:16686.

---primer OpenTelemetry в ASP.NET Core
```bash
dotnet add src/Exchange.Api package OpenTelemetry.Extensions.Hosting
dotnet add src/Exchange.Api package OpenTelemetry.Instrumentation.AspNetCore
dotnet add src/Exchange.Api package OpenTelemetry.Exporter.OpenTelemetryProtocol
```

```csharp
public static class Shop
{
    public static readonly ActivitySource Source = new("Shop");          // span'ы
    private static readonly Meter Meter = new("Shop");                    // метрики
    public static readonly Counter<long> Orders = Meter.CreateCounter<long>("shop.orders");
    public static readonly Histogram<double> PayTime = Meter.CreateHistogram<double>("shop.pay.duration", unit: "s");
}

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("shop-api"))
    .WithMetrics(m => m.AddAspNetCoreInstrumentation().AddMeter("Shop").AddOtlpExporter())
    .WithTracing(t => t.AddAspNetCoreInstrumentation().AddSource("Shop").AddOtlpExporter());

Shop.Orders.Add(1, new KeyValuePair<string, object?>("country", "RU"));   // метка — небольшое число значений!
using (var span = Shop.Source.StartActivity("charge card"))              // свой span внутри запроса
    await gateway.ChargeAsync(…);
```

Health checks:

```csharp
builder.Services.AddHealthChecks().AddCheck<DbCheck>("db", tags: ["ready"]);
app.MapHealthChecks("/health/live", new() { Predicate = _ => false });              // без проверок — жив ли процесс
app.MapHealthChecks("/health/ready", new() { Predicate = c => c.Tags.Contains("ready") });
```

---steps
1. Подключи OpenTelemetry: метрики ASP.NET Core, свой Meter и ActivitySource, экспорт OTLP. Запусти и найди метрики в Prometheus (http://localhost:19090).
2. Свои метрики: заявки, сделки, гистограмма времени сведения (подумай о границах корзин в секундах).
3. Трейс через Kafka: сохрани `traceparent` в строке outbox, положи в заголовок сообщения, у потребителя начни span с этим родителем.
   Найди трейс в Jaeger (http://localhost:16686).
4. Логи: шаблоны со свойствами в ключевых местах.
5. `/health/live` и `/health/ready`.
6. Дашборд в Grafana (http://localhost:13000): собери руками, экспортируй JSON в `observability/dashboards/`, добавь `uid`.
7. Правила алертов в `observability/alerts.yml`: SLO по p99, «торговля встала», доля 5xx.

---hint
Метрика из OpenTelemetry меняет имя в Prometheus: точки становятся подчёркиваниями, к счётчику добавляется `_total`, к единице `s` — `_seconds`.
Значит, счётчик называешь `exchange.orders`, а гистограмму — `exchange.match.duration` с `unit: "s"`. Значения записываются в секундах,
а дефолтные корзины гистограммы рассчитаны на миллисекунды — задай свои через `InstrumentAdvice`.

---hint
Трейс не перепрыгнет через таблицу сам: в момент записи outbox текущий `Activity.Current?.Id` — это и есть `traceparent`. Сохрани его
в строке. Публикатор: начни span-продюсер с этим родителем (`ActivityContext.TryParse`) и положи его id в заголовок сообщения.
Потребитель: прочитай заголовок и начни span с `ActivityKind.Consumer` и этим родителем.

---hint
`/health/live` не должен проверять базу: если база упала, перезапуск процесса не поможет, а оркестратор начнёт убивать здоровые экземпляры.
В `ready` — то, без чего экземпляр бесполезен. Kafka туда **не** входит: outbox переживёт её отсутствие.

---debrief
## Три столпа и зачем все три

Метрики говорят **что** и **сколько** (p99 вырос в 10 раз), трейсы — **где** (время ушло в ожидание блокировки), логи — **почему**
(в этой заявке был вот такой счёт). Без метрик не узнаешь о проблеме, без трейсов не найдёшь её в распределённой системе,
без логов не поймёшь причину. Корреляция — trace id в логах: из трейса прыгаешь в логи этого запроса.

## Перцентили, а не среднее

Среднее время 20 мс может прятать 1% запросов по 3 секунды. А один медленный запрос из ста на каждой странице означает,
что у пользователя, загружающего 10 ресурсов, примерно каждая десятая страница медленная. Поэтому SLO формулируют перцентилями (p95, p99),
а считают их по **гистограмме** (корзины), а не по сохранённым значениям. Границы корзин — проектное решение: слишком крупные — p99 неточный.

## Кардинальность

Каждая уникальная комбинация меток — отдельный временной ряд. Метка `ticker` (десятки значений) — нормально. `userId` или `orderId`
(миллионы) — взрыв рядов, память Prometheus и счёт за мониторинг. Высокая кардинальность — это работа трейсов и логов, а не метрик.

## SLI, SLO, SLA и алерты

**SLI** — что меряем (доля заявок быстрее 100 мс), **SLO** — цель (99,9% за 30 дней), **SLA** — обещание клиенту с последствиями.
Разница между 100% и SLO — **бюджет ошибок**: пока он есть, можно рисковать релизами. Алерт будит человека только на нарушение SLO
пользователя (симптом), а не на «CPU 80%» (причина, которая может ничего не значить). Алерты на всё подряд приучают их игнорировать.

## Почему коллектор, а не прямой экспорт

Приложение говорит на одном протоколе (OTLP) и ничего не знает о Prometheus и Jaeger. Коллектор батчит, фильтрует, семплирует трейсы,
добавляет метаданные и отправляет куда угодно. Сменить Jaeger на Tempo или Prometheus на VictoriaMetrics — поменять конфиг коллектора,
а не код. Альтернатива для .NET-проекта — **.NET Aspire Dashboard** локально: OTLP «из коробки» без всей этой инфраструктуры.

## Liveness и readiness

Liveness «я жив» — если нет, процесс перезапускают. Readiness «готов принимать трафик» — если нет, его выводят из балансировщика, но не трогают.
Классическая авария: зависимость легла, liveness её проверяет, оркестратор перезапускает **все** экземпляры по кругу, и они не успевают подняться.

---recall
Q: Метрики, трейсы и логи — что каждое даёт?
A: Метрики — что и сколько во времени (дёшево, алерты); трейсы — где тратится время запроса по всем сервисам; логи — подробности конкретного события. Связывает их trace id.

Q: Что такое кардинальность метрик и почему она важна?
A: Число уникальных комбинаций меток = число временных рядов. Метки с большим числом значений (userId) взрывают хранилище — для них трейсы и логи.

Q: SLI, SLO, SLA?
A: SLI — измеряемый показатель, SLO — внутренняя цель по нему, SLA — обещание клиенту с последствиями; разница до 100% — бюджет ошибок.

Q: Liveness против readiness?
A: Liveness — жив ли процесс (иначе перезапуск), без проверки зависимостей; readiness — готов ли принимать трафик (иначе вывод из балансировки).

Q: Зачем OpenTelemetry Collector?
A: Единая точка приёма OTLP: батчинг, фильтрация, семплирование и отправка в любые бэкенды; приложение не зависит от Prometheus/Jaeger.
