Сердце биржи — **стакан** (order book): все активные заявки на покупку и продажу. Когда приходит заявка, которая
пересекается по цене со встречной, происходит **сделка**. Правила простые и при этом безжалостные:

- сначала исполняется лучшая цена (самая дешёвая продажа для покупателя, самая дорогая покупка для продавца);
- при равной цене — та заявка, что пришла раньше (приоритет «цена–время»);
- цена сделки — цена заявки, которая **уже стояла** в стакане;
- заявка может исполниться частично, остаток стоит дальше.

Ошибка в любом пункте — и кто-то получает чужие деньги. Поэтому здесь впервые нужны **свои unit-тесты**: логику сведения
ты покрываешь сам, а хаб проверяет, что тесты есть и зелёные.

---primer Чистая логика и unit-тест
Логику, которую сложно проверить через API, выносят в класс без зависимостей: на входе данные, на выходе результат.
Пример — расчёт скидки корзины:

```csharp
public static class Discounts
{
    public static decimal Apply(decimal total, int items) =>
        items >= 10 ? total * 0.9m : items >= 5 ? total * 0.95m : total;
}
```

Тест по схеме «подготовь — сделай — проверь» (Arrange–Act–Assert):

```csharp
public class DiscountsTests
{
    [Fact]
    public void TenItems_TenPercent() => Assert.Equal(900m, Discounts.Apply(1000m, 10));

    [Theory]
    [InlineData(4, 1000)]
    [InlineData(5, 950)]
    [InlineData(9, 950)]   // границы — там живут баги
    public void Thresholds(int items, decimal expected) => Assert.Equal(expected, Discounts.Apply(1000m, items));
}
```

Проект для тестов:

```bash
dotnet new xunit -o tests/Exchange.Tests
dotnet add tests/Exchange.Tests reference src/Exchange.Api
dotnet sln Exchange.slnx add tests/Exchange.Tests
```

## Почему движок без базы

Правила сведения — **доменная логика**, самая ценная часть системы. Если она размазана по эндпоинтам и запросам к базе,
её можно проверить только медленными интеграционными тестами, и каждый крайний случай стоит секунды. Вынесенная в чистый класс,
она проверяется сотней тестов за миллисекунды. Это и есть идея «гексагональной» архитектуры (порты и адаптеры): домен в центре,
база и HTTP — снаружи.

## Пирамида тестов

- **Unit** — много, быстрые, проверяют логику (твои тесты движка).
- **Интеграционные** — меньше, медленнее, проверяют, что части работают вместе: API + база (тесты хаба).
- **E2E** — совсем мало, проверяют сценарий целиком.

Ошибка новичка — только интеграционные тесты («так надёжнее»): они медленные, хрупкие и не показывают, где сломалось.
Ошибка «наоборот» — моки на всё: тесты зелёные, а вместе не работает.

## Как устроены настоящие стаканы

Мы ищем встречные заявки запросом к базе — на каждую заявку O(N). Настоящие биржи держат стакан **в памяти**:
`SortedDictionary<цена, Queue<заявка>>` (или дерево/массив уровней), один поток на инструмент, а в базу и журнал событий пишут
асинхронно. Сведение — микросекунды. Это компромисс «скорость против надёжности»: если процесс упал, стакан восстанавливают
из журнала. Мы придём к этому на этапах 8–9, когда упрёмся в скорость.

## Цена сделки

Почему по цене стоящей заявки? Тот, кто выставил заявку первым, «назначил» цену и рисковал, стоя в стакане.
Пришедший позже соглашается на неё (или на лучшую для себя). Это стимулирует выставлять заявки — давать ликвидность.

? Что такое пирамида тестов?

? Почему для приоритета времени лучше последовательный номер, а не `DateTime.UtcNow`?
- [ ] DateTime медленный
- [x] У двух заявок время может совпасть, а системные часы могут прыгнуть назад
- [ ] DateTime нельзя хранить в PostgreSQL
- [ ] Номер занимает меньше места
> Монотонный счётчик даёт строгий порядок. Время — для людей и аудита.

? Чем хорош unit-тест, а чем плох?
- [ ] Хорош всем, интеграционные не нужны
- [x] Быстрый и точно показывает, где ошибка, но не проверяет, что части работают вместе
- [ ] Медленный, но надёжный
- [ ] Проверяет только UI
> Поэтому нужны оба уровня: unit на логику, интеграционные на связку с базой и HTTP.

---recall
Q: Что такое приоритет «цена–время»?
A: Встречные заявки исполняются сначала по лучшей цене, а при равной цене — в порядке поступления.

Q: По какой цене проходит сделка и почему?
A: По цене заявки, которая уже стояла в стакане: её автор первым назначил цену и дал ликвидность.

Q: Зачем выносить бизнес-логику в класс без зависимостей?
A: Чтобы проверять её быстрыми unit-тестами и менять базу или транспорт, не трогая правила (порты и адаптеры).
