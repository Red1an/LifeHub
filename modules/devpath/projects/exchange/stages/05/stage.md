У биржи есть API, но торговать через curl никто не будет. Нужен **торговый терминал**: выбрать инструмент, видеть стакан,
котировку и сделки, деньги и бумаги счёта, выставить заявку и отменить её.

Это первый фронтенд-этап. Стек — то, что чаще всего просят в вакансиях: **React + TypeScript + Vite**.
Главное здесь не вёрстка, а инженерные вопросы фронтенда: откуда берутся данные, где живёт состояние, как обновлять экран
после действия, что делать с ошибками сети и сервера, как не дать человеку отправить ерунду.

Проверяет хаб по-настоящему: собирает твой фронтенд, поднимает API и открывает терминал в браузере (Edge через Playwright),
нажимает кнопки и смотрит, что на экране.

---task
**Фронтенд** — папка `web/` в корне проекта (Vite + React + TypeScript):

- `npm run build` собирает в `web/dist`; адрес API берётся из `import.meta.env.VITE_API_URL` (хаб собирает с `http://127.0.0.1:15080`);
- терминал открывается по адресу `/?account=<id>&ticker=SBER` (тикер по умолчанию — SBER), инструмент меняется кнопками
  и попадает в адрес — после перезагрузки остаётся тот же.

**Разметка для тестов** — атрибуты `data-testid` (числа — в `data-*`, чтобы не зависеть от форматирования на экране):

| Что | Разметка |
|---|---|
| Кнопки инструментов | `ticker-SBER`, `ticker-GAZP`, … — из `GET /instruments` |
| Деньги | `cash` и `reserved-cash` с `data-value` |
| Бумаги | внутри `positions` — `position` с `data-ticker`, `data-qty`, `data-reserved` |
| Стакан | внутри `bids` и `asks` — `level` с `data-price`, `data-qty`, в порядке API |
| Котировка | `quote-bid`, `quote-ask`, `quote-last` с `data-value` (пусто, если нет) |
| Сделки | внутри `trades` — `trade` с `data-price`, `data-qty`, новые первыми |
| Форма | `side-buy`, `side-sell`, `order-price`, `order-qty`, `order-submit`, ошибка — `form-error` |
| Мои заявки | внутри `orders` — `order` с `data-id`, `data-status`, у активных кнопка `order-cancel` |
| Ошибка целиком | `app-error` (например, счёта нет) |

Поведение:
- после заявки или отмены экран обновляется **без перезагрузки**: резерв, стакан, заявки;
- неверная цена (не кратна 0,01) или количество (не целое > 0) — ошибка в форме **без запроса** к серверу;
- ошибка сервера (например, не хватает денег) — понятный текст в `form-error`;
- несуществующий счёт — `app-error`, а не белый экран; в консоли браузера нет ошибок JS.

**API** — два дополнения:
- `GET /accounts/{id}/orders` — заявки счёта, новые первыми;
- CORS: разрешить запросы с `http://127.0.0.1:15090` (адрес терминала в тестах) и с адреса `vite dev`.

---primer React + TypeScript: компоненты, состояние, эффекты
Создать проект:

```bash
npm create vite@latest web -- --template react-ts
cd web && npm install && npm run dev
```

Компонент — функция, которая по данным возвращает разметку. Состояние — `useState`; при его изменении React перерисовывает компонент.
Загрузка данных — в `useEffect` (он выполняется после отрисовки и при изменении зависимостей):

```tsx
interface Book { id: string; title: string }

export function Library({ shelf }: { shelf: string }) {
  const [books, setBooks] = useState<Book[]>([]);
  const [error, setError] = useState<string | null>(null);

  const load = useCallback(async () => {
    const res = await fetch(`${import.meta.env.VITE_API_URL}/books?shelf=${shelf}`);
    if (!res.ok) return setError(`Ошибка ${res.status}`);
    setBooks(await res.json());
  }, [shelf]);

  useEffect(() => { void load(); }, [load]); // перезагрузится, когда сменится полка

  if (error) return <div data-testid="error">{error}</div>;
  return (
    <ul>
      {books.map((b) => <li key={b.id}>{b.title}</li>)}  {/* key — чтобы React узнавал элементы между отрисовками */}
    </ul>
  );
}
```

Форма — управляемые поля: значение в состоянии, `onChange` его меняет. Сабмит — `onSubmit` с `e.preventDefault()`.

CORS на стороне ASP.NET Core:

```csharp
builder.Services.AddCors(o => o.AddDefaultPolicy(p =>
    p.WithOrigins("http://localhost:5173").AllowAnyHeader().AllowAnyMethod()));
// …
app.UseCors();
```

---steps
1. `npm create vite@latest web -- --template react-ts`, проверь, что `npm run dev` открывается.
2. Модуль API: типы ответов (`interface Account …`), функция `call()` с разбором ProblemDetails в понятный текст.
3. Каркас: чтение `account`/`ticker` из адреса, загрузка всего нужного для экрана (`Promise.all`), состояния «загрузка» и «ошибка».
4. Компоненты: баланс, стакан, котировка, сделки, форма, мои заявки. Сразу ставь `data-testid` из контракта.
5. Форма: проверка ввода до запроса, ошибки сервера, блокировка кнопки на время запроса, обновление экрана после успеха.
6. API: `GET /accounts/{id}/orders` и CORS.
7. «Проверить». Ошибки TypeScript хаб покажет так же, как ошибки C#.

---hint
Если браузер пишет `blocked by CORS policy`, а curl работает — это не баг API. Браузер не даёт странице с одного адреса читать ответы
другого без разрешения сервера. Порт тоже часть адреса: `127.0.0.1:15090` и `127.0.0.1:15080` — разные «источники».

---hint
Не храни в React копию «моих денег», которую сам пересчитываешь после заявки: она разойдётся с сервером при первой же сделке.
Проще и надёжнее после действия перечитать с сервера то, что могло измениться (баланс, заявки, стакан). Одна функция `refresh()`.

---hint
Проверка цены с шагом 0,01: `Math.round(p * 100) === p * 100`. Ошибку ProblemDetails достань из ответа: `errors` (для 400), иначе `detail` или `title`.
Инструмент в адресе: `history.replaceState(null, "", "?" + new URLSearchParams({...}))` и чтение через `new URLSearchParams(location.search)`.

---debrief
## Источник правды — сервер

Самая частая ошибка во фронтенде — держать в состоянии «свою версию» серверных данных и вручную её поддерживать: прибавил заявку
в список, вычел деньги из баланса… При первой сделке, отмене с другого устройства или ошибке сервера копия расходится.
Мы делаем проще: состояние терминала — это **кэш ответов сервера**, а после действия перечитываем то, что могло измениться.
Библиотеки вроде **TanStack Query** (React Query) построены ровно на этой идее: запросы, кэш, инвалидация после мутаций, повторы и загрузка.
В реальном проекте берут её; руками мы писали, чтобы понять, что она решает.

## Проверка на фронте и на сервере

Проверка в форме — для **человека**: мгновенная подсказка без ожидания сети. Проверка на сервере — для **безопасности**:
фронт можно обойти curl-ом. Поэтому правила дублируются, а источник истины — сервер. Хорошая практика — общая схема
(например, Zod на фронте и FluentValidation на сервере по одному описанию).

## Что такое CORS на самом деле

Политика одного источника (same-origin policy) запрещает странице читать ответы с другого «источника» (схема + хост + порт).
CORS — способ сервера сказать браузеру «этому источнику можно». Для запросов с JSON браузер сначала делает **preflight**: `OPTIONS`
с вопросом, разрешены ли метод и заголовки. CORS — защита **пользователя в браузере**, а не API: curl и другие серверы его игнорируют.
Поэтому `AllowAnyOrigin` в продакшене — плохо (особенно с куками), а авторизация всё равно нужна (этап 7).

Альтернатива CORS — раздавать фронт с того же адреса, что и API (через reverse proxy или `vite dev` с proxy). Тогда источник один.

## Почему data-testid

Тесты, которые ищут элементы по CSS-классам или тексту, ломаются от любой правки дизайна или перевода. `data-testid` — договорённость
между разработчиком и тестами: «вот этот элемент — баланс». Числа в `data-value` отделяют проверку логики от форматирования
(`1 500,50 ₽` на экране и `1500.5` в атрибуте). Так же делают в Playwright, Cypress и Testing Library.

## Что дальше

Сейчас терминал узнаёт об изменениях, только когда что-то сделал сам. Чужие сделки и заявки он не видит, пока не перезагрузишь
страницу. Это следующий этап: живые обновления по WebSocket.

---recall
Q: Почему состояние терминала — это кэш ответов сервера, а не своя копия данных?
A: Сервер — источник правды; своя копия расходится при сделках, отменах и ошибках. После действия перечитываем то, что могло измениться (как TanStack Query с инвалидацией).

Q: Что такое CORS и preflight?
A: Браузер не даёт странице читать ответы с другого источника (схема+хост+порт), пока сервер не разрешит заголовком Access-Control-Allow-Origin; для «непростых» запросов сначала уходит OPTIONS (preflight).

Q: Зачем проверять ввод и на фронте, и на сервере?
A: На фронте — мгновенная подсказка человеку; на сервере — защита, потому что фронт можно обойти.

Q: Зачем data-testid в разметке?
A: Стабильная договорённость с тестами: поиск элементов не ломается от правок дизайна и текстов.
