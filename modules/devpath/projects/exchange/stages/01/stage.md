Любая биржа начинается не со сведения сделок, а с **денег**. Клиент открывает счёт, заносит деньги и бумаги,
выставляет заявки. Главное правило с первого дня: нельзя выставить заявку на деньги, которых нет, и нельзя продать дважды одну бумагу.
Поэтому заявка не просто записывается, а **резервирует** деньги или бумаги.

На этом этапе ты с нуля поднимаешь API на ASP.NET Core с базой PostgreSQL. Сведения сделок ещё нет:
заявки просто стоят. Зато фундамент — модель данных, валидация, коды ответов, хранение — должен быть крепким:
на нём держатся следующие 14 этапов.

---task
**Контракт API** (JSON в camelCase, id — `Guid`). Его проверяют тесты хаба в `hub/Stage01`.

| Запрос | Ответ |
|---|---|
| `GET /instruments` | `[{ ticker, name, tick }]` — SBER, GAZP, LKOH есть сразу, шаг цены 0.01 |
| `POST /accounts { name }` | `201 { id, name, … }` |
| `GET /accounts/{id}` | `{ id, name, cash, reservedCash, positions: [{ ticker, qty, reserved }] }` |
| `POST /accounts/{id}/deposit { amount }` | `200` счёт |
| `POST /accounts/{id}/securities { ticker, qty }` | `200` счёт — зачислить бумаги |
| `POST /orders { accountId, ticker, side, price, qty }` | `201 { id, status: "new", … }`, `side` — `buy` или `sell` |
| `GET /orders/{id}` | `{ id, accountId, ticker, side, price, qty, filled, status }` |
| `DELETE /orders/{id}` | `200 { status: "cancelled", … }`, резерв освобождается |

- Покупка резервирует `price × qty` денег, продажа — `qty` бумаг. Свободно = всего − в резерве.
- Неверные данные — `400` в формате ProblemDetails; нет счёта или заявки — `404`; не хватает свободных денег/бумаг
  или повторная отмена — `409`.
- Строка подключения — `ConnectionStrings:Exchange` (тесты подменяют её на свою базу). Схема создаётся при старте приложения.
- Данные переживают перезапуск: всё в PostgreSQL.

Инфраструктура — `infra/docker-compose.yml` (PostgreSQL на порту 15432). Хаб поднимает её сам перед проверкой,
а вручную: `docker compose -f infra/docker-compose.yml up -d`.

```csharp
public class Book
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public required string Title { get; set; }
    public int Copies { get; set; }
    public int Lent { get; set; }          // выдано — как «резерв»
}

public class LibraryDb(DbContextOptions<LibraryDb> options) : DbContext(options)
{
    public DbSet<Book> Books => Set<Book>();
}

// Program.cs
builder.Services.AddDbContext<LibraryDb>(o => o.UseNpgsql(builder.Configuration.GetConnectionString("Library")));
builder.Services.AddProblemDetails();
var app = builder.Build();

using (var scope = app.Services.CreateScope())
    scope.ServiceProvider.GetRequiredService<LibraryDb>().Database.EnsureCreated(); // или Migrate()

app.MapPost("/books/{id:guid}/lend", async (Guid id, LibraryDb db) =>
{
    var book = await db.Books.FindAsync(id);
    if (book is null) return Results.NotFound();
    if (book.Copies - book.Lent < 1) return Results.Problem("Все экземпляры выданы", statusCode: 409);
    book.Lent++;
    await db.SaveChangesAsync();
    return Results.Ok(book);
});

// Ошибки ввода — 400 с полями, как любят фронтендеры:
return Results.ValidationProblem(new Dictionary<string, string[]> { ["title"] = ["Нужно название"] });
```

Деньги — только `decimal`, и в базе тоже: `HasPrecision(18, 2)` даст `numeric(18,2)`, а не `double`.

## Почему резерв, а не проверка при сделке

Если проверять деньги только в момент сделки, клиент может выставить десять заявок на одни и те же деньги — и часть
исполнится в минус. Резерв делает инвариант простым: **свободные деньги никогда не отрицательны**. Так устроены
реальные брокеры: «заблокировано под заявки».

## Почему PostgreSQL

Деньги требуют транзакций и строгой согласованности: изменение счёта и заявки — всё или ничего. Реляционная база даёт это
из коробки (ACID). Документная база (MongoDB) удобна для гибких данных, но транзакции между документами там дороже и сложнее.
Выбирают по свойствам данных, а не по моде.

## Guid или число

`Guid` можно создать на клиенте или в любом сервисе без обращения к базе — удобно в распределённой системе, и id не выдаёт,
сколько у вас клиентов. Минусы: 16 байт против 8, и случайный `Guid` фрагментирует индекс. В PostgreSQL помогает
`Guid.CreateVersion7()` (.NET 9+): он упорядочен по времени.

## EnsureCreated или миграции

`EnsureCreated` создаёт схему, только если базы нет, и **не умеет её менять**. Добавишь таблицу на этапе 2 — у существующей
базы её не появится. В реальном проекте — миграции (`dotnet ef migrations add`, `Database.Migrate()`), они хранят историю
изменений схемы в коде. Тесты хаба каждый раз создают новую базу, поэтому сработает и то и другое. Но для своей рабочей базы
попробуй миграции: этот вопрос любят на собеседованиях.

## Коды ответов

`400` — клиент прислал ерунду, повтор не поможет. `404` — нет ресурса. `409 Conflict` — запрос корректен, но противоречит
текущему состоянию (денег не хватает). Есть школа, которая для бизнес-ошибок использует `422 Unprocessable Entity`. Важно не какой
код, а чтобы он был одинаковым по всему API и клиент мог отличить «исправь запрос» от «повтори позже».

? Клиент пытается купить на 1000 ₽, а свободно 500 ₽. Какой код честнее всего?
- [ ] 400 Bad Request
- [ ] 500 Internal Server Error
- [x] 409 Conflict (или 422, если так принято в API)
- [ ] 404 Not Found

---recall
Q: Зачем бирже (или банку) резервировать деньги под заявку?
A: Чтобы нельзя было потратить одни деньги дважды: свободно = всего − в резерве, и инвариант «свободные ≥ 0» проверяется при каждой заявке.

Q: Чем отличаются коды 400, 404 и 409?
A: 400 — неверный запрос (исправь и повтори), 404 — нет ресурса, 409 — запрос верный, но конфликтует с текущим состоянием.

Q: Плюсы и минусы Guid как первичного ключа?
A: Плюсы: создаётся без базы, не раскрывает количество, удобен в распределённых системах. Минусы: больше места, случайный Guid фрагментирует индекс (помогает Guid v7).
