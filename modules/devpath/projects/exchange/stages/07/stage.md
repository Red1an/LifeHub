Сейчас любой, кто знает id счёта, может выставить с него заявку, посмотреть баланс и даже пополнить себе счёт на миллион.
Перед запуском биржи нужна защита — и это не одна галочка «добавить JWT», а несколько разных угроз:

- **кто ты** — вход по паролю, токены, их срок жизни и отзыв (аутентификация);
- **что тебе можно** — свой счёт да, чужой нет, деньги заводит только администратор (авторизация);
- **подбор пароля** и **заваливание заявками** — ограничения частоты, общие для всех серверов;
- **двойное нажатие и повтор по таймауту** — клиент отправил заявку, ответ потерялся, он шлёт её снова. Без защиты это вторая заявка.

Терминал тоже меняется: форма входа, выход и незаметное обновление токена.

---task
**Вход:**

| Запрос | Ответ |
|---|---|
| `POST /auth/register { login, password }` | `201`; логин занят — `409`; пароль короче 8 — `400` |
| `POST /auth/login { login, password }` | `200 { accessToken, refreshToken, expiresIn }`; неверно — `401` |
| `POST /auth/refresh { refreshToken }` | новая пара токенов; refresh **одноразовый** — повтор `401` |
| `POST /auth/logout { refreshToken }` | `204`, refresh-токен отозван |
| `GET /me` | `{ id, login, roles, accounts: [{ id, name }] }` |

- Access-токен — JWT (подпись ключом `Auth:SigningKey`), живёт `Auth:AccessSeconds` (по умолчанию 900).
- Администратор создаётся при старте из `Auth:AdminLogin` / `Auth:AdminPassword`, у него роль `admin`.

**Доступ:**
- без токена — `401` на всё, кроме данных рынка (`/instruments`, `/orderbook`, `/trades`, `/quotes`, `/ws/quotes`) и `/auth/*`;
- счёт принадлежит тому, кто его создал; чужие счета и заявки — `403` или `404`;
- пополнение денег и бумаг — только `admin` (пользователю — `403`); администратор видит и может всё.

**Защита от злоупотреблений:**
- не больше **20 заявок в секунду** на пользователя, **общий счётчик для всех экземпляров** API; сверх — `429` и заголовок `Retry-After`. Администратор не ограничен;
- после **5 неудачных** входов подряд логин закрыт на несколько минут (`429`), даже с верным паролем;
- заголовок `Idempotency-Key` у `POST /orders`: повтор с тем же ключом возвращает **ту же** заявку и не создаёт новую (даже параллельно с двух серверов);
  тот же ключ с другой заявкой — `422`.

**Терминал:**
- без входа — форма: `login-form`, `login-user`, `login-pass`, `login-submit`, ошибка — `login-error`;
- токены хранятся в `localStorage["exchange.auth"]` как `{ accessToken, refreshToken }`; к запросам — `Authorization: Bearer …`;
- счёт берётся из `?account=…`, иначе первый из `/me`;
- кнопка `logout` — выход (форма входа, токены стёрты);
- истёк access-токен — терминал сам делает refresh и повторяет запрос, человек ничего не замечает.

---design
Какие угрозы ты закрываешь каждым механизмом и какие не закрываешь? Почему access-токен короткий, а refresh — длинный и одноразовый?
Где хранить счётчики лимитов и ключи идемпотентности, если серверов два, и что будет, если это хранилище недоступно?

---primer JWT-вход в ASP.NET Core
```bash
dotnet add src/Exchange.Api package Microsoft.AspNetCore.Authentication.JwtBearer
```

```csharp
var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(builder.Configuration["Auth:SigningKey"]!));
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o => o.TokenValidationParameters = new()
    {
        ValidIssuer = "shop", ValidAudience = "shop", IssuerSigningKey = key,
        ClockSkew = TimeSpan.FromSeconds(5),   // по умолчанию 5 минут!
    });
builder.Services.AddAuthorizationBuilder().AddPolicy("admin", p => p.RequireRole("admin"));

app.UseAuthentication();
app.UseAuthorization();

app.MapGet("/cart", (ClaimsPrincipal user) => $"Корзина {user.FindFirstValue("sub")}").RequireAuthorization();
app.MapPost("/prices", () => Results.Ok()).RequireAuthorization("admin");

// Выдача токена (после проверки пароля):
var token = new JsonWebTokenHandler().CreateToken(new SecurityTokenDescriptor
{
    Issuer = "shop", Audience = "shop",
    Claims = new Dictionary<string, object> { ["sub"] = user.Id.ToString(), ["role"] = "admin" },
    Expires = DateTime.UtcNow.AddMinutes(15),
    SigningCredentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256),
});
```

Пароль храни только хэшем с солью и «медленной» функцией: `Rfc2898DeriveBytes.Pbkdf2(password, salt, 100_000, HashAlgorithmName.SHA256, 32)`
(или `PasswordHasher<T>` из Identity). Сравнение — `CryptographicOperations.FixedTimeEquals`.

---steps
1. Пользователи и хэши паролей, регистрация и вход, выдача JWT.
2. Подключи проверку токенов, раздели эндпоинты: публичные, для пользователя, для администратора. Владелец у счёта.
3. Refresh-токены: случайные, хранятся хэшем, одноразовые, отзыв при выходе.
4. Администратор из настроек при старте. Проверь, что тесты прошлых этапов (они ходят от его имени) снова зелёные.
5. Лимит заявок и блокировка подбора пароля — счётчики в Redis.
6. `Idempotency-Key`: где хранить, как сделать «проверил — создал» атомарным для двух серверов.
7. Терминал: форма входа, хранение токенов, заголовок, тихий refresh, выход.

---hint
Чужой счёт — что вернуть: 403 или 404? 403 честно говорит «есть, но не твоё» — и подтверждает, что такой id существует. 404 ничего не раскрывает.
Оба варианта приняты в индустрии, но выбор надо уметь объяснить. И проверка владельца нужна везде, где id приходит от клиента, — в том числе
в `POST /orders` (accountId в теле) и в `DELETE /orders/{id}`.

---hint
Встроенный `AddRateLimiter` в ASP.NET Core считает **в памяти одного экземпляра** — с двумя серверами лимит удвоится. Общий счётчик — в Redis:
`INCR rate:orders:{userId}` и `PEXPIRE 1000` при первом инкременте (одним Lua-скриптом, чтобы не было ключа без срока жизни).
Ключ идемпотентности проверяй и записывай **в той же транзакции и под той же блокировкой**, что и создание заявки, — иначе два параллельных
повтора проверят «ключа нет» одновременно.

---hint
Refresh: храни SHA-256 от токена, при использовании — `UPDATE … SET used_at = now() WHERE hash = @h AND used_at IS NULL` и смотри,
изменилась ли строка: так два одновременных refresh одним токеном не пройдут оба. В терминале: при 401 один общий промис refresh на все
запросы, повтор запроса один раз; refresh не удался — стереть токены и показать вход.

---debrief
## Аутентификация и авторизация

Аутентификация отвечает на вопрос «кто ты» (пароль → токен), авторизация — «что тебе можно» (роль, владение ресурсом). Самые частые дыры
на практике — не в криптографии, а в авторизации: **IDOR** (Insecure Direct Object Reference) — поменял id в запросе и получил чужое.
Это №1 в OWASP API Top 10 (Broken Object Level Authorization). Защита — проверка владельца **на каждом** обращении к ресурсу по id.

## Почему access короткий, а refresh одноразовый

JWT проверяется без базы — это быстро, но **его нельзя отозвать** до истечения срока. Поэтому access живёт минуты: украли — вред ограничен.
Refresh живёт долго, но хранится на сервере (хэшем), одноразовый и отзывается при выходе. Ротация даёт бонус: если украденный refresh
использовали, у настоящего владельца следующий refresh не пройдёт — и это сигнал, что токен утёк (можно отозвать всю цепочку).

## Где хранить токены в браузере

`localStorage` — просто, но доступен любому JS на странице: XSS = кража токенов. Альтернатива — refresh в **HttpOnly Secure SameSite** cookie,
access — только в памяти. Тогда JS refresh не прочитает, но появляется CSRF, который закрывают SameSite и анти-CSRF токеном. Для учебного
терминала мы взяли localStorage, на защите тебя спросят, чем это плохо.

## Пароли

Хэш с солью и **медленной** функцией (PBKDF2, bcrypt, scrypt, Argon2): соль ломает радужные таблицы, медленность — перебор.
SHA-256 от пароля — плохо: он быстрый, видеокарта переберёт миллиарды в секунду. Одинаковый ответ на «нет такого логина» и «неверный пароль»
и сравнение за постоянное время не дают выяснить по ответу, что существует.

## Лимиты: fail open или fail closed

Redis лёг — пропускать всех (fail open) или отказывать всем (fail closed)? Для лимита заявок мы выбрали fail open: биржа без лимита
опаснее, чем биржа, которая не торгует? Это решение, а не очевидность. Для блокировки подбора пароля часто выбирают обратное.
Важно, что выбор сделан сознательно, записан и виден в метриках (этап 9).

## Идемпотентность — снова

Тот же принцип, что в миссии про платёжку, но со стороны сервера: клиент присылает ключ, сервер помнит «ключ → ответ».
Тонкость — атомарность: проверка и запись в одной транзакции под блокировкой, иначе два повтора пройдут оба. В реальных API (Stripe)
ключи живут сутки, ответ хранится целиком, а тот же ключ с другим телом — ошибка.

---recall
Q: Чем аутентификация отличается от авторизации?
A: Аутентификация — кто ты (проверка личности, выдача токена), авторизация — что тебе можно (роли, владение ресурсом).

Q: Зачем пара access + refresh токенов и ротация refresh?
A: Access короткий и проверяется без базы, но не отзывается; refresh хранится на сервере, отзывается и одноразовый — повторное использование выдаёт кражу.

Q: Как хранить пароли?
A: Хэш медленной функцией (PBKDF2/bcrypt/Argon2) с уникальной солью, сравнение за постоянное время, одинаковый ответ на «нет логина» и «неверный пароль».

Q: Как сделать лимит частоты для нескольких экземпляров API?
A: Общий счётчик в Redis (INCR + EXPIRE атомарно) или лимит на API-шлюзе; встроенный лимитер в памяти считает только свой экземпляр.

Q: Как сделать POST идемпотентным по ключу?
A: Клиент шлёт Idempotency-Key; сервер в одной транзакции проверяет и сохраняет «ключ → ответ»; повтор получает тот же ответ, тот же ключ с другим телом — ошибка.
