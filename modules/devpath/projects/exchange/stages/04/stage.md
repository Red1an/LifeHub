Трейдеру нужно видеть рынок **сейчас**: лучшую цену покупки (bid), лучшую цену продажи (ask) и цену последней сделки (last).
Сейчас для этого есть только `GET /orderbook`, который каждый раз группирует все заявки в базе. Терминал опрашивает его раз в секунду,
у тебя тысяча пользователей — это тысяча тяжёлых запросов в секунду в базу ради трёх чисел, которые меняются только после заявки или отмены.

Решение из двух частей:
- **кэш**: котировка лежит в Redis и пересчитывается только когда меняется стакан;
- **push вместо опроса**: клиент держит WebSocket, сервер сам присылает изменения.

Сложность в том, что серверов два: заявка пришла на первый, а клиент подключён ко второму. Значит, экземплярам нужен общий канал — **Redis pub/sub**.

---task
Добавляется к контракту:

| Запрос | Ответ |
|---|---|
| `GET /quotes/{ticker}` | `{ ticker, bid, ask, last }` — числа или `null`, если нет заявок/сделок; неизвестный тикер — `404` |
| WebSocket `/ws/quotes?ticker=SBER` | сразу после подключения — текущая котировка, дальше — сообщения при каждом изменении |

Сообщения WebSocket — JSON:
- `{ "type": "quote", "ticker": "SBER", "bid": 300, "ask": 304, "last": 302 }` — котировка изменилась;
- `{ "type": "trade", "ticker": "SBER", "price": 302, "qty": 5 }` — прошла сделка.

Требования:
- котировка хранится в Redis по ключу `quote:{тикер}` (строка подключения — `ConnectionStrings:Redis`, в тестах `localhost:16379`);
- отмена лучшей заявки **сразу** меняет котировку — кэш не устаревает;
- подписчик получает только свой тикер;
- клиент, подключённый к одному экземпляру, получает изменения, которые произошли на другом;
- оборвавшийся клиент не ломает рассылку остальным;
- после параллельной нагрузки на оба сервера котировка совпадает со стаканом.

Инфраструктура этапа — Redis в `infra/docker-compose.yml` (хаб обновит файл сам).

---design
Когда именно обновлять котировку в Redis: до коммита транзакции или после? Что увидит клиент в каждом случае, если транзакция откатится?
Два сервера одновременно пишут котировку SBER — как гарантировать, что старая не перезапишет новую?

WebSocket в Minimal API:

```csharp
app.UseWebSockets();
app.Map("/ws/echo", async (HttpContext ctx) =>
{
    if (!ctx.WebSockets.IsWebSocketRequest) return Results.BadRequest();
    using var ws = await ctx.WebSockets.AcceptWebSocketAsync();
    var buf = new byte[4096];
    while (ws.State == WebSocketState.Open)
    {
        var r = await ws.ReceiveAsync(buf, ctx.RequestAborted);
        if (r.MessageType == WebSocketMessageType.Close)
        {
            await ws.CloseAsync(WebSocketCloseStatus.NormalClosure, "", CancellationToken.None); // ответный Close
            break;
        }
        await ws.SendAsync(buf.AsMemory(0, r.Count), WebSocketMessageType.Text, true, CancellationToken.None);
    }
    return Results.Empty;
});
```

Две вещи, о которые спотыкаются все: у одного сокета **нельзя** вызывать `SendAsync` из двух потоков одновременно (нужен свой `SemaphoreSlim`),
а закрытие — это рукопожатие: на `Close` от клиента сервер отвечает своим `Close`.

---steps
1. Подними Redis (`docker compose -f infra/docker-compose.yml up -d`), подключи `StackExchange.Redis` синглтоном.
2. Функция «посчитать котировку из базы»: лучший bid, лучший ask, цена последней сделки.
3. После каждой заявки и отмены — пересчитать и положить в Redis, `GET /quotes` читает из Redis (промах — из базы).
4. Публикация изменений в канал Redis; каждый экземпляр подписан и раздаёт своим WebSocket-клиентам нужного тикера.
5. WebSocket-эндпоинт: снимок при подключении, реестр клиентов, отписка при обрыве.
6. Подумай о порядке: две заявки, две котировки, два сервера — какая запишется последней?

---hint
Если записать котировку в Redis до COMMIT, а транзакция откатится, клиенты увидят несуществующее. Если записать после COMMIT —
между коммитом и записью может успеть другой сервер со своей, более новой котировкой. Что поможет понять, какая из двух новее?

---hint
Дай котировке номер версии, который растёт в порядке коммитов (например, `nextval` последовательности PostgreSQL, взятый **под той же
блокировкой**, что и сведение). В Redis записывай, только если версия больше текущей. Сделать «сравнить и записать» атомарно в Redis
можно Lua-скриптом (`ScriptEvaluateAsync`).

---hint
Реестр клиентов — `ConcurrentDictionary<Guid, (тикер, WebSocket, SemaphoreSlim)>`. Подписка на канал — одна на экземпляр, при старте приложения.
Ошибка отправки клиенту — удалить его из реестра и продолжить. Цикл чтения сокета прерывай при остановке приложения
(`IHostApplicationLifetime.ApplicationStopping`), иначе сервер не сможет остановиться.

---debrief
## Кэш: что, когда и почему инвалидация — самое сложное

«В информатике две трудные вещи: инвалидация кэша и придумывание имён». Здесь стратегия **write-through**: при каждом изменении источника
(стакан в базе) пересчитываем и пишем кэш. Альтернативы:
- **cache-aside с TTL** — читать из кэша, при промахе — из базы и положить на N секунд. Проще, но котировка устаревает до N секунд — для биржи неприемлемо, для каталога товаров нормально;
- **удалить ключ при изменении** — следующий читатель пересчитает. Дёшево, но «гонка» читателя и писателя может вернуть старое значение в кэш.

## Почему версия

Два сервера, две транзакции: A закоммитила раньше B, но записать в Redis успела позже — и перезаписала новую котировку старой.
Время не помогает (часы серверов расходятся), помогает **монотонная версия**, выданная там, где порядок уже определён — под блокировкой сведения.
Запись «если новее» — атомарно в Redis (Lua). Это частный случай общего приёма: **оптимистичная конкурентность для кэша** и fencing token
для распределённых блокировок.

## Ловушка: кэш переживает базу

Версия котировки живёт в базе (последовательность), а котировка — в Redis. Пересоздал базу (или восстановил из бэкапа), а Redis
оставил — новые версии начинаются с 1, старая котировка в Redis «новее», и обновления молча отбрасываются. На этом попадаются
при деплоях и в тестах: у кэша и источника должен быть общий жизненный цикл, а ключи кэша — префикс окружения или версию схемы.

## Pub/sub и его гарантии

Redis pub/sub — **at-most-once**: если экземпляр в момент публикации переподключался, сообщение потеряно навсегда. Поэтому клиенту
при подключении отдаётся снимок, а сообщения — только «изменения». Для сделок, которые терять нельзя, нужен журнал с хранением:
Redis Streams или Kafka — это этап 8.

## Polling, long polling, SSE, WebSocket

- **Polling** — проще всего, но нагрузка растёт с числом клиентов, а свежесть ограничена интервалом.
- **Server-Sent Events** — односторонний поток по обычному HTTP, авто-переподключение в браузере. Хватает для котировок!
- **WebSocket** — двусторонний канал; нужен, если клиент тоже шлёт (заявки, подписки на лету).
- **SignalR** — обёртка .NET над WebSocket с запасными транспортами, группами и Redis-backplane из коробки. В продакшене чаще берут его;
  руками мы писали, чтобы понимать, что внутри.

## Масштаб

Один экземпляр держит десятки тысяч WebSocket, но рассылка «всем подписчикам SBER» при каждом изменении — это fan-out O(клиентов).
Реальные биржи шлют котировки пачками (conflation: раз в 50–100 мс последнее состояние), а не каждое изменение.

---recall
Q: Write-through, cache-aside и инвалидация удалением — в чём разница?
A: Write-through — при изменении источника сразу пишем новое значение в кэш; cache-aside — читаем из кэша, при промахе грузим из базы (часто с TTL); удаление — при изменении стираем ключ, следующий читатель пересчитает.

Q: Как не дать устаревшей записи в кэше перезаписать новую, если пишут несколько серверов?
A: Монотонная версия, выданная там, где порядок определён (под блокировкой/в транзакции), и атомарная запись «только если версия новее» (Lua в Redis).

Q: Какие гарантии у Redis pub/sub и что делать, если сообщения терять нельзя?
A: At-most-once, без хранения. Клиенту — снимок при подключении; для надёжной доставки — Redis Streams или Kafka.

Q: Polling, SSE, WebSocket — когда что?
A: Polling — редкие обновления и простота; SSE — поток от сервера к клиенту; WebSocket — двусторонний обмен в реальном времени (в .NET часто через SignalR).
