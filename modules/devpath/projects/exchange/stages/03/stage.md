Биржа выросла: одного сервера мало, за балансировщиком теперь **два экземпляра API** на одной базе. И сразу пошли жалобы:

- клиент нажал «Купить» на все деньги десять раз подряд, и прошли две заявки — денег ушло в минус;
- пополнения «пропадают»: внёс 100 раз по рублю, на счету 73 ₽;
- заявку отменили, а она всё равно исполнилась;
- в пик торгов часть запросов падает с 500 и словом `deadlock` в логах.

На одном сервере `SemaphoreSlim` спасал. Но это блокировка **внутри одного процесса**: второй экземпляр про неё не знает.
Теперь защищать данные должна база. Это главный этап про конкурентность — его спрашивают на каждом собеседовании Middle+.

---task
Контракт API не меняется. Тесты этапа поднимают **два экземпляра** приложения на одной базе и бьют в них параллельно:

- 20 одновременных заявок на все деньги — принимается ровно одна, остальные `409`;
- одну бумагу нельзя продать дважды;
- 100 одновременных пополнений по 1 ₽ с двух серверов — на счету ровно 100 ₽;
- пополнение во время торговли не теряется;
- отмена и исполнение одной заявки одновременно — что-то одно, не оба;
- встречная торговля двух счетов не заканчивается дедлоком;
- 300 случайных заявок параллельно — деньги и бумаги сходятся, стакан не «пересекается».

И главное: **ни одного 500**. Конфликт конкурентности — нормальная ситуация, её обрабатывают (ждут блокировку или повторяют транзакцию),
а не отдают клиенту ошибку сервера.

---primer Потерянное обновление и три способа его победить
Классика — счётчик просмотров статьи:

```csharp
var post = await db.Posts.FindAsync(id);   // прочитали views = 10
post.Views++;                              // посчитали 11
await db.SaveChangesAsync();               // записали 11 — а другой запрос тоже записал 11
```

**1. Атомарное изменение в базе** — база сама прибавит к актуальному значению:

```csharp
await db.Posts.Where(p => p.Id == id)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.Views, p => p.Views + 1));
// UPDATE posts SET views = views + 1 WHERE id = @id
```

**2. Пессимистичная блокировка** — заблокировать строку до конца транзакции, остальные ждут:

```csharp
await using var tx = await db.Database.BeginTransactionAsync();
await db.Database.ExecuteSqlAsync($"SELECT 1 FROM \"Posts\" WHERE \"Id\" = {id} FOR UPDATE");
var post = await db.Posts.FindAsync(id);   // теперь никто не изменит её, пока мы не закончим
post.Views++;
await db.SaveChangesAsync();
await tx.CommitAsync();
```

**3. Оптимистичная конкурентность** — не блокировать, а проверить при записи, что строку никто не менял:

```csharp
modelBuilder.Entity<Post>().Property<uint>("xmin").IsRowVersion(); // в PostgreSQL — системная колонка версии
// SaveChanges бросит DbUpdateConcurrencyException, если версия изменилась, — тогда перечитать и повторить
```

Ещё инструмент PostgreSQL — **advisory lock**: блокировка по номеру, а не по строке. `pg_advisory_xact_lock(42)` в транзакции
держится до COMMIT и работает для всех подключений, то есть для всех экземпляров приложения.

Блокировка в памяти (`lock`, `SemaphoreSlim`) живёт в одном процессе. Нужна блокировка, которую видят все экземпляры:
строки в базе (`SELECT … FOR UPDATE`) или `pg_advisory_xact_lock`. Дедлок случается, когда две транзакции берут те же блокировки
в разном порядке. Как сделать порядок одинаковым?

---hint
Рабочая схема: транзакция → `pg_advisory_xact_lock(N)` для сведения (одно сведение за раз на всю биржу) →
`SELECT … FROM "Accounts" WHERE "Id" = ANY(…) ORDER BY "Id" FOR UPDATE` для всех затронутых счетов → изменения → COMMIT.
Отмена берёт ту же advisory-блокировку. Обёртка с повтором при `PostgresException` с `SqlState` `40P01`/`40001`.
Если упрёшься в `53300 too many clients` — посчитай, сколько соединений держат два пула по 100.

## Почему блокировка в памяти не работает

`lock` и `SemaphoreSlim` синхронизируют потоки **одного процесса**. Как только экземпляров два (а в продакшене их почти всегда
несколько — ради отказоустойчивости), общая у них только база. Значит, и инварианты денег держит база. Это первое, что проверяют
вопросом «а если серверов станет два?».

## Какой инструмент когда

- **Атомарный UPDATE** — лучший выбор, когда изменение выражается одной формулой (`cash = cash + x`). Ни блокировок в коде, ни гонок.
  Проверку тоже можно вписать в SQL: `UPDATE … SET cash = cash - x WHERE id = … AND cash - reserved >= x` — и смотреть, сколько строк изменилось.
- **Пессимистичная блокировка (`FOR UPDATE`)** — когда нужно прочитать, подумать и записать (сведение, резервы).
  Цена — ожидание. Правило против дедлоков: **один порядок блокировок для всех** (по Id).
- **Оптимистичная (версия строки)** — когда конфликты редки: никто не ждёт, а проигравший повторяет. При частых конфликтах повторы
  съедают всё время — для горячего счёта маркет-мейкера плохо.
- **SERIALIZABLE** — база сама находит опасные пересечения и прерывает одну из транзакций (40001). Код проще, но повторы
  обязательны и под нагрузкой их много.
- **Advisory lock** — блокировка «по смыслу» (сведение инструмента), а не по строке. Удобна, когда защищаемого ресурса как строки нет.

## Уровни изоляции, которые спросят

`Read Committed` (по умолчанию в PostgreSQL) — каждый запрос видит закоммиченное на момент **запроса**, поэтому потерянное
обновление возможно. `Repeatable Read` — снимок на всю транзакцию, конфликт записи даёт ошибку 40001. `Serializable` — как будто
транзакции шли по очереди. Аномалии: грязное чтение (в PostgreSQL невозможно), неповторяющееся чтение, фантомы,
потерянное обновление, write skew.

## Цена нашего решения

Одна advisory-блокировка на всю биржу — это **одно сведение за раз**. Это корректно, но не масштабируется: SBER ждёт, пока сводится GAZP.
Следующий шаг — блокировка на инструмент (`pg_advisory_xact_lock(hashtext(ticker))`) и аккуратный порядок блокировок счетов
между инструментами. А настоящие биржи вообще уходят от блокировок: **один поток-писатель на инструмент** в памяти и журнал событий
(этапы 8–11). Конкурентность там решается архитектурой, а не локами.

## Пул соединений

Каждый экземпляр держит пул (Npgsql — до 100 соединений). Запрос, ждущий блокировку, держит соединение. Два экземпляра × 100 >
`max_connections = 100` у PostgreSQL — и новые подключения получают `53300 too many clients`. В продакшене между приложением и базой
ставят **PgBouncer** и считают бюджет соединений заранее: экземпляры × размер пула ≤ лимит базы.

---recall
Q: Что такое потерянное обновление и как его избежать?
A: Две транзакции читают одно значение и обе записывают результат — одна запись теряется. Лечат атомарным UPDATE, блокировкой строки (FOR UPDATE) или оптимистичной проверкой версии с повтором.

Q: Чем пессимистичная блокировка отличается от оптимистичной?
A: Пессимистичная блокирует строку заранее, остальные ждут; оптимистичная не блокирует, а при записи проверяет версию и при конфликте повторяет. Первая — для частых конфликтов, вторая — для редких.

Q: Уровни изоляции в PostgreSQL и что они защищают?
A: Read Committed (по умолчанию) — видно закоммиченное на момент запроса; Repeatable Read — снимок на транзакцию; Serializable — как последовательное выполнение, с ошибками 40001 и повторами.

Q: Что такое advisory lock в PostgreSQL?
A: Блокировка по произвольному номеру, а не по строке; pg_advisory_xact_lock держится до конца транзакции и видна всем подключениям — подходит для «сведение инструмента идёт по одному».
