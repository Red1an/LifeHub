Терминал этапа 5 «слепой»: он знает о рынке только то, что прочитал при загрузке или после своего действия.
Кто-то выставил заявку — в стакане её нет. Твою заявку исполнили — статус всё ещё «активна». Трейдер жмёт F5 каждые пять секунд.

Первое, что приходит в голову, — опрашивать сервер раз в секунду. Но тысяча открытых терминалов — это тысяча запросов в секунду
впустую, а обновление всё равно запаздывает на секунду. На этапе 4 ты уже сделал WebSocket с котировками. Теперь его нужно
**правильно** использовать во фронтенде, а это сложнее, чем кажется:

- соединение рвётся (Wi-Fi, сон ноутбука, перезапуск сервера) — нужно переподключаться, и не все клиенты в одну секунду;
- пока связи не было, на рынке что-то произошло — после переподключения нужно догрузить пропущенное;
- при смене инструмента старое соединение надо закрыть, иначе они копятся;
- человек должен видеть, что данные сейчас могут быть неактуальны.

---task
Терминал обновляется **сам**, без перезагрузки и без опроса:

- чужая заявка появляется в стакане, котировка и лента сделок меняются вживую (за секунду-две);
- мою заявку исполнил кто-то другой — меняются её статус, деньги и бумаги;
- когда ничего не происходит, терминал **не ходит в API** (проверяется: 4 секунды тишины — ни одного запроса);
- индикатор связи — `data-testid="connection"` с `data-state`: `online`, `connecting` или `offline`;
- API перезапустили: индикатор уходит из `online`, терминал сам переподключается и показывает то, что произошло, пока связи не было;
- переключение инструментов не плодит соединения: открыт не больше одного WebSocket.

Сообщения WebSocket — из этапа 4 (`/ws/quotes?ticker=…`: `quote` и `trade`). Бэкенд на этом этапе менять не обязательно.

---design

---primer WebSocket в браузере и эффекты с очисткой
```ts
const ws = new WebSocket("ws://localhost:5000/ws/chat?room=1");
ws.onopen = () => console.log("подключились");
ws.onmessage = (e) => console.log(JSON.parse(e.data));
ws.onclose = () => console.log("соединение закрыто"); // и при обрыве, и при ws.close()
ws.close();
```

В React подписки живут в `useEffect`, а функция, которую эффект возвращает, — это **очистка**: она вызывается перед следующим
запуском эффекта (сменились зависимости) и при уходе компонента со страницы.

```tsx
function Room({ room }: { room: string }) {
  const [messages, setMessages] = useState<string[]>([]);
  useEffect(() => {
    const ws = new WebSocket(`ws://localhost:5000/ws/chat?room=${room}`);
    ws.onmessage = (e) => setMessages((m) => [...m, e.data]); // функция-обновление: не нужен свежий messages в замыкании
    return () => ws.close();                                   // сменилась комната — старое соединение закрыто
  }, [room]);
  return <ul>{messages.map((m, i) => <li key={i}>{m}</li>)}</ul>;
}
```

Переподключение с растущей паузой и случайной добавкой (jitter):

```ts
let attempt = 0;
const delay = () => Math.min(10_000, 500 * 2 ** attempt++) + Math.random() * 300;
```

---steps
1. Хук подписки на `/ws/quotes?ticker=…` в `useEffect` с очисткой; адрес — из `VITE_API_URL` с `http` → `ws`.
2. Индикатор связи: `connecting` при первом подключении, `online` после `onopen`, `offline` после обрыва.
3. Переподключение после `onclose` с растущей паузой; при удачном переподключении — перечитать данные (могли пропустить события).
4. Реакция на сообщения: `quote` — сразу на экран; любое изменение — перечитать стакан, сделки и свои данные. Пачку событий
   (одна заявка даёт несколько сообщений) склеить в один запрос.
5. Убери опрос, если он был: в тишине — ни одного запроса.
6. «Проверить» и пройди «Сломай и посмотри».

---hint
Сообщение говорит «что-то изменилось», но в нём нет всего: нового стакана, моих денег, статуса моей заявки. Перечитать с сервера после события —
надёжнее, чем пытаться собрать состояние из событий. Чтобы десять событий подряд не дали десять запросов, отложи перечитывание на 50 мс
и сбрасывай таймер при каждом новом событии (debounce).

---hint
`onclose` срабатывает и при обрыве, и когда ты сам закрыл сокет в очистке эффекта. Отличи эти случаи флагом «эффект остановлен»,
иначе после смены инструмента начнёшь переподключать старый тикер. Обработчики сокета видят функции из момента создания —
свежий `refresh` держи в `useRef`.

---hint
Каркас: `useEffect(() => { let stopped = false; let ws; const connect = () => { ws = new WebSocket(url); ws.onopen = …; ws.onmessage = …;
ws.onclose = () => { if (stopped) return; setState("offline"); setTimeout(connect, delay()); }; }; connect();
return () => { stopped = true; ws?.close(); }; }, [ticker])`. Первое сообщение после подключения — снимок, по нему перечитывать не нужно.

---debrief
## Push вместо polling

Опрос (polling) прост, но платишь дважды: нагрузкой (запросы идут, даже когда ничего не меняется) и задержкой (до интервала опроса).
Push по WebSocket приходит сразу и только когда есть что сказать. Цена — соединение нужно сопровождать: переподключение,
догрузка, индикатор. Компромиссы: **long polling** (запрос висит, пока нет новостей) и **SSE** (поток от сервера по HTTP, сам переподключается).

## Событие как сигнал, а не как данные

Есть два подхода. **Применять дельты**: событие «сделка 3 шт. по 125» — вычесть из стакана, прибавить в ленту. Быстро, но любое
пропущенное или переставленное событие ломает картину навсегда, и нужна нумерация и пересинхронизация. **Событие как сигнал**:
«что-то изменилось — перечитай». Чуть больше запросов, зато картина всегда совпадает с сервером. Мы взяли второе и склеиваем
пачку событий (debounce). Биржевые терминалы с тысячами обновлений в секунду применяют дельты с номерами последовательности и
снимком при расхождении — к этому вернёмся на этапе 10.

## Переподключение: exponential backoff + jitter

Сервер перезапустился — все клиенты оборвались **одновременно**. Если все переподключатся через ровно секунду, сервер получит
удар в тысячу подключений и снова упадёт (thundering herd). Растущая пауза снижает частоту попыток, случайная добавка размазывает
клиентов во времени. Тот же приём, что для повторов запросов в миссии про платёжку.

## Эффекты и очистка в React

`useEffect` — место для подписок (WebSocket, таймеры, события окна). Каждая подписка обязана иметь очистку, иначе:
утечки соединений, обработчики для уже ушедшего со страницы компонента, двойные события. В режиме разработки React
**специально** запускает эффекты дважды (StrictMode), чтобы такие ошибки было видно сразу.

Замыкания: обработчик, созданный в эффекте, видит значения из момента создания. Решения — функциональные обновления
`setState(s => …)`, `useRef` для свежих функций или зависимости эффекта (но тогда сокет переподключится при каждом их изменении).

## Где хранить состояние

Пока у нас один хук на экран, хватает `useState`. Когда экранов и компонентов станет много (стакан в одном месте, баланс в другом,
уведомления в третьем), общее состояние выносят: **Zustand** (простое хранилище с подпиской на части), Redux Toolkit
(строгие правила, удобная отладка) или TanStack Query для серверных данных. Правило выбора: серверные данные — в кэш запросов,
UI-состояние (открыта ли модалка) — локально, и только действительно общее — в глобальное хранилище.

## Оптимистичные обновления

Можно показать «заявка отменена» сразу при клике, не дожидаясь ответа, и откатить, если сервер откажет. Экран кажется мгновенным,
но нужен откат и честный индикатор. Для денег и сделок обычно показывают «отменяется…» до подтверждения: врать о деньгах нельзя.

---recall
Q: Polling, long polling, SSE, WebSocket — чем отличаются?
A: Polling — периодические запросы (просто, но нагрузка и задержка); long polling — запрос висит до события; SSE — односторонний поток сервера по HTTP с авто-переподключением; WebSocket — двусторонний постоянный канал.

Q: Что нужно сделать фронту при обрыве WebSocket?
A: Показать, что связи нет; переподключаться с растущей паузой и jitter; после переподключения перечитать данные, потому что пропущенные события не вернутся.

Q: Зачем функция очистки в useEffect?
A: Закрывает подписки (сокеты, таймеры, слушатели) при смене зависимостей и уходе компонента, иначе утечки и двойные события.

Q: Что такое оптимистичное обновление и когда его не стоит делать?
A: Показать результат до ответа сервера и откатить при ошибке; не стоит для денег и сделок, где важна честность состояния.
