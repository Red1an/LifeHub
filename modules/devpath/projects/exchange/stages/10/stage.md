Открыли торги — пришли маркет-мейкеры. Они держат в стакане тысячи заявок и шлют сотни в секунду. На Grafana видно: p99 сведения
полторы секунды, пропускная способность — несколько десятков заявок в секунду на всю биржу, а при глубоком стакане каждая заявка
становится медленнее. Ты поставил Grafana, теперь пора ей пользоваться.

Главное правило этапа: **сначала измерь, потом ускоряй**. Не «перепишу на что-нибудь быстрое», а: где именно уходит время,
сколько, почему, что изменилось после правки. Тесты этапа — это нагрузочный тест: 32 клиента, два сервера, три инструмента,
стакан на тысячи заявок.

---task
Контракт API не меняется. Тесты (пороги подобраны под этот компьютер):

- **поток**: 1500 заявок от 32 клиентов на два экземпляра API по трём инструментам — не меньше **80 заявок в секунду**, p99 задержки — до **800 мс**;
- **глубокий стакан**: в стакане 3000 заявок, каждая новая покупка пересекает его весь, но берёт одну лучшую — p95 до **45 мс**;
- **чтение стакана**: `GET /orderbook` по стакану на 3000 заявок — p95 до **5 мс**;
- и все тесты прошлых этапов — зелёные. Ускорение, которое ломает деньги или порядок, не ускорение.

Результаты замеров видны в выводе тестов (p50, p95, p99, заявок в секунду).

---design
Где сейчас уходит время одной заявки? Перечисли запросы к базе и Redis на пути `POST /orders` и что из этого происходит под блокировкой.
Что из этого можно не делать, делать реже, делать одним запросом или вне блокировки — и чем каждое ускорение рискует?

---primer Как искать узкое место
1. **Замер снаружи** — нагрузочный тест и перцентили (как в тестах этапа). Цифра «до» обязательна.
2. **Где время** — трейсы (этап 9): span'ы запросов к базе (`Npgsql` пишет их в OpenTelemetry: `AddNpgsql()` в трейсинге) показывают,
   сколько запросов и сколько каждый.
3. **План запроса** — `EXPLAIN (ANALYZE, BUFFERS)` в PostgreSQL:

```sql
EXPLAIN ANALYZE
SELECT * FROM "Orders"
WHERE "Ticker" = 'SBER' AND "Side" = 'sell' AND "Status" IN ('new', 'partial') AND "Price" <= 5000
ORDER BY "Price", "Seq" LIMIT 1;
-- Seq Scan + Sort по всем строкам — плохо; Index Scan по (Ticker, Side, Status, Price, Seq) с LIMIT — хорошо
```

4. **Горячий код в C#** — профилировщик (`dotnet-trace`, `dotnet-counters`, Visual Studio Profiler) и микробенчмарки:

```bash
dotnet new console -o bench && cd bench && dotnet add package BenchmarkDotNet
```

```csharp
[MemoryDiagnoser]
public class MatcherBench
{
    private List<BookOrder> _book = /* 3000 заявок */;
    [Benchmark] public int Match() => Matcher.Match(new BookOrder(Guid.NewGuid(), Side.Buy, 5000, 1, 0), _book).Count;
}
// BenchmarkRunner.Run<MatcherBench>();  — запускать в Release
```

Закон Литтла: среднее число запросов в системе = пропускная способность × среднее время ответа. Если сведение одного инструмента
занимает 25 мс под блокировкой, больше 40 заявок в секунду на инструмент не получится никакими потоками.

---steps
1. Запусти тесты этапа и запиши цифры «до». Посмотри трейс одной заявки: сколько запросов к базе, сколько под блокировкой.
2. Блокировка: нужна ли одна на всю биржу, или хватит одной на инструмент? Что тогда с порядком блокировок счетов?
3. Встречные заявки: читай только нужные (лучшие по цене и времени, не больше нужного количества) — с подходящим индексом. Проверь `EXPLAIN`.
4. Счета: один запрос на все затронутые, а не по два на каждую сделку. Меньше `SaveChanges`.
5. Котировка и версия — одним запросом. Справочник инструментов — в памяти.
6. `GET /orderbook`: группировка в базе вместо загрузки всех заявок, и кэш, который не устаревает (версия котировки из этапа 4).
7. После каждой правки — замер. Правка без эффекта откатывается: сложность без пользы — тоже долг.

---hint
Блокировка на инструмент: `pg_advisory_xact_lock(int, int)` с двумя ключами — номер «сведения» и `hashtext(тикер)`. Внимание к типам:
двухаргументная версия принимает `int`, а не `bigint`. Отмена должна взять ту же блокировку, что и сведение её инструмента, — значит,
сначала узнать тикер заявки, потом заблокировать, потом перечитать заявку.

---hint
Встречных заявок, которые реально исполнятся, не больше `qty` (у каждой остаток ≥ 1). `ORDER BY price, seq LIMIT qty` с индексом
`(Ticker, Side, Status, Price, Seq)` превращает чтение стакана в чтение нескольких строк. И осторожно с «одним SaveChanges на всё»:
EF Core не гарантирует порядок INSERT внутри одного сохранения, а у сделок номер — это порядок исполнения.

---hint
Стакан для чтения: `GROUP BY side, price` в SQL и кэш в Redis с той же версией, что у котировки. Читатель берёт текущую версию котировки,
и если у кэша она такая же — отдаёт готовый JSON без базы; если нет — пересчитывает и кладёт с этой версией. Версию читай до подсчёта:
тогда кэш никогда не окажется старше опубликованной котировки.

---debrief
## Что мы сделали и почему это сработало

- **Блокировка на инструмент** вместо одной на биржу — параллелизм между инструментами. Цена: счета теперь блокируются из разных
  инструментов одновременно — дедлоки возможны, поэтому порядок блокировок и повтор транзакции из этапа 3 стали обязательными.
- **Чтение только нужного** — сведение больше не зависит от глубины стакана: O(исполненных), а не O(стакана).
- **Меньше обращений к базе** — каждое обращение к базе в Docker на Windows стоит порядка миллисекунды, и под блокировкой это прямо
  делит пропускную способность. Запросов стало в несколько раз меньше.
- **Кэш с версией** — чтение стакана из Redis без риска показать устаревшее.

## Почему это всё ещё не биржа

Даже после ускорения потолок — несколько сотен заявок в секунду на инструмент, потому что сведение идёт через базу под блокировкой.
Настоящие биржи сводят **в памяти**: один поток-писатель на инструмент держит стакан в структуре данных, сведение занимает микросекунды,
а надёжность даёт **журнал событий** (event sourcing): каждая заявка сначала пишется в журнал (часто пачками — group commit),
стакан после рестарта восстанавливается проигрыванием журнала, а база получает данные асинхронно. Это архитектура LMAX Disruptor.
Её спрашивают на System Design для финтеха — и ты сможешь объяснить, почему пришёл к ней, а не просто назвать.

## Закон Литтла и очереди

Пропускная способность системы ограничена самой узкой сериализованной частью. Пока заявки ждут одну блокировку, добавление потоков
только удлиняет очередь и задержку (p99 растёт, поток — нет). Поэтому ускоряют то, что под блокировкой, или делят её (шардирование по ключу).

## Как меряют в продакшене

Нагрузочные тесты — отдельный инструмент (k6, NBomber, Gatling), с прогревом, реалистичным профилем (не все бьют в один счёт)
и длительностью минуты, а не секунды. Сравнивают перцентили до/после на одной и той же машине, а результат проверяют в Grafana:
синтетика без наблюдаемости не говорит, **где** узкое место.

---recall
Q: Как искать узкое место в производительности сервиса?
A: Замер снаружи (нагрузка, перцентили) → трейсы (где тратится время запроса) → планы запросов (EXPLAIN ANALYZE) и профилировщик/бенчмарки для кода; после правки — повторный замер.

Q: Что такое закон Литтла?
A: Число запросов в системе = пропускная способность × время ответа; сериализованный участок ограничивает пропускную способность значением 1/время на нём.

Q: Почему реальные биржи сводят заявки в памяти?
A: Сведение через базу под блокировкой упирается в задержку базы; в памяти с одним писателем на инструмент это микросекунды, а надёжность даёт журнал событий и восстановление проигрыванием.

Q: Как сделать кэш, который не отдаёт устаревшее?
A: Версия, растущая с каждым изменением источника; кэш хранит версию, по которой собран, и пересчитывается, если текущая версия другая (версию читать до подсчёта).
